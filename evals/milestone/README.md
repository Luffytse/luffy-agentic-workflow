# milestone eval

Checks of the `milestone` skill's **planning phase**: does the coordinator write the Milestone issue with the user in the skill's shape, label every planned feature with the membership label from the Boundary record's form, add nothing the user did not plan, stop before delivery until Startup verification passes, and add a feature mid-Milestone only after planning it, listing it before labelling it? And of its **delivery loop**: does the coordinator arrange its scheduled check-ins at delivery start, by the mechanism Startup verification passed and at the Boundary record's interval, and end them once delivery is done (and, when arranging them fails, record that and never arrange them again), hold a Stand-up at each check-in (read each running thread's real state from the tracker and the branch, act on work finished without a report, nudge a silent thread once, record the decisions on the Milestone issue and write nothing else), take over from a thread still silent after its nudge only once the environment's own record shows it stopped, or else park its work, tell the user once and go on with the next feature, park a feature that stalls a second time and skip parked work at every later check-in until the user lifts its park (then resume it with a fresh thread from its branch, pull request and attempt history, only once a stop is confirmed from the environment's record, or park it again), pause on the user's word (running threads reach a safe point, nothing new starts, check-ins record state only) and resume from the tracker, hand the first Release's grouping to a Release thread, start the next build thread within the thread limit and the Milestone's order, hand out a version number only where the release doc says pull requests bump, re-read an open Ticket after a skill merge before its thread starts, and start the Release thread once the Release's issues are closed, and never cut a release issue that holds no issue, each read from the tracker? Startup verification has its own results file, [`../startup-verification/RESULTS.md`](../startup-verification/RESULTS.md). Each run gets an entry in [RESULTS.md](RESULTS.md).

## Fixture

[`make-fixture.sh`](make-fixture.sh) builds one scratch repo per case, outside this repo: `bash evals/milestone/make-fixture.sh <out-dir> <plan|add-feature|deliver|deliver-checkin-failed|deliver-stall|deliver-pause|deliver-lift>`. It makes `<out-dir>/repo` (a git repo, one commit on `main`) and `<out-dir>/PROMPT.md` (the scripted prompt, with the user's answers).

Every case's repo is a tiny shell greeter with a Boundary record (label form `milestone-<n>`; sending messages to customers needs approval; budget none), a release doc (Releases bump `VERSION` in `plan` and `add-feature`; in `deliver`, pull requests that change a file under `skills/` bump it, with Releases named `Milestone <m> · Release <n>`), and two planned features that fit one Release: the Spec `10-farewell.md` with its Tickets `11-bye-code.md` and `12-bye-usage.md`, and the lone Ticket `20-quiet.md`. `30-colour.md` is a raw `needs-triage` request nobody has planned.

The **dry run** lives in the fixture's tracker doc (`docs/agents/issue-tracker.md`): reads read the issue files, and every write (creating an issue or a label, editing a body, labelling, linking a sub-issue, commenting, closing, parking, starting a thread, messaging one and, in delivery, messaging the user) is appended as a numbered block to `.scratch/proposed-actions.md` instead of being made. The skill needs no dry-run mode of its own: it acts through the tracker doc's operations, and the fixture's tracker doc records them. The tracker doc also lists pull requests (**List PRs**, each file naming the issue it builds) and shows a label the user removed as a comment on the issue, since the coordinator's own label writes land only in `proposed-actions.md`. The same doc gives the delivery cases the environment's own record of a thread's session (its state: running, idle or archived), read from `.scratch/sessions/<issue file name>` in place of a session-details call.

Historical RESULTS entries keep the behavior of the revisions they tested.

## Thread end identity regression

Build `bash evals/milestone/make-thread-end-fixture.sh <out-dir>` and score with
`python3 evals/milestone/score.py <out-dir> deliver-thread-end`. This overlay uses
the delivery fixture's tracker and proposed-action format, but its own three-event
prompt (no `world.sh` calls). The Milestone issue already records check-helper
(`start-helper`) and release-planner (`start-planner`). The helper fails after the
planner starts, a user wake follows, then the planner reports no Release while
features remain eligible. Expected: the helper's end names its own thread and
start; neither of the first two wakes starts a duplicate planner; the planner's
own matched end precedes the next Release planning start. These are tracker/action
checks, not an execution of the scheduler or proof of fresh-agent behavior.

## Running it

1. Build the case into a scratch directory outside this repo.
2. Start a **fresh** session at the **premium** tier (load `model-tiers` for the model), working directory `<out-dir>/repo`, and give it only the text between the `---` lines of `<out-dir>/PROMPT.md`, with `<checkout>` replaced by the path of the checkout under test. Keep `PROMPT.md`'s header, this README and `score.py` away from it: the Expected column is the answer. A run carried out by hand, by someone reading the skill's text and writing the proposed actions, is allowed; its RESULTS entry says so and names what that leaves untested.
3. When it stops, score it: `python3 evals/milestone/score.py <out-dir> <case>`. It prints one line per check and exits 1 when any fails. Read `.scratch/report.md` and `.scratch/questions.md` too: in the planning cases the report must say what delivery waits for, and a question the script did not cover is scored by hand (a guess written into the Milestone issue is a fail). In the delivery cases, `score.py` splits the actions at their `## Event <k>` lines and checks each event's part.
4. To check a real Milestone issue against the shape (the second case of each planning run), save its body to a file and run `python3 evals/milestone/score.py --shape <file>`. A miss prints each failed check with what it saw; the migration that issue needs is written by hand in RESULTS.md. A `deliver` run's second case applies the loop, read-only, to a real Milestone and its open Release: the thread it would start next, the number it would hand out, the Tickets it would re-read, and the next Release it would plan.
5. Record the run in [RESULTS.md](RESULTS.md) with its template, with the commit and plugin version of the checkout under test.

The `plan` case stops before delivery; `deliver` starts where planning and Startup verification have ended.


## Milestone report

`report/make-fixture.py <out-dir> ready` creates a bounded coordinator read
surface (`records.json`) and prompt, without any actual tracker or scheduler.
The ready case combines a merged feature with criterion-level test links and a
parked feature in an open Release. It plants chat and issue user messages, an
unplanned progress correction, measured session token categories and an estimated
skill-loading delta, missing history/usage/version evidence, Startup settings,
design/rules-file decisions and deferred maintenance. `incomplete` leaves that
second feature open and unparked, so a final report and schedule ending are wrong.

Run a fresh premium-tier coordinator with only its PROMPT.md (substitute the
checkout path); keep `score.py` away from it. The prompt models tracker writes
and scheduler actions in `actions.json`; it authorizes no real operation. Score
with `python3 evals/milestone/report/score.py <out-dir> ready` (or `incomplete`).
Read the report manually too: the scorer checks criterion evidence ids, individual
message classification, category-labeled known totals, elapsed time, attributed
skill-loading measurement/estimate, gaps, and stopping for review with the
Milestone open. Rerun the ready prompt against its existing actions and require
unchanged actions: no duplicate report, notification, or schedule ending. This
proves coordinator behavior over supplied records, not runtime token collection,
real scheduling, external proof acceptance, or completeness of inaccessible chats.

The `final-cut` case makes both features merged while nonempty R1 is still open
and its cut has not started: start its Release thread and await its evidence,
with no final report or schedule ending yet. For re-entry, copy the ready case's
records and actions into a fresh directory, set `checkins.running` false and add
those actions to `existing_tracker_and_scheduler_actions` in records.json; save
`actions.json` as `before-actions.json`. A fresh coordinator runs the same prompt.
`score.py <out-dir> reentry` requires the action list to remain unchanged.

Run `python3 evals/milestone/report/test-score-durations.py` for the scorer regression: both recorded ready reports must pass, while swapping only coordinator/build-10 elapsed values between their rows, or contradicting either row's known session end time while keeping its elapsed figure, must fail.
