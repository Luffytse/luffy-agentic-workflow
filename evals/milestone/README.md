# milestone eval

Checks of the `milestone` skill's **planning phase**: does the coordinator write the Milestone issue with the user in the skill's shape, label every planned feature with the membership label from the Boundary record's form, add nothing the user did not plan, stop before delivery until Startup verification passes, and add a feature mid-Milestone only after planning it, listing it before labelling it? And of its **delivery loop**: does the coordinator hand the first Release's grouping to a Release thread, start the next build thread within the thread limit and the Milestone's order, hand out a version number only where the release doc says pull requests bump, re-read an open Ticket after a skill merge before its thread starts, and start the Release thread once the Release's issues are closed, and never cut a release issue that holds no issue, each read from the tracker? Startup verification has its own results file, [`../startup-verification/RESULTS.md`](../startup-verification/RESULTS.md). Each run gets an entry in [RESULTS.md](RESULTS.md).

## Fixture

[`make-fixture.sh`](make-fixture.sh) builds one scratch repo per case, outside this repo: `bash evals/milestone/make-fixture.sh <out-dir> <plan|add-feature|deliver>`. It makes `<out-dir>/repo` (a git repo, one commit on `main`) and `<out-dir>/PROMPT.md` (the scripted prompt, with the user's answers).

Every case's repo is a tiny shell greeter with a Boundary record (label form `milestone-<n>`; sending messages to customers needs approval; budget none), a release doc (Releases bump `VERSION` in `plan` and `add-feature`; in `deliver`, pull requests that change a file under `skills/` bump it, with Releases named `Milestone <m> · Release <n>`), and two planned features that fit one Release: the Spec `10-farewell.md` with its Tickets `11-bye-code.md` and `12-bye-usage.md`, and the lone Ticket `20-quiet.md`. `30-colour.md` is a raw `needs-triage` request nobody has planned.

The **dry run** lives in the fixture's tracker doc (`docs/agents/issue-tracker.md`): reads read the issue files, and every write (creating an issue or a label, editing a body, labelling, linking a sub-issue, commenting, closing, starting a thread and messaging one) is appended as a numbered block to `.scratch/proposed-actions.md` instead of being made. The skill needs no dry-run mode of its own: it acts through the tracker doc's operations, and the fixture's tracker doc records them.

## Running it

1. Build the case into a scratch directory outside this repo.
2. Start a **fresh** session at the **premium** tier (load `model-tiers` for the model), working directory `<out-dir>/repo`, and give it only the text between the `---` lines of `<out-dir>/PROMPT.md`, with `<checkout>` replaced by the path of the checkout under test. Keep `PROMPT.md`'s header, this README and `score.py` away from it: the Expected column is the answer. A run carried out by hand, by someone reading the skill's text and writing the proposed actions, is allowed; its RESULTS entry says so and names what that leaves untested.
3. When it stops, score it: `python3 evals/milestone/score.py <out-dir> <case>`. It prints one line per check and exits 1 when any fails. Read `.scratch/report.md` and `.scratch/questions.md` too: in the planning cases the report must say what delivery waits for, and a question the script did not cover is scored by hand (a guess written into the Milestone issue is a fail). In `deliver`, `score.py` splits the actions at their `## Event <k>` lines and checks each event's part.
4. To check a real Milestone issue against the shape (the second case of each planning run), save its body to a file and run `python3 evals/milestone/score.py --shape <file>`. A miss prints each failed check with what it saw; the migration that issue needs is written by hand in RESULTS.md. A `deliver` run's second case applies the loop, read-only, to a real Milestone and its open Release: the thread it would start next, the number it would hand out, the Tickets it would re-read, and the next Release it would plan.
5. Record the run in [RESULTS.md](RESULTS.md) with its template, with the commit and plugin version of the checkout under test.

The `plan` case stops before delivery; `deliver` starts where planning and Startup verification have ended.
