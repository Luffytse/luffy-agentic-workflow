# setup-project draft check

The seam is the instruction draft the user reviews, including the difference between projects inside a Milestone and those without an open Milestone agreement. These are bounded draft-stage conversation cases: each supplies facts and explicit shared-understanding confirmation, so it tests drafting rather than re-running the interview. They authorize no project setting, repository file or tracker write.

Run each prompt in a fresh agent with the selected source's `setup-project` skill. Make its sibling `milestone` skill available by name; give only the case prompt, never this scoring guide. Run `milestone-rerun.txt` against main before the change, then both older cases against the candidate. Retain the actual draft and diff locally and record the observed outcomes and limits in the PR evidence. Compare meaning, not exact wording.

For `milestone-rerun.txt`, pass only when the full draft:

- Names the `milestone` skill as the coordinator workflow and `team-lead` for its delivery, points to the repo/docs/tracker, and retains the two-thread limit and backend-before-dashboard order.
- Retains the project's schema-migration merge gate, explicit completion callback, archive rule, and pull-main/reload-changed-skills rule after every merge. Any version hand-out or post-merge Ticket re-read the project wants is its own rule, kept in its instructions or release doc; no skill states one.
- Leaves out the shared thread-kind/brief/model-start rules, Release grouping, nudge/stop/takeover procedure and retro procedure. These are reached through their owning skills.
- Points to the Boundary record rather than copying its check-in interval, budget or deploy approval rule.
- Omits current-work state (`#7`, `#31`, `#32`) and shows a diff against the existing text as well as the full replacement.
- Remains an unsaved draft waiting for the user's approval, with no file/settings write or handover claim.

For `no-milestone.txt`, pass only when the full draft keeps the existing full-instructions behavior: coordinator/thread kinds and their skills (the coordinator running `team-lead` for delivery of planned work), every brief field, Model tiers and model-start rule, project limits/merge rules and standing rules, docs/tracker pointers and tracker lookup for open work. It must not switch this project to the `milestone` workflow, add current-work state or claim approval/save/handover.

These cases do not exercise exploration, an actual grilling exchange, the user's later approval or the coordinator's save operation. Check those unchanged steps by diff inspection; passing draft cases is not evidence that settings were saved. This is a local-source behavior check, not an installed-runtime discovery test.

## Coordinator that cannot load the plugin

`no-plugin.txt` (inside a Milestone) and `no-plugin-outside.txt` (no open Milestone agreement) give a project thread a coordinator that reports a skill list of built-ins only, and the project facts the coverage list needs: the harness, the repo's `CLAUDE.md` rule on main's copy and its coordinator-facing merge-time steps (quoted, since the run has no repo), and the commit to stamp. Decision-level, premium tier, a fresh headless session per run. Give each run a folder holding only the `setup-project`, `milestone`, `team-lead`, `model-tiers`, `to-tickets`, `release` and `triage` skill folders (the last two for their threads' tiers) (from a `git archive` of the branch, or of main for the baseline) and the case prompt, with read-only file tools, told to read nothing outside the folder; never this guide.

For each, score the draft by meaning against `setup-project`'s coverage list. Pass only when the full draft:

1. Starts planning with a planning thread that runs `milestone`, offers the set-aside work first and writes the Milestone issue last, after the features are planned.
2. Has feature planning briefs name the skills a feature thread runs for a Spec and for a lone Ticket, from `milestone`'s Planning step 3 (`grill-with-docs` or `grilling`, then `to-spec` and `to-tickets` for a multi-session feature, or one lone Ticket) or the project's own planning skills where the case gives them (the coverage list prefers those), and carry the Milestone number and the planning thread's link, end with an issue holding acceptance criteria, and report a scope change to the planning thread.
3. Says what happens to a feature the user plans mid-Milestone (planned with the user first, then joins through a thread running `milestone`) and to a bug the user raises then (a `triage` thread files it).
4. Starts a Startup verification thread before any Build thread, and starts no Build thread until its result reads `Verdict: ready` or the user says to go on.
5. Gives `team-lead`'s delivery steps: a Release thread started with `release` when none runs and no open, unparked issue carries an open release issue's label, and either a release issue naming this Milestone is open or a planned feature is open, not parked, carries no release label and is unblocked (or blocked only by open issues `release` ranks ahead of it), its brief leaving cut or plan to `release` (separate plan and cut triggers keyed on a "current Release", as the old loop had, fail); Build threads in the release issue's Order within the slots (two here, and the order rule), none while a Release thread runs, with the Build-thread kinds; and, when a Release thread reports a blocked cut or nothing planned while features are open, tells the user once and starts no Release thread again until that changes or the user writes.
6. Arranges the check-in (through a thread where the coordinator cannot) when Build threads start, and ends it as the report starts, before the report is written.
7. Has every build brief carry the line in `team-lead`'s Wakes that has every worker record what it loaded (load source and version, permission and sandbox settings, session usage reference) and the `CLAUDE.md` rule to follow main's copy of each skill.
8. Says what to do with a thread that goes quiet and that it still holds its slot.
9. Starts the report only once the last Release cut has ended, then waits for the user's review: on acceptance a thread closes the Milestone issue; a feature sent back goes back into delivery, with the check-in arranged again and a new report linking the earlier one.
10. Names thread kinds and tiers, chore threads included (a tier the given skills do not name is taken from `model-tiers`' "Use for" column or named to the user as unfilled), and writes a tier map with a model for each tier.
11. Copies both merge-time steps from the case's `CLAUDE.md` quote, with who gives the number, how it is raised, one out at a time, and the re-read before the next start.
12. Gives, in the draft, the meaning of parked, Order, order rule and report re-entry; a pointer to a skill or a doc the coordinator cannot read does not count.
13. Carries the stamp `4f2c9e1` and, in the Startup verification step, has the thread compare it with main's and the coordinator tell the user once to re-run `setup-project` when it moved, going on unless the user says to wait.
14. Does not tell the coordinator to run `milestone`, `team-lead` or `release` itself.
15. For `no-plugin.txt`, keeps the project choices (two-thread limit, backend before dashboard, migration merge gate) and points to the Boundary record (or gives its values); for `no-plugin-outside.txt`, keeps the full instructions (thread kinds and skills, every brief field, Model tiers and model-start rule, limits and merge rules, tracker lookup).
16. Holds no current-work state and claims no approval, save or handover.

Main's skill copies the earlier delivery loop's five steps (from a file this change deletes), so it is expected to fail items 1, 2, 3, 5, 6, 7, 8, 9, 10, 11, 12 and 13, and to pass 4 (the loop's step 1), 14, 15 and 16 (11 may pass too, as a project merge gate).

Both older prompts state that the coordinator, asked to check its own skill list, answered that it can load `team-lead`, `milestone`, `release` and `worker-control`; their drafts add none of the assembled cycle: no planning, feature-brief or mid-Milestone steps, no Startup verification step, no delivery or Releases steps, no check-in, no load-source and version line, no quiet-thread rule, no report or acceptance steps, no definitions of terms, no copied merge-time steps beyond what the project's existing text or facts carry, no tier map naming models where the user gave none (in `no-milestone.txt`, a pointer to `model-tiers`' defaults is not a map), and no source stamp. What each older case's own pass list requires is not counted against it. Main passes this too (its text adds nothing for such a coordinator): it is a regression guard.

## Plugin behind main

`no-plugin-behind.txt` is `no-plugin.txt` with the plugin the thread runs from behind main. Run like the no-plugin cases, except that the folder's `skills/team-lead` and `skills/milestone` are an older version's (main `7d9ef50`, whose `team-lead` keeps separate plan and cut triggers keyed on a "current Release"), and `main-skills/` holds the branch's `team-lead` and `milestone` as main's (for the baseline run too). Pass only when the draft's delivery steps and its stamp match: either its Releases step is `main-skills/`'s (one trigger, when none runs and no open, unparked issue carries an open release issue's label, the brief leaving cut or plan to `release`) and it carries `4f2c9e1`, or it keeps the older text and its stamp is not `4f2c9e1`, with the user told. The older text stamped `4f2c9e1` fails, and so does a draft with no stamp. Items 14 and 16 above also apply.

## Blind run

A fresh premium-tier session is given only the assembled draft of a passing `no-plugin-outside.txt` branch run (its first scenario starts with no Milestone open), with no skills, no repo, no `CLAUDE.md` and no tools, and acts as that coordinator through these scenarios, saying at each what it does and anything it would need a skill or a doc it cannot read for: the user asks for a Milestone; two features planned in parallel threads; a feature thread reports a scope change; planning settles; Startup verification (stamp unchanged, then moved); the first Release; Build threads started; the user plans a feature mid-Milestone; the user raises a bug; a skill pull request asks for its version number while another is out; that merge and the re-read; a thread quiet past a check-in; a Release thread reports a blocked cut; the last Release's issues all closed; the report; the user sends a feature back; the user accepts. A scorer, given the draft and the branch's `setup-project`, `milestone` and `team-lead` folders, marks each scenario pass when the session's action is what those skills give for that point (for the stamp moving at Startup verification, a bug the user raises and the user's acceptance, what `setup-project`'s coverage list gives; for the skills a feature planning thread runs, the project's own planning skills count where the case gives them) and the session needed no skill or doc it cannot read; a repo doc the draft links (the index, the tracker doc, the Boundary record) does not count as needed; a skill, a skill's own file, or a meaning or step the coverage list says the draft carries does. Where the draft has no step for a scenario, the scorer names the gap. One failed scenario fails the run. The same scenarios run once on main's `no-plugin-outside.txt` draft as the baseline, expected to fail at the latest at Startup verification with the stamp moved (main's draft has no stamp).
