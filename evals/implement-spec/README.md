# implement-spec eval

Build-flow checks of `implement-spec`. Each run gets an entry in [RESULTS.md](RESULTS.md).

## Merge-authority check

**Run level**, as in [`implement`'s README](../implement/README.md#run-level): the six merge-authority cases are decision-level in a subagent (from step 8) or full build-flow in a top-level session (a session that can start the Implementers and the reviewers); the three membership cases are decision-level in a subagent only. Record the level in every RESULTS entry.

The same check as `implement`'s ([its README](../implement/README.md#merge-authority-check)), for the Spec thread's step 8, which loads `merging` (the rule is `merging`'s; the cases are its [own eval](../merging/README.md), here run through the Spec thread): one merge rule for every Spec pull request, whether the Spec carries a Milestone label or not (the Boundary record applies as written; a Milestone issue holds no boundaries of its own); the Spec pull request's Door is one-way if any ticket's is; any bump is the release doc's merge-time step, taken for the Spec pull request only; the `Agent-merged rules:` line is written in the body on every agent merge that changes a rules file or carries a design answer, and step 9's report names the same items.

Build each case with the `spec` flow: `bash evals/implement/merge-authority/make-fixture.sh <out-dir> <case> spec`. The work issue `.scratch/issues/10-work.md` is then a Spec (`Type: spec`) with two tickets, `11-code.md` (the code and test) and `12-adr.md` (the ADR, blocked by 11); only the Spec carries the Milestone label. Run, score and record it as `implement`'s README says (a decision-level run starts at step 8 and lists steps 1 to 7 as not exercised), with the Spec thread's prompt from `<out-dir>/PROMPT.md`, and the same six cases and Expected lines: `no-milestone`, `inside-deep-adr`, `inside-boundary`, `outside-boundary`, `no-record-twoway` and `no-record-oneway`. The shared fixture also has the corrective-check membership decisions described in that README: run all three additional cases (`retro-inside`, `retro-outside`, `unrelated-no-issue`) with `spec`, whose membership source is the originating Spec, not its child Tickets; under the one rule all three end in a merge by the thread, listed on the `Agent-merged rules:` line.

## Closing check

**Run level**: decision-level in a session (every tracker, pull request and git write is a block in `.scratch/proposed-actions.md`). Only landed Tickets and the Spec close after the merge; a dropped Ticket stays open. [`closing/`](closing/) holds a fixture builder (`make_fixture.py`: Spec 20, Tickets 21 and 22 landed on `spec-20`, Ticket 23 dropped by the user but still in the Spec pull request's `Closes` lines), the Spec thread's prompt (`PROMPT.md`, written into the output directory), a scorer (`score.py`) and a self-test (`test_cases.py`). The expected behaviour: step 8 removes Ticket 23's line from the body just before the merge (the fixture's body still carries it, as when a Ticket is dropped while the pull request waits); then the merge is a merge commit titled with the pull request's typed title; only after it are #20, #21 and #22 closed as completed, naming the pull request; #23 is never closed. It scores behaviour on the dry-run blocks, never the skill's sentences.

1. `python3 evals/implement-spec/closing/make_fixture.py <out-dir>`.
2. Start a **fresh** premium-tier session (load `model-tiers`) in `<out-dir>/repo` with the text of `<out-dir>/PROMPT.md` between its `---` lines, `<checkout>` replaced by the checkout under test. Keep `closing/score.py` and `test_cases.py` away from it.
3. `python3 evals/implement-spec/closing/score.py <out-dir>`. Run it twice on fresh fixtures, on the branch's skills and on main's (a `git archive` of main). Record both in [RESULTS.md](RESULTS.md). If the run cannot write `.scratch/report.md`, it returns the report text as its final message and the thread writes that text to the file before scoring, the same way for both runs ([evals guide](../../docs/dev-skills/evals.md#making-model-runs)).

`python3 evals/implement-spec/closing/test_cases.py` (add `-v`) scores a reference run, which must pass, and planted wrong runs, each of which must fail: the dropped Ticket's line left in the body, no body edit, the dropped Ticket closed (completed or not planned), a landed Ticket or the Spec left open, a close before the merge, a squash, the tracker's default merge title, no merge, and a real file write. It is not a model run.

## Ticket-branch check

**Run level**: decision-level in a subagent, regular tier. Step 3.1 on re-entry: a thread died after its Implementer committed and before step 6.4, and a local Ticket branch is left. [`ticket-branch/`](ticket-branch/) holds a fixture builder (`make_fixture.py`: a scratch repo with a bare `origin`, the pushed Spec branch `spec-30` holding Ticket 32's squash commit, and a local, never-pushed `ticket-31` holding one commit; Ticket 31 has not landed), the prompt (`PROMPT.md`, written into the output directory), a scorer (`score.py`) and a self-test (`test_cases.py`). Three scenarios, `reuse` (default), `landed` and `waiting`. Expected in `reuse`: the branch is reused (the worktree is added on the existing branch with no `-b`, nothing deleted or reset), the Spec tip is merged in (never a rebased one), and the Implementer's brief is a handoff of what is done and open that still requires evidence and the ticket check. In `landed` the pushed Spec branch also holds Ticket 31's squash commit (Ticket 32 is landed on the Spec branch too, but its tracker file stays open until the Spec merges) (the ticket landed and the thread died before deleting the local branch): the leftover local branch is discarded (`Branch: discard`, a `git branch -D ticket-31` in `Cleanup:`), no worktree is built and no Implementer started for the landed ticket; reusing it, or recreating it with `-b`, fails. `reuse` is the scenario that separates the branch's skill from main's (main deletes the surviving branch and recreates it with `-b`); `landed` is a stated guard scenario, not a separate discriminating case: it passes on main by design and passes on both, since step 1 already treats a squash commit on the Spec branch as landed, and guards only the landed sentence of step 3.1. `waiting` is step 9 with the Spec thread staying open: Ticket 32 landed on `spec-30` and left its local `ticket-32` (its own pre-squash commit) and a real worktree `wt-32`; Ticket 31 has not landed, waits on the user and keeps its unpushed commit on `ticket-31`, with a real worktree `wt-31` (both worktrees sit beside `repo/`; `fixture.json` records the worktree list). Expected: the cleanup removes `wt-32` and `ticket-32` and never deletes the `ticket-31` branch (removing only the `wt-31` worktree is allowed; no glob, loop or `xargs` delete), `Keep:` lists only what is left and names `ticket-31`, the thread stays open (`Thread: open`) and the report names Ticket 31 as waiting. `waiting` is a stated guard scenario like `landed`, not a discriminating case: a careful model on main's step 9 reads it together with steps 3.1 and 6.4 and keeps the unlanded ticket's branch, so it passes on main by design in such a run (see its [RESULTS.md](RESULTS.md) entry). It guards the new keep sentence of step 9; a model that follows main's "remove any worktrees left and their local Ticket branches" literally would remove `wt-31` and delete `ticket-31`, and the unpushed commit would be lost, which the scorer fails.

1. `python3 evals/implement-spec/ticket-branch/make_fixture.py <out-dir> [reuse|landed|waiting]` (the builder records the scenario in `fixture.json`, which `score.py` reads).
2. Start a **fresh** regular-tier subagent in `<out-dir>/repo` with the text of `<out-dir>/PROMPT.md` between its `---` lines and the whole `implement-spec` folder from the checkout under test. Keep `score.py` and `test_cases.py` away from it. The prompt makes the run read-only and has it write `.scratch/answer.md`.
3. `python3 evals/implement-spec/ticket-branch/score.py <out-dir>`. Run it on the branch's skill and on main's (a `git archive` of main) and record both in [RESULTS.md](RESULTS.md).

`python3 evals/implement-spec/ticket-branch/test_cases.py` builds the fixture, checks the rendered prompt and repo say what the case means, scores a reference answer (which must pass) and planted wrong ones (each must fail), for all three scenarios. Reuse: recreating the branch with `-b`, discarding it, a rebase, no handoff, no answer, and a branch deleted in git. Landed: reusing the branch, `-b` on the existing branch with no delete, rebuilding the ticket after deleting, discard said but nothing deleted, and no answer. Waiting: the reference and passing variants (also removing only the `wt-31` worktree; `git -C` with `--delete` on `ticket-32`; backticks around each command, the whole line, a branch name or the `Thread:` value; a trailing parenthetical aside), and planted wrong answers: main's step 9 (every worktree and branch removed), deleting `ticket-31` with `--delete`, `-d`, `update-ref -d`, a glob, `xargs` or a loop, leaving `ticket-32` or its worktree or either half of them, `Keep: none`, ending the thread (also in backticks), an aside that follows a `ticket-31` delete, a report that omits the waiting ticket, and no answer. It is not a model run.

## Main-check check

**Run level**: decision-level in a subagent, regular tier. Step 1's "Check against main", for the Spec thread and for a Worker handed one ticket: before anything is made, the Spec (or the Worker's ticket) is read against freshly fetched main; when main already has the work the thread writes no code, tells the coordinator (a Worker also the Spec's owner) it is already fixed or obsolete with evidence on main, and stops; when it does not, the build goes on. [`main-check/`](main-check/) holds a fixture builder (`make_fixture.py`), a scorer (`score.py`) and a self-test (`test_cases.py`). The builder makes a scratch repo with a bare `origin`, a local Markdown tracker (`.scratch/`, outside git) and Spec 50 (2026-10-02) with two unblocked tickets, 51 (`src/bye.sh`) and 52 (`src/shout.sh`), each asking for its script with a test; the local `main` is one commit behind origin's, whose later commit is pull request 9 (2026-10-10, closing no issue). The changed-scope and cannot-tell verdicts and a re-entry after the coordinator's answer are not covered by a case.

| Scenario | Pull request 9 and branches | Expected |
| --- | --- | --- |
| `fixed` (default) | added both commands and their tests in `test.sh`; no Spec branch | no Spec branch, worktree or Implementer; a message to the coordinator that the Spec is already fixed or obsolete, naming its evidence on main (the commit, pull request 9, `src/bye.sh` or `src/shout.sh`); stopped |
| `valid` | edited only the README; no Spec branch | the Spec branch made and pushed, worktrees and Implementers for 51 and 52, nothing reported fixed; building |
| `worker` | added only `src/bye.sh` and its test (no `shout` script or test); `spec-50` pushed, owned by `spec-thread-50` (its owner record on the Spec); the run is a Worker the coordinator handed Ticket 51 | no branch, worktree or Implementer; the coordinator told Ticket 51 is already fixed or obsolete, with evidence (the commit, pull request 9 or `src/bye.sh`); the owner `spec-thread-50` told too; stopped |

`fixed` and `worker` separate the branch's skill from main's, on the end state: in the recorded runs main's model also noticed the work on main and made nothing, but with no rule for it asked the coordinator and waited, so each fails on `Thread: stopped` (see [RESULTS.md](RESULTS.md)); `valid` is a guard scenario that passes on main by design.

1. `python3 evals/implement-spec/main-check/make_fixture.py <out-dir> [fixed|valid|worker]` (the builder records the scenario in `fixture.json`, which `score.py` reads).
2. Start a **fresh** regular-tier subagent in `<out-dir>/repo` with the text of `<out-dir>/PROMPT.md` between its `---` lines and the whole `implement-spec` folder from the checkout under test (`continuation.md` included; the branch's, then main's from a `git archive`). Keep `score.py`, `test_cases.py` and `fixture.json` away from it. The prompt makes the run read-only and has it write `.scratch/answer.md`.
3. `python3 evals/implement-spec/main-check/score.py <out-dir>`. Run all three scenarios on the branch's skill and on main's and record the runs in [RESULTS.md](RESULTS.md).

`python3 evals/implement-spec/main-check/test_cases.py` builds all three scenarios, checks the rendered prompt and repo say what the case means (the prompt asks for the seven lines and names no rule of the check; the issues are open, unblocked, unparked, older than pull request 9 and name no fix; the local `main` is stale; origin's `main`, its `test.sh` (a test for each command the scenario adds, none in `valid`) and branches are as the table says; in `worker` the owner record names `spec-thread-50` and the prompt hands over Ticket 51), scores a reference answer (which must pass) and planted wrong ones (each must fail): building anyway, a stop with no evidence, evidence with no verdict, a report that still makes a worktree, starts an Implementer or keeps building, a report with evidence that waits instead of stopping (main's recorded runs), and no answer; in `worker` also the owner not told, or told without the verdict; in `valid` calling it fixed, no Spec branch, no push, one ticket only and waiting (a message that says still valid, or one with an incidental "already", passes). A branch made in git fails the dry-run check in all three. It is not a model run.
