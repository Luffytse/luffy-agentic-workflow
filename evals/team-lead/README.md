# team-lead eval

Checks of the `team-lead` skill (`plugins/dev-skills/skills/team-lead/`): its snapshot command, and its delivery as dry runs built on harness events. Each run gets an entry in [RESULTS.md](RESULTS.md).

## Run level

**Run level** means what the runner can show from where it runs. *Decision-level in a subagent*: a fresh subagent (which cannot start subagents of its own) is given the skill and the fixture and says what it would do; steps that start or watch real workers are listed as not exercised. *Full build-flow in a top-level session*: a session that can start subagents, schedule a check-in and archive a worker runs the skill end to end.

| Check | Run level |
| --- | --- |
| `test_snapshot.py`, `test_cases.py` | no model session: ordinary commands |
| the five dry runs (`deliver`, `deliver-stall`, `deliver-pause`, `deliver-lift`, `deliver-earlier`) | decision-level in a subagent: every start, stop, message and check-in is a block in `.scratch/` and every event is scripted, so nothing real is started. A subagent run is not a check that the real Harness starts workers, delivers a check-in or stops one; that is `worker-control`'s check, which needs a top-level session. (Judged from the fixture's prompt; a full build-flow run of these cases has not been tried.) |
| `main-check-report` | decision-level in a subagent: the coordinator writes what it would do for three scripted worker reports; nothing is run |
| `carried-over` | decision-level in a subagent: the coordinator writes what it would do at three scripted wakes; nothing is run |

## Snapshot command: unit tests

`python3 evals/team-lead/test_snapshot.py` runs ordinary unit tests of `snapshot.py` as a command, on disposable git repos with dated commits and fixture tracker data: a local Markdown tracker (issue and pull request files), and GitHub through a stub `gh` on `PATH` that answers the REST routes the command calls. They cover each verdict (active; silent since a time, counted from the last commit, comment or start; nudged and waiting; still silent after its nudge; pull request ready or merged but not reported, and the same reported), a pull request found by the worker's branch when no report named it (a lost report, on both trackers), a ready pull request whose worker still comments or pushes (a Spec thread in its review) counted as working and not flagged, a ready pull request acted on and then tested for silence through `reported`, a resume restarting the silence clock and voiding an earlier nudge (`resumed`), earlier `<!-- milestone ... -->` records (a nudge counts, none is activity), a `###` heading inside a comment body, a nudge recorded minutes after its check-in still counting a whole interval at the next one, a replacement not flagged for its predecessor's merged pull request, the team lead's own records not counting as activity, the harness state printed as given, one row per worker, and the hand-read fallback: an issue the tracker does not have, an unreachable API, no `gh`, a tracker doc the command cannot read and no tracker doc, each exiting 3 with `read by hand` in the tracker cells while git is still read. Run them after changing `snapshot.py`.

## Dry runs on Harness events

[`make-fixture.sh`](make-fixture.sh) builds one case outside this repo: `bash evals/team-lead/make-fixture.sh <out-dir> <deliver|deliver-stall|deliver-pause|deliver-lift|deliver-earlier>`. It makes `<out-dir>/repo` and `<out-dir>/PROMPT.md`. The repo is a tiny greeter at Milestone 1's start: a Milestone issue with three features (the Spec `10-farewell.md` naming Review level Deep, the lone Tickets `20-quiet.md` and `25-hello-doc.md`, 25 blocked by `35-readme-tool.md` outside the Milestone, an enhancement not at `ready-for-agent`, so `release` would not rank it ahead of 25 and no Release starts for 25 while it is open), a passing Startup verification result for the dry-run harness, a Boundary record (check-in every hour), a release doc where pull requests bump, and the repo's merge-time steps (a version number per skill-changing pull request, a re-read of open issues after one merges) in its own `CLAUDE.md`, since the skill states none.

- **Tracker:** a local Markdown tracker in the form `snapshot.py` reads (`docs/dev-skills/issue-tracker.md`); every write is a block in `.scratch/proposed-actions.md`, and branches are the repo's own git branches.
- **Harness:** `docs/dev-skills/harness.md` documents a dry-run harness that `worker-control` has no reference for, so its fallback reads that page: starting, messaging and stopping a worker and arranging a check-in are blocks too, and each worker's state is a line in `.scratch/harness/workers.md`. What the Harness pushes (a worker reporting or asking, a worker that ended or failed, a stop taken, a check-in firing, the user writing) is the case's events.
- **World:** [`world.py`](world.py), copied into the fixture, moves the tracker, git and the harness to each event's state, and applies the coordinator's comment and label blocks to the issue files as the tracker would, so later reads and the snapshot see its nudge, start and park records.

### Running a case

1. Build it into a scratch directory outside this repo.
2. Start a **fresh** session at the **premium** tier (load `model-tiers` for the model), working directory `<out-dir>/repo`, and give it only the text between the `---` lines of `<out-dir>/PROMPT.md`, with `<checkout>` replaced by the checkout under test. Keep this README, `score.py` and `test_cases.py` away from it.
3. Score it: `python3 evals/team-lead/score.py <out-dir> <case>`. It splits the actions at their `## Event <k>` lines and prints one line per check; it exits 1 when any fails. A quiet check-in is scored as an event with no block at all.
4. Record the run in [RESULTS.md](RESULTS.md) with the commit, plugin version and run level under test.

### Self-test of the cases

`python3 evals/team-lead/test_cases.py` builds each case and replays a reference run written by hand from the skill text, event by event as a coordinator would, checking at each check-in that the snapshot prints the verdict the case is built to show; the reference must score clean, and planted wrong runs (a quiet check-in that writes, a takeover before the stop reads back, a start while paused, a second user notice about 10 (alone, beside 20, beside the Milestone issue, or without the file name), a second worker beside an old delivery-thread record, a check-in arranged for a planning-only Release worker) must fail, and a mention of 10 inside the park notice for 20 must pass. It proves the fixture, world, snapshot and scorer agree; it is not a model run of the skill.

## Main-check report

**Run level and tier:** decision-level in a subagent, premium tier. Does the coordinator act on a build worker's check against main as `team-lead`'s "A worker reports or asks" says? Case files in [`main-check-report/`](main-check-report/): `STATE.md` (Milestone 1 with planned features #20 and #25, the bug #30 blocking #25, workers on #20 and #30, and what main holds), `PROMPT.md` (three worker reports, each from that state: #30 already fixed, #20 already fixed, #30 changed scope), `EXPECTED.md` (pass and fail per event; keep it away from the session under test) and `test.sh`, which checks the files exist and that the prompt and state name no rule the case scores (it never greps skill text; `scripts/run-tests.sh` runs it). Give a fresh premium-tier subagent the whole `team-lead` folder from the checkout under test (the branch's, then main's from a `git archive`), `STATE.md` and `PROMPT.md`, and score its answer by hand against `EXPECTED.md`. Event 2 (the planned feature not closed but brought to the user, waiting with no worker started) is the one the change moves (in the recorded run main's skill closed #20 itself); event 1 (the not-planned bug closed as completed with where on main once its evidence is opened, its dependent started) is expected to move but may pass on main, whose skill has no rule for such a report; event 3 is a guard.

## Carried-over Release

**Run level and tier:** decision-level in a subagent, premium tier. Does the coordinator start a Release worker that cuts a Release whose issues were all carried over, as `team-lead`'s **Releases** rule says (no Release worker running and no build of the current Release left, then `release`'s "Find where you are" decides cut or plan)? Case files in [`carried-over/`](carried-over/): `STATE.md` (Milestone 1 with planned features #20 and #25, release issue #40 open with both listed under `## Carried over` and no issue carrying its label, no changelog entry, no worker running), `PROMPT.md` (three wakes, each from that state with one change: a check-in; the user writing while #20 and #25 are both blocked by an issue `release` would not rank ahead; a check-in where #20 still carries the label and its worker is active), `EXPECTED.md` (pass and fail per event; keep it away from the session under test) and `test.sh`, which checks the files exist and that the prompt and state name no rule the case scores (it never greps skill text; `scripts/run-tests.sh` runs it). Build a run folder holding only the `team-lead/` skill folder from the checkout under test (the branch's, then main's, each from a `git archive` of that folder alone), `STATE.md` and `PROMPT.md`; start a fresh premium-tier session in it with read-only file tools, told to read nothing outside that folder; score its answer by hand against `EXPECTED.md`. `STATE.md` names `release`'s tier, since `release` is not given. Event 2 (no planned feature qualifies, so main's rule starts no Release worker and #40 stays open) is the one the change moves; event 1 (main's rule finds no current Release and briefs the worker to fill #40 instead of cutting it) is expected to move but may pass on main if the worker is briefed loosely; event 3 is a guard. `release` is not given: with it, or with a whole checkout to read, a coordinator on main read the cut from `release`'s own step 1 and passed (RESULTS, Ticket #75).
