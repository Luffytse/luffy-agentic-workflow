# team-lead eval

Checks of the `team-lead` skill (`plugins/dev-skills/skills/team-lead/`): its snapshot command, and its delivery as dry runs built on harness events. Each run gets an entry in [RESULTS.md](RESULTS.md).

## Snapshot command: unit tests

`python3 evals/team-lead/test_snapshot.py` runs ordinary unit tests of `snapshot.py` as a command, on disposable git repos with dated commits and fixture tracker data: a local Markdown tracker (issue and pull request files), and GitHub through a stub `gh` on `PATH` that answers the REST routes the command calls. They cover each verdict (active; silent since a time, counted from the last commit, comment or start; nudged and waiting; still silent after its nudge; pull request ready or merged but not reported, and the same reported), a pull request found by the worker's branch when no report named it (a lost report, on both trackers), a ready pull request acted on and then tested for silence through `reported`, a resume restarting the silence clock and voiding an earlier nudge (`resumed`), earlier `<!-- milestone ... -->` records (a nudge counts, none is activity), a `###` heading inside a comment body, a nudge recorded minutes after its check-in still counting a whole interval at the next one, a replacement not flagged for its predecessor's merged pull request, the team lead's own records not counting as activity, the harness state printed as given, one row per worker, and the hand-read fallback: an issue the tracker does not have, an unreachable API, no `gh`, a tracker doc the command cannot read and no tracker doc, each exiting 3 with `read by hand` in the tracker cells while git is still read. Run them after changing `snapshot.py`.

## Dry runs on Harness events

[`make-fixture.sh`](make-fixture.sh) builds one case outside this repo: `bash evals/team-lead/make-fixture.sh <out-dir> <deliver|deliver-stall|deliver-pause|deliver-lift|deliver-earlier>`. It makes `<out-dir>/repo` and `<out-dir>/PROMPT.md`. The repo is a tiny greeter at Milestone 1's start: a Milestone issue with three features (the Spec `10-farewell.md` naming Review depth Deep, the lone Tickets `20-quiet.md` and `25-hello-doc.md`, 25 blocked by `35-readme-tool.md` outside the Milestone), a passing Startup verification result for the dry-run harness, a Boundary record (check-in every hour), a release doc where pull requests bump, and the repo's merge-time steps (a version number per skill-changing pull request, a re-read of open issues after one merges) in its own `CLAUDE.md`, since the skill states none.

- **Tracker:** a local Markdown tracker in the form `snapshot.py` reads (`docs/agents/issue-tracker.md`); every write is a block in `.scratch/proposed-actions.md`, and branches are the repo's own git branches.
- **Harness:** `docs/agents/harness.md` documents a dry-run harness that `worker-control` has no reference for, so its fallback reads that page: starting, messaging and stopping a worker and arranging a check-in are blocks too, and each worker's state is a line in `.scratch/harness/workers.md`. What the Harness pushes (a worker reporting or asking, a worker that ended or failed, a stop taken, a check-in firing, the user writing) is the case's events.
- **World:** [`world.py`](world.py), copied into the fixture, moves the tracker, git and the harness to each event's state, and applies the coordinator's comment and label blocks to the issue files as the tracker would, so later reads and the snapshot see its nudge, start and park records.

### Running a case

1. Build it into a scratch directory outside this repo.
2. Start a **fresh** session at the **premium** tier (load `model-tiers` for the model), working directory `<out-dir>/repo`, and give it only the text between the `---` lines of `<out-dir>/PROMPT.md`, with `<checkout>` replaced by the checkout under test. Keep this README, `score.py` and `test_cases.py` away from it.
3. Score it: `python3 evals/team-lead/score.py <out-dir> <case>`. It splits the actions at their `## Event <k>` lines and prints one line per check; it exits 1 when any fails. A quiet check-in is scored as an event with no block at all.
4. Record the run in [RESULTS.md](RESULTS.md) with the commit and plugin version under test.

### Self-test of the cases

`python3 evals/team-lead/test_cases.py` builds each case and replays a reference run written by hand from the skill text, event by event as a coordinator would, checking at each check-in that the snapshot prints the verdict the case is built to show; the reference must score clean, and planted wrong runs (a quiet check-in that writes, a takeover before the stop reads back, a start while paused, a second worker beside an old delivery-thread record, a check-in arranged for a planning-only Release worker) must fail. It proves the fixture, world, snapshot and scorer agree; it is not a model run of the skill.
