Issue: 41-name-log.md
Body:
~~~
> *This was generated by AI during triage.*

## Agent Brief

**Category:** bug
**Summary:** Stop greet.sh from writing every name it is given to a world-readable log

**Current behavior:**
Every run of the greeter, for any command (including an unknown one that only prints the usage line), appends the name argument (or `world` when none is given) to a shared log file under `/tmp` and then sets that file's mode to 0666. Any user on the machine can read (and write) the file, and callers pass email addresses as the name, so personal data leaks to every local user. Verified on 2026-11-04: `bash src/greet.sh hello probe@example.com` appended `probe@example.com` to the log, and the file's mode was `-rw-rw-rw-`. The write has been present since the greeter's first commit; nothing in the repo reads the log and no issue asked for it.

**Desired behavior:**
The greeter writes no record of the names it is given anywhere on disk. Every command's stdout, stderr and exit code are unchanged: `hello <name>` prints `Hello, <name>!`, `bye <name>` prints `Goodbye, <name>!`, the default name is still `world`, and an unknown command still prints the usage line on stderr and exits 2. The greeter no longer changes the mode of any file.

**Key interfaces:**
- The greeter's command-line contract (`greet.sh <command> <name>`): output and exit codes stay as they are.
- The name-logging side effect: removed, not relocated.

**Acceptance criteria:**
- [ ] Running `hello`, `bye` and an unknown command with a name creates or modifies no file (a test checks that a run leaves the old log file's contents and mode unchanged)
- [ ] The greeter's source contains no `chmod` and no write to a log file
- [ ] `bash test.sh` passes, and it covers the no-log behaviour

**Out of scope:**
- Deleting or cleaning up logs already written on users' machines (a human task, flagged to the user)
- Adding any replacement logging or audit feature
- The usage-line wording issues (#30, #31, #36) and argument parsing (#40)
~~~

### 4. Comment on an issue
Issue: 50-json-output.md
Body:
~~~
> *This was generated by AI during triage.*

## Agent Brief

**Category:** enhancement
**Summary:** Add a `--json` flag that prints the greeting as a JSON object

**Current behavior:**
The greeter prints plain text: `hello <name>` prints `Hello, <name>!` and `bye <name>` prints `Goodbye, <name>!`. Arguments after the name are ignored, so `greet.sh hello Ada --json` prints `Hello, Ada!` and exits 0 (verified 2026-11-04). No JSON output exists anywhere in the greeter.

**Desired behavior:**
With `--json` given after the name, `hello` and `bye` print one line of JSON on stdout with a single `greeting` string field holding exactly the text the plain mode would print, for example `{"greeting": "Hello, Ada!"}`. The name is escaped so the output is valid JSON for any name (quotes, backslashes). Exit codes are unchanged. Without the flag, output is byte-for-byte unchanged. An unknown command keeps printing the usage line on stderr and exiting 2, with or without the flag.

**Key interfaces:**
- The greeter's command-line contract: a new `--json` flag read from the arguments after the name, read the same way as the other flags after the name (see #40, which makes the arguments after the name read at all, and #20, the quiet flag).
- JSON shape: `{"greeting": <string>}`, nothing else.

**Acceptance criteria:**
- [ ] `greet.sh hello Ada --json` prints `{"greeting": "Hello, Ada!"}` and exits 0
- [ ] `greet.sh bye Ada --json` prints `{"greeting": "Goodbye, Ada!"}` and exits 0
- [ ] A name containing `"` or `\` still yields valid JSON (a test parses it)
- [ ] Without `--json`, every existing `test.sh` check passes unchanged
- [ ] `bash test.sh` covers the cases above

**Out of scope:**
- JSON for the usage line or other errors
- Combining `--json` with the quiet flag (#20) or a colour flag (#51)
- Any other output format
- Building the general parsing of arguments after the name, which is #40's; build this after #40 lands
~~~
