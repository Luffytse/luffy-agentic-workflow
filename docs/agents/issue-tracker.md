# Issue tracker: GitHub

Issues and specs for this repo live as GitHub issues in [`Luffytse/luffy-dev-skills`](https://github.com/Luffytse/luffy-dev-skills). Use the `gh` CLI for all operations. A session without `gh` (some cloud sessions) does the same operations with the GitHub tools it has.

Some cloud sessions have `gh` but no GraphQL: `gh repo view`, `gh issue view` and `gh label list` fail with "GraphQL is not available". The other `gh issue` subcommands (list, create, comment, edit, close) fail the same way, so use the session's GitHub tools or the `gh api repos/<owner>/<repo>/issues...` REST routes for them. `gh api repos/<owner>/<repo>/...` (REST) still works, so use it for those: `gh api repos/<owner>/<repo>/issues/<number>` reads an issue (add `/comments` for its comments), `gh api repos/<owner>/<repo>/labels --paginate --jq '.[].name'` lists labels, and `gh api repos/<owner>/<repo>` checks that the repo is reachable.

## Conventions

- **Create an issue**: `gh issue create --title "..." --body "..."`. Use a heredoc for multi-line bodies.
- **Read an issue**: `gh issue view <number> --json number,title,body,labels,comments`.
- **List issues**: `gh issue list --state open --json number,title,body,labels,comments --jq '[.[] | {number, title, body, labels: [.labels[].name], comments: [.comments[].body]}]'` with appropriate `--label` and `--state` filters.
- **Make an issue a sub-issue of a parent**: `gh issue create --parent <parent> ...`, or `gh issue edit <parent> --add-sub-issue <child>` afterwards (`gh` 2.94+). Older `gh`: `gh api --method POST repos/<owner>/<repo>/issues/<parent>/sub_issues -F sub_issue_id=<child-db-id>` (database id, as in **Blocking** below). Without sub-issues, put `Part of #<parent>` on the line after the `Blocked by:` line (the second line of the child body), or as the first line when the child has no `Blocked by:` line (on a child that already exists, see **Add a line to an issue body**).
- **Check a sub-issue link**: the child is linked when either form is present. Native: `gh api --paginate repos/<owner>/<repo>/issues/<parent>/sub_issues --jq '.[].number'` lists the parent's sub-issues and must include the child. Fallback: the child body has a `Part of #<parent>` line (`gh api repos/<owner>/<repo>/issues/<child> --jq .body`).
- **Blocking**: GitHub's **native issue dependencies**, the canonical, UI-visible representation. Add an edge with `gh issue create --blocked-by <n>,<n> ...` or `gh issue edit <child> --add-blocked-by <blocker>` (`gh` 2.94+). Older `gh`, or a session without GraphQL: `gh api --method POST repos/<owner>/<repo>/issues/<child>/dependencies/blocked_by -F issue_id=<blocker-db-id>`, where `<blocker-db-id>` is the blocker's numeric **database id** (`gh api repos/<owner>/<repo>/issues/<n> --jq .id`, _not_ the `#number` or `node_id`). Where dependencies aren't available, fall back to a `Blocked by: #<n>, #<n>` line as the first line of the child body; a `Part of #<parent>` line, if the child needs one, is the second line. The same applies when a native write fails at run time: add the line to the existing ticket (see **Add a line to an issue body**), listing every blocker of the ticket, then check with **Count open blockers** that every blocker is in place in one form or the other. A ticket is unblocked when every blocker is closed, except a blocker closed without the work being done (`state_reason` `not_planned` or `duplicate`, or the `wontfix` label), which does not unblock it. A close as completed counts as done, because GitHub records no reliable link from a blocker to the merged change that built it. This is the rule for tickets that a change builds; a blocker that is itself a wayfinding ticket (label `wayfinder:<type>`) is cleared once closed, and a wayfinding ticket's own blockers follow the wayfinding skill.
- **Count open blockers**: first read a `Blocked by: #<n>` line if the first or second line of the issue body is one (read each named issue's state with `gh api repos/<owner>/<repo>/issues/<n> --jq .state`, and count those that are `open`). It is written first, but a body can have a `Part of #<parent>` line first and the `Blocked by:` line second, so look at both lines. Then `gh api repos/<owner>/<repo>/issues/<n> --jq .issue_dependencies_summary.blocked_by` (open native blockers only). To list the native blockers with their state and how each closed one was closed, `gh api --paginate repos/<owner>/<repo>/issues/<n>/dependencies/blocked_by --jq '.[] | {number, state, state_reason, labels: [.labels[].name]}'` (REST, no GraphQL). It lists closed blockers too; to show only the open ones, `--jq '.[] | select(.state == "open") | .number'` (when the call succeeds, no output means none open). `gh issue view <n> --json blockedBy` needs GraphQL and a `gh` that has that field; it also lists closed blockers, so filter it: `--jq '[.blockedBy.nodes[] | select(.state == "OPEN")] | length'`. Startable only when no `Blocked by` issue is open and the native blockers are 0. These counts see only open or closed, so they treat every closed blocker as cleared. If the blocked ticket is built by a change (not a wayfinding ticket, label `wayfinder:<type>`), also check how each closed blocker, from either source, was closed, unless the blocker is itself a wayfinding ticket (cleared once closed). For a native blocker the listing above already gives `state_reason` and the labels; for a `Blocked by:` line blocker read them with `gh api repos/<owner>/<repo>/issues/<blocker> --jq '{state_reason, labels: [.labels[].name]}'`. A blocker with `state_reason` `not_planned` or `duplicate`, or the `wontfix` label, was closed without the work being done: do not start the dependent and tell the user. Any other closed blocker counts as cleared (the closed event's `commit_id` is often null even when a merged pull request closed the issue, so it cannot tell a merge from a hand close). If a read in this operation fails, or a count prints `null` or something that is not a number, stop and tell the user; do not read it as cleared.
- **Add a line to an issue body**: for a fallback line (`Blocked by:` or `Part of #<parent>`) on an issue that already exists. `gh issue edit --body` replaces the whole body, so never run it with only the new line. Read the current body (**Read an issue**); if the read fails or comes back empty, stop and tell the user, and do not write. Then put the new line where the rules say: a `Blocked by:` line first; a `Part of #<parent>` line second, after the `Blocked by:` line, or first when there is none. If the body already has a `Blocked by:` line, replace that line with one listing every blocker rather than adding a second. Write the WHOLE body back (the original text with the new line in place) with `gh issue edit <number> --body-file <file>`. Then read the body back and check that the rest of the original text (everything except a replaced `Blocked by:` line) is still there and the new line is in place; if not, tell the user, write the original body back once if you still have it (and say so), and do not report the ticket published (or the link made).
- **Comment on an issue**: `gh issue comment <number> --body "..."`
- **Apply / remove labels**: `gh issue edit <number> --add-label "..."` / `--remove-label "..."`
- **Close**: post the explanation with `gh issue comment <number> --body "..."`, then `gh issue close <number>`. REST: post the comment with `gh api --method POST repos/<owner>/<repo>/issues/<number>/comments -f body="..."` (or the session's GitHub tools), then `gh api --method PATCH repos/<owner>/<repo>/issues/<number> -f state=closed -f state_reason=completed` (`not_planned` for a wontfix close). On an already-closed issue, `gh issue close --comment` drops the comment and still exits 0.
- **Park**: mark an issue as parked, or read whether it is. To mark it, add the `parked` label (**Apply / remove labels**), then comment on the issue (**Comment on an issue**) with a link to the attempt history: its attempt records (the `review-record` shape) and the pull request, if there is one. To read it, an issue is parked when its labels (**Read an issue**) include `parked`. A parked issue waits on the user: no skill builds it, reviews it or merges its pull request until the user removes the label (**Apply / remove labels**), which lifts the park.

Infer the repo from `git remote -v`; `gh` does this automatically when run inside a clone.

File issues only into the user's own repo. Never file into the plugin's own repo (where these skills come from) unless the user owns it. In a fork, `gh` can default to the upstream parent, so before the first `gh issue create` of a session, check the target with `gh repo view --json nameWithOwner` (REST: a non-empty `gh api repos/<owner>/<repo> --jq .parent.full_name` means a fork) and confirm it with the user if it is not their repo.

## Pull requests as a triage surface

**PRs as a request surface: no.** _(Set to `yes` if this repo treats external PRs as feature requests; `/triage` reads this flag.)_

When set to `yes`, PRs run through the same labels and states as issues, using the `gh pr` equivalents:

- **Read a PR**: `gh pr view <number>`, then `gh pr view <number> --comments` (off a TTY, `--comments` prints only the comments, not the body), and `gh pr diff <number>` for the diff.
- **List external PRs for triage**: `gh api --paginate 'repos/{owner}/{repo}/pulls?state=open' --jq '.[] | select(.author_association | IN("OWNER","MEMBER","COLLABORATOR") | not) | {number, title, author: .user.login, author_association, labels: [.labels[].name]}'`.
- **Comment / label / close**: `gh pr comment`, `gh pr edit --add-label`/`--remove-label`, `gh pr close`.

GitHub shares one number space across issues and PRs, so a bare `#42` may be either: resolve with `gh pr view 42` and fall back to `gh issue view 42`.

## Wayfinding operations

Used by `/wayfinder`. The **map** is a single issue with **child** issues as tickets.

- **Map**: a single issue labelled `wayfinder:map`, holding the Notes / Decisions-so-far / Fog body. `gh issue create --label wayfinder:map`.
- **Child ticket**: an issue linked to the map as a GitHub sub-issue (see **Make an issue a sub-issue of a parent**). Where sub-issues aren't enabled, add the child to a task list in the map body and put `Part of #<map>` on the line after the child's `Blocked by:` line (the second line of the body), or as its first line when the child has no `Blocked by:` line (on a child that already exists, see **Add a line to an issue body**). Labels: `wayfinder:<type>` (`research`/`prototype`/`grilling`/`task`). Once claimed, the ticket is assigned to the driving dev.
- **Blocking**: see **Blocking** under Conventions.
- **Frontier query**: list the map's open children (`gh issue list --state open`, scoped to the map's sub-issues / task list), drop any with an open blocker (see **Count open blockers**, or an open issue in the `Blocked by` line, first or second line of the body) or an assignee; first in map order wins.
- **Claim**: `gh issue edit <n> --add-assignee @me`, the session's first write.
- **Resolve**: `gh issue comment <n> --body "<answer>"`, then `gh issue close <n>`, then append a context pointer (gist + link) to the map's Decisions-so-far.
