# `release` is version-free and command-free, and a Release is a step of a Milestone

The `release` skill knows no version policy and names no tracker command. It checks the current Release shipped, writes the changelog entry for everything merged since the last Release, runs the **cut steps** and whole-Release check the repo's release doc lists, closes the Release, runs `triage` (the Triage batch) and `retro-planning`, and plans the next Release from one **ranked list**, picked from the top up to the release doc's **Release size**. Every plan is a Milestone: a small Release is a Milestone with one Release. Settled with the user on 2026-11-03 in the planning thread "Plan splitting the release skill" (Spec #633, answering #617).

## Why

`release` had grown to 6,919 words, over the Boundary record's 5,000-word limit, and most of it was not Release work: two whole versioning policies (semver sizes, the bump pull request, label renames, version collisions between open Releases, the urgent patch Release), a separate "inside a Milestone" path whose detection rule was copied into `triage` and `retro-planning`, and 19 GitHub commands. Each repo versions differently or not at all, a repo with no version could not use `release`, and parsing `triage`'s and `retro-planning`'s records tied `release` to their layout.

## Decisions

- **Version-free.** A Release has a name (the release doc's name form; setup's default `Release <n>`), never a version. Each repo's versioning policy (none, pull requests bump, Releases bump) is written into its own release doc by `setup-dev-skills`, as cut steps the skill runs in order; a cut step wins over the skill's own text. A repo that bumps records the versions delivered in the changelog entry. No label renames, no version comparisons.
- **No urgent Release.** A fix that cannot wait is built and merged like any issue, and the next Release's changelog lists it. A release doc may give a step between Releases.
- **Command-free.** The skill says what to find or do; agents already know how to list, read and label issues. Rules with real meaning stay as rules, such as the shipped test (a merged pull request into the default branch closed the issue with a closing keyword; a close by hand or "does not close #n" does not count). The tracker doc is to keep only the traps an agent would not know; the tracker docs keep their commands until a later change slims them.
- **A Release is a step of a Milestone.** Planning always involves the user (the Milestone's goal and features, with `milestone`); everything after it is agentic. There is no separate "inside a Milestone" path. A small Release is a one-Release Milestone, which `milestone` plans with defaults for what it does not need (one at a time, nothing excluded); `team-lead` has one path. A Milestone issue holds no boundaries of its own: they are the Boundary record's ([ADR 0004](0004-build-threads-coordinate-and-subagents-code.md)). A feature the user plans while a Milestone runs joins it unless the user says it is for the next Milestone; the planning thread lists it, then updates the open Tickets it touches, and a change to the goal, acceptance or exclusions goes to the user as one question.
- **One shared mark.** `next-release`, a role in the triage label doc, is set by `triage` and `retro-planning` and read and cleared by `release`, so no skill parses another skill's records (amended 2026-11-14, Ticket #160: only `triage` sets it now).
- **One ranked list.** Group 1: severe issues and issues marked `next-release`. Group 2: the Milestone's features, re-ordered at every planning (dependencies first, then what moves the goal furthest, the original order breaking ties), each preceded by its open blockers. Group 3: `ready-for-agent` bugs, oldest first. An issue meeting several conditions goes in its highest group, first within it. A feature the Milestone issue does not list is never ranked. (Amended 2026-11-04, Ticket #686, absorbing #685: an issue the last Release carried over goes where its kind puts it, an unplanned feature proposed, one no agent can take left out with the reason "carried over, an agent cannot take it", any other `ready-for-agent` one first in group 3, because a carried-over issue of no group was ranked as a bug or dropped with no reason; and a carried-over issue stays accounted for in its Release's Order, so a rerun cuts that Release, even one whose every issue was carried over, instead of planning it again. Carry-over is gone: see the amendment note of Ticket #174 below.)
- **A backlog sweep at every Release end**, in `triage`'s Triage batch, over every open `ready-for-agent` issue, so the ranked list ranks a true backlog: duplicates close (linking the kept issue), what main's current code made obsolete closes as completed with where on main (amended 2026-11-04, Ticket #680: a close as not planned read as work not done, so a planned feature it blocked was left out for good), and an issue left out of 3 Releases in a row (read from the "Left out" lists of the last 3 release issues) closes as not planned with "reopen to bring it back". An enhancement an agent found (an audit, investigation or retro finding) waits for the user at `ready-for-human`: agents never rank, close or expire it. `triage` has no separate "inside a Milestone" test either: run by the user it asks per issue, run at a Release end it is the batch.
- **Planning checks every open issue against main** (amended 2026-11-04, Ticket #670): before ranking, every open issue that carries no release label, is not parked and is not left to a later Milestone is read against freshly fetched main, merges since it was written included, and given a verdict (still valid, already fixed, changed scope, obsolete, cannot tell) recorded in the release issue, an already fixed or obsolete one closing as completed (Ticket #680); the sweep's Obsolete test is the one definition, and only what survives is ranked. The sweep alone saw only `ready-for-agent` issues, at the previous Release's end.
- **Release size.** Items of any kind (a Spec with its Tickets is 1, a lone Ticket 1, a bug 1), set per repo (setup's default 5, this repo 10). A severe issue joins past it. The release issue records the order with a reason per entry, the size used, and what was left out and why.

## Considered options

- **Split `release` into a main file and mode references** (#617's first proposal). It kept two version policies in the plugin and the separate Milestone path, and only moved the words.
- **Keep the 5-feature cap and maintenance fixes outside it.** Bugs outside the Milestone's features never shipped until planned, and "touches a feature" fitted almost every fix (Retro #461).

## Consequences

- `release/SKILL.md` is back under 5,000 words and off `known_over` in `scripts/check-plugin.sh`.
- ADR 0008's version rule for this repo stood when this ADR was written; its "How a Release works" is amended by this ADR. This repo's version hand-out and Ticket re-read stayed in `CLAUDE.md` and `docs/dev-skills/release.md`.
- Existing repos rerun `setup-dev-skills` to gain the release doc's new fields (versioning policy, Release size, cut steps) and the `next-release` label.

*Amendment note, 2026-11-14, Ticket #150.* [ADR 0016](0016-releases-bump-the-plugin-version-once.md) replaced ADR 0008's version rule: this repo's versioning policy is now Releases bump, and its cut steps raise the version once in the changelog pull request and name the one new version on the `Versions:` line. The version hand-out and the Ticket re-read are gone. The decisions above (a version-free, command-free `release` that runs the cut steps the repo's release doc lists) are unchanged.

*Amendment note, 2026-11-14, Ticket #158.* The Triage batch lives in its own file, `plugins/dev-skills/skills/triage/TRIAGE-BATCH.md`, which the Release thread reads at a Release end; `triage`'s main file holds only what a session triaging with the user does, and one sentence pointing to the batch. The batch's rules moved as they were, except that "handled at once" (a severe issue or a blocker triaged outside the batch) and the dry-run mode left: an issue seen during a Release waits for the next batch, or the user triages it. The rule for when to set `next-release` moved into the batch file beside the sweep's "Needs the mark" test; run with the user, `triage` sets the mark only when the user asks. The decisions above are unchanged.

*Amendment note, 2026-11-14, Ticket #160.* The end-of-Release pass runs `retro-planning` first and the Triage batch second, and its record comment for Retro planning links that run's record. Retro planning sets no `next-release` mark and files no Ticket: it hands a repeated or severe Retro issue to triage with `needs-triage`, and the batch briefs it (ADR 0007's amendment). The planning's check against main and ranked list take a `retro` issue at `ready-for-agent` like a `ready-for-agent` bug (group 3); other `retro` issues and the `retro-planning` records are still left alone.

*Amendment note, 2026-11-14, Ticket #167.* A feature planned while a Milestone runs no longer joins it: the features are fixed once planning settles, and a feature planned later waits for the next Milestone's planning ([ADR 0017](0017-milestone-features-are-planned-in-their-own-sessions-and-fixed-once-planning-settles.md)). The other decisions above are unchanged.

*Amendment note, 2026-11-14, Ticket #174 (Spec #173).* The cut changes, and carry-over is gone from `release` for good. A cut asks the user nothing unless an open issue of the Release is neither parked nor waits with a parked issue, and no issue is carried over: the `## Carried over` section, the choice to wait or carry over and the carried-over candidates are removed, and so are the "accounted for" rule of "Find where you are" and the reading of a release issue that has a `## Scope` list and no `## Order`. An issue closed as completed that fails the shipped test was closed by hand: the Release thread checks it against main itself, as the check against main reads any issue; with the work on main it counts as shipped and the release issue notes the evidence, without it the issue is reopened and is then an open issue. A parked issue, and an issue that **waits with** it (open, labelled, with at least one open blocker, each of which is parked, already listed under `## Left the Release`, or itself waiting with a parked issue; a Spec and its open Tickets go together, so when one of them is parked or waits with a parked issue through its blockers, the others wait with it, once no worker builds the Spec), leaves the Release at the cut: it loses the release label, with one line under `## Left the Release` in the release issue naming it and why, and is changed in no other way. Any other open issue with the label stops the cut and the user is told which. A release issue written by the earlier planning (an Order without `After:` lines) is cut by the same steps. The user's words, 2026-11-12, on a stuck issue: "if moving out that ticket doesn't really affect other features of milestone from running ... you could continue to run and move that to the end of milestone". The decisions above are otherwise unchanged; how the next Release is planned changed with Ticket #175 (below).

*Amendment note, 2026-11-14, Ticket #175 (Spec #173).* Planning follows the Milestone's graph, and the one ranked list is gone: no group ranking, no re-ordering of the planned features, no proposal of unplanned features and no dry run. Planning takes the **slice**: the open, unlabelled, unparked features of the Milestone issue's table, in its order, never re-ordered, up to the Release size. A feature whose blocker is parked, waits with a parked issue or cannot be taken by an agent is left out naming that blocker, with every feature that depends on it; an unparked setup Ticket for the person (at `ready-for-human`, published by planning for a live step) leaves no feature out, and is named on its `After:` line. The **bug dependency pass** decides, for each waiting issue (severe, marked `next-release`, or any other issue at `ready-for-agent`: a bug, a chore, a handed-over `retro` issue with its brief, whatever its category label), whether it blocks a feature of the slice; one that does gets the blocker link recorded and goes just before that feature. The other waiting issues follow the features: severe, then `next-release`, then the rest, oldest first within each; a severe issue still joins past the size. Each Order entry ends with `After: #<n>, ...` or `After: none`, its open blockers when planned (a Spec's include those of its Tickets that lie outside it); the tracker's blocker links stay the record. An unplanned feature waits for the next Milestone's planning, and the `## Proposed to the user` section leaves the release issue. The check against main now covers only the features and waiting issues the planning is about to take, with the same four verdicts. "When nothing qualifies" opens no release issue, writes nothing and tells the user why; "Rerun first" finishes the labelling of an open release issue whose Order has entries, plans into one whose Order is empty, and opens no second issue; the path for release labels with no release issue left with it. The user's words, 2026-11-11: "I think it should take the next slice of the graph ... we should have some part to determine if any of the bugs would like block our like the features we're gonna take in the next slice". `team-lead` reads the new Order with the start rule that Ticket #176 brought ([ADR 0010](0010-delivery-is-split-into-planning-a-team-lead-and-harness-references.md)'s note): every open, unparked entry with no open blocker gets a build worker. The other decisions above are unchanged.
