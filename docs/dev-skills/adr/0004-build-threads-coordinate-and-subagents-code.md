# Build threads coordinate; subagents write the code

Every piece of work starts as a GitHub issue: a spec is one issue, its tickets are sub-issues of it, and a milestone groups the specs and tickets for one goal. The project coordinator hands each one to its own thread: a **spec** goes to a **spec thread**, which runs `implement-spec`, and a **lone ticket** (a ticket under no spec, such as a bug fix, a chore or CI/CD work) goes to a **ticket thread**, which runs `implement`. A build thread never writes code itself, not even to resolve a merge conflict. It starts **Implementer** subagents to build test-first and to fix, runs the review of [ADR 0003](0003-code-review-runs-find-verify-rank-in-rounds.md) with fresh reviewer subagents, talks to the user, and merges. We chose this because it keeps the thread's own context small enough to stay sharp for coordinating, and because each piece of work gets its own thread that the user can watch and steer.

## How a build thread works

- **Model tier.** `to-tickets` marks each ticket regular or premium (premium for heavy or tricky work), and its Implementer runs on that tier. A lone ticket runs on the regular tier unless its issue says premium. Spec-PR fixes that touch no ticket's files also run on the regular tier. Trivial jobs, such as running a test suite, go to cheap subagents.
- **Fixes.** The Implementer that built a ticket also fixes its review Findings, because it already knows the code, or disputes one with evidence for the next Verifier to decide; design Findings are answered first, by a premium-tier agent within what the spec agreed, and the Implementer commits only the answers that change the pull request ([ADR 0003](0003-code-review-runs-find-verify-rank-in-rounds.md)). Findings on a spec's pull request, which can span tickets whose Implementers have finished, go to a new Implementer working on the spec branch, on the highest tier of the tickets the Finding touches. Merge conflicts go to an Implementer the same way. Reviewers stay fresh every Round.
- **Evidence.** Before a lone ticket's pull request opens, or before a spec's ticket is squash-merged, the Implementer shows that the work works: test output, the typecheck, and screenshots for anything visual. The thread checks it, and it goes into the pull request's Evidence section (the `pr` skill); a spec's pull request sums up each ticket's evidence there. Before reporting, the Implementer also checks its own diff against the repo's review rules file's Always-check lines, and walks the sequences of any new rule that runs over Rounds or steps before Round 1, so the reviewer's first Rounds do not find what it could (amended 2026-11-03, Ticket #586, absorbing #477 and #482). When a criterion names a run that needs tools the Implementer does not hold, `to-tickets` marks it, the brief says the thread produces that evidence, the Implementer drafts the entry with pending markers and reports the criterion as owed, and the thread makes the run, hands the observed output back to the Implementer to record in place of the markers, makes it again after a fix, and lets nothing land or open with a marker left (amended 2026-11-03, Ticket #587, absorbing #470).
- **Inside a spec thread.** Each ticket gets its tests and a **ticket check** before it joins the spec branch, so problems surface while the ticket is fresh. A ticket check is one Quick Round over the ticket branch's diff against the spec branch, recorded as a comment on the spec's pull request (posted once the draft opens), so `retro` sees it. The Implementer fixes or disputes each open Important and "fix" Nit, and the ticket lands; the spec pull request's Round 1 carries the check's open Findings and decides them, so they are never raised twice. Pre-existing Findings wait and are filed once, after the spec pull request's last Round. The full Rounds then run once over the spec's pull request (amended 2026-11-03, Spec #555: a ticket check no longer runs up to 3 times, and a ticket is no longer parked for a check that would not settle).
- **Check against main first** (amended 2026-11-04, Ticket #671). Before a build thread makes anything, on every entry, it reads its issue (a Spec with its unlanded Tickets, or a Worker's one Ticket) against freshly fetched main, with the verdicts of `release`'s check against main (ADR 0012), its own branches and pull request not counting. Only still valid builds. An already fixed or obsolete issue gets no code: the thread reports the evidence on main and stops, and the coordinator, not the thread, closes it as completed naming where on main, or re-plans it, because closing a planned feature or changing the Milestone's agreement is the coordinator's call or the user's. Changed scope and cannot tell wait for the coordinator's answer, which settles the check on re-entry. A merge during a Release can fix or change an issue after it was planned in, and the planning's check cannot see that.
- **Parallel work.** Up to 3 build threads run at once, so usage stays predictable and pull requests don't pile up conflicts. Implementer subagents inside a thread don't count toward this; a spec thread runs at most 3 Implementers at once.

## When the user must review

The thread merges its own pull request once the review is clean and CI is green, unless it must bring it to the user. One rule decides it, inside a Milestone or not (amended 2026-11-03, Spec #572; before that, 2026-11-01, Spec #398, from [#385](https://github.com/Luffytse/luffy-dev-skills/issues/385#issuecomment-6556848716): Deep is a review level, not an approval, and [boundaries are per repo](https://github.com/Luffytse/luffy-dev-skills/issues/385#issuecomment-6564185667)).

**Membership plays no part in the merge** (amended 2026-11-04, Spec #633). A pull request is inside a Milestone when its issue (for a spec's pull request, the spec) carries the Milestone's membership label, in the form the repo's **Boundary record** (`docs/dev-skills/boundaries.md`, written by `setup-dev-skills`) names; the Milestone issue carries the same label. Delivery and Release planning read membership; the merge does not, because a Milestone issue holds no boundaries of its own: the Boundary record applies as written to every pull request. With no Boundary record the thread reads an empty one: no irreversible action is allowed to agents and no action needs the user's approval, so only a one-way door (and what the repo's own rules reserve) goes to the user. `to-tickets` copies the Spec's membership label to each Ticket it splits from it and publishes a Milestone Spec's breakdown without asking the user when the Tickets keep the Spec's scope (amended 2026-11-02, Ticket #458). A retro's check pull request, which has no issue of its own, records `Retro origin: <Ticket or Spec issue link>` in its body; its body is its spec for design answers, and its merge follows the same rule (amended 2026-11-02, #476; 2026-11-03, Spec #555, which moved the membership read out of the review).

*Amendment note, 2026-11-04, Spec #633.* From 2026-11-01 to 2026-11-04 a Milestone issue could name allowed or forbidden actions of its own, which won over the record for its issues, and the merge read the issue's membership (or a corrective check's `Retro origin` issue's labels) to know whether they applied. Every plan is now a Milestone and boundaries are the repo's only, so a Milestone issue never restates or contradicts the record.

The thread brings the pull request to the user, and does not merge it, only if:

- it crosses a boundary: it takes, or its merge would take, an action the Boundary record says needs the user's approval, or goes past a limit or budget the record sets; or it is a **one-way door** and the record does not allow agents to take each of its irreversible actions. A one-way door is a change that reverting would not undo (a data migration, deleted data, a public interface others depend on, a message sent outside the project); each Implementer says so with its evidence, the `pr` skill marks it on the pull request, and a spec's pull request is a one-way door if any of its tickets is;
- the repo's own rules (its `CLAUDE.md`, the project instructions, its docs) say a person merges it.

A review never stops for a reason the Boundary record does not list (amended 2026-11-03, Spec #555): after Round 3 its open Importants become bug Tickets or are dismissed and the pull request merges, and it waits on the user only when a fix, a design answer, a bug Ticket or the merge would cross a boundary, which the first case above covers. The restart and park of a stuck pull request or ticket (2026-11-02, Spec #400, #448, #481) went with the attempts ([ADR 0003](0003-code-review-runs-find-verify-rank-in-rounds.md)). A Deep review alone, and a change to an ADR, the glossary, a `CLAUDE.md`, an `AGENTS.md` or a `REVIEW.md`, are agent merges. The thread lists each such file it merged, with each design answer an agent gave on the pull request, on one pull request body line (`Agent-merged rules: <files>; design answers: <id> <link>, ...`) and in its report, so the user can read them after the fact; the Milestone report reads the same line.

*Amendment note, 2026-11-03, Spec #572.* Until then the rule had two lists: inside a Milestone only a boundary crossing or a repo rule sent the pull request to the user, while outside one it also went to the user whenever its review ran at Deep, it was a one-way door whatever the record said, or it changed an ADR, the glossary, a `CLAUDE.md` or a `REVIEW.md`, and the rules-file merges inside a Milestone were listed on a `Milestone review:` line. The user, planning #572: "I don't think that there's a difference between a milestone and non-milestone. My end goal is definitely remove all the gate. Okay, so even outside the milestone, it should be the same." The outside list is gone, a project with no Boundary record reads an empty one, and the listing line has a name that does not depend on membership. Planning approvals outside a Milestone (the next Release's scope, triage per issue, a to-tickets breakdown) are not merge gates and stay with the user.

A repo's own rules may add cases; the skills name only the general ones.

Where each pull request bumps the version (a project's own choice; [ADR 0008](0008-each-skill-change-bumps-the-plugin-version.md), superseded for this repo by [ADR 0016](0016-releases-bump-the-plugin-version-once.md)), the bump merged with it is not a published release, and it does not make the pull request a one-way door on its own: a bad change is walked back by a revert. A Release that publishes a version, where Releases bump, is the same: in this repo a merged version bump is no one-way door (ADR 0016).

A thread that brings a pull request to the user names what stops the merge (the boundary and where it is listed, or the rule and its file), so the user can decide quickly. The user then merges, or tells the thread to. This follows the Claude Code team's practice of setting human review by the risk of the change, not by who wrote it.

## Considered options

- **Upstream's `implement` as-is:** the session builds and commits to the current branch itself, with no pull request. Its context fills with code, and nothing reaches the user for review.
- **Dropping `implement-spec`** in favour of one thread per ticket: the user preferred one thread per spec, with subagents doing the tickets and one review over the whole spec.
- **Always asking the user to merge:** safe, but the user becomes the bottleneck on low-risk work.
- **Bringing a stuck review to the user as a merge decision:** a pull request the review could not settle lands on the user as a merge to judge without a clean review behind it. From 2026-11-02 (#400) a stuck review restarted once from main and then parked; from 2026-11-03 (Spec #555) the 3-Round cap and the after-Round-3 sort into bug Tickets bound it instead, with no restart or park.
- **Keeping a Deep review and ADR, glossary, `CLAUDE.md` and `REVIEW.md` changes as user merges:** most such merges need no decision from the user, who reads them on the `Agent-merged rules:` line (at the Milestone review, inside a Milestone) instead; Deep adds scrutiny, not a wait (2026-11-01, #385, inside a Milestone; everywhere from 2026-11-03, Spec #572).
- **A second merge list outside a Milestone:** it kept user merges for Deep, one-way doors the record allows and rules files, whatever the Boundary record said; the user chose one rule and, in the end, no gate (Spec #572).

## Consequences

- The `merging` Base skill, which `implement`, `implement-spec` and `release` load at their merge step, reads the Boundary record (empty when there is none) and applies the one rule, whatever the issue's labels (amended 2026-11-04, Spec #633; the rule moved into `merging` by Spec #641, ADR 0009); every agent merge of an ADR, glossary, `CLAUDE.md`, `AGENTS.md` or `REVIEW.md` change is listed on the `Agent-merged rules:` line (#423, renamed by Spec #572), and so are the design answers an agent gave on a merged pull request (ADR 0003); the Milestone report reads that line.
- `implement` and `implement-spec` are rewritten as coordinator skills. `to-tickets` adds a model tier to each ticket, `pr` gains an Evidence section and a one-way-door marker, and `to-tickets` and `wayfinder` end by offering `setup-project`.
- A new skill, `setup-project`, writes the project instructions that tell the coordinator how to brief build threads (which skill, model tier, repo, review level). It runs `grilling` inside, so it asks at most 3 questions at a time. The user runs it by hand, and `wayfinder` and `to-tickets` offer it to the user at their end only when planning added a repo, a kind of thread or a standing rule. The instructions say how threads work and carry the user's tier-to-model map; they never hold the state of the work, and tell the coordinator to find open specs, plannings and tickets on the tracker. Once the user approves the text, the thread sends it to the coordinator, which saves it.

*Amendment note, 2026-11-14, Milestone 4 (#170).* `to-tickets` and `wayfinder` no longer end by offering `setup-project` (the offer named in the two Consequences lines above). The user asks for `setup-project` when a new repo, kind of thread or standing rule calls for it.
