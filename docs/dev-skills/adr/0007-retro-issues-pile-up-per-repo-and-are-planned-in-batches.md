# Retro issues pile up per repo and are planned in batches

`retro` used to hand its suggestions to the person in its report, where most were read once and lost. Now every suggestion except a repeated Bug class becomes a **Retro issue** on a GitHub tracker, and the open ones form that repo's **Retro backlog**. A **Retro planning** session, run by the new `retro-planning` skill, works through one repo's backlog in a batch: it merges duplicates, closes what was seen only once, and turns at most 3 groups into Tickets (replaced 2026-11-14 by one unattended sort that hands repeated problems to triage; see the amendment at the end). We chose this because one thread's retro sees one session, so it cannot tell a one-off from a pattern; only a backlog that collects "seen again" votes across threads can. `dev-skills` is loaded by several projects, so no skill text names one project or repo, and a Retro issue goes to the repo where its fix lands.

## Filing (what `retro` does)

- A repeated Bug class from `agentic-review` becomes a Retro issue that proposes the check or the `REVIEW.md` line, like every other suggestion (amended 2026-11-14, Spec #157: a retro only files; it adds no check or `REVIEW.md` line and opens no branch or pull request, so a rule is added only after Retro planning hands the issue on). Every suggestion becomes a Retro issue: label `retro`, title starting `Retro:`, and **no** `needs-triage`, so build threads ignore it and `triage` skips it (see Consequences). Its body names the source thread, what went wrong, and the suggested fix. `retro` creates the `retro` label if the repo lacks it.
- **Routing follows where the fix lands, named by the Retro's Scope (added by #32).** Each Retro carries a Scope line: `skill` and `environment` (a limit of the agent or Harness) go to the `dev-skills` repo, `this repo` to that project's own tracker. A problem with a skill or the workflow (skill text, review rules, how threads run) goes to the `dev-skills` repo, from any project. A problem only one project has (its CI, its docs, its `CLAUDE.md`) goes to that project's repo. No suggestion goes to both. A project that wants a skill of its own builds it in its own repo or `CLAUDE.md`; it may still suggest a `dev-skills` change, which `dev-skills`' Retro planning hands to triage or closes, with a reason.
- `retro` finds the `dev-skills` repo from the `repository` field of the plugin's manifest (`plugins/dev-skills/.claude-plugin/plugin.json`), and the project's tracker from its `docs/dev-skills/issue-tracker.md`. When the thread cannot write to the `dev-skills` repo, `retro` puts the issue text in its report so the coordinator can file it.
- **Votes.** When a Retro issue, open or closed, already covers a suggestion, `retro` comments "seen again in <thread>" on it instead of opening a duplicate, and reopens it if it was closed (amended 2026-11-14, Spec #157, so a closed one-off keeps its count).
- **No due notice.** `retro` does not count the backlog or say Retro planning is due (changed by #570): the Release thread runs Retro planning at every Release end, and the user can start one by asking.
- `implement` and `implement-spec` run `retro` on their own thread as their last step, once the pull request is merged and its issue is closed; a thread that handed its pull request to the person waits, and runs `retro` after the person merges it, or asks whether to run it if the person drops or closes the pull request unmerged, or the thread never opened one. Planning threads keep their project's rule instead.

## Retro planning (what `retro-planning` did until 2026-11-14)

This section and the two paragraphs after it are history: the amendment at the end replaced them. It runs per repo and reads only that repo's Retro issues; the `dev-skills` repo is planned in the project that builds it.

1. **Snapshot and open record.** At its start the planning files its record, an **open** issue titled `Retro planning <yyyy-mm-dd>`, label `retro-planning`, and reads every open Retro issue with its "seen again" votes and its age as of the record's creation. That snapshot is all it plans. Anything filed or voted on later waits for the next planning and is listed under "Arrived during this planning"; other threads keep running and nothing is held. A late vote is not lost: it counts as a new vote next time.
2. Group them by Scope, then by root cause, and merge duplicates.
3. Propose a verdict per group. Seen in only one thread: close as `wontfix` with a reason, unless it is severe (lost data, security, a large waste) or its fix is a cheap deterministic check of the project's own tooling (a CI step, a checker rule, a test) that a **necessity check** confirms (amended by #629, see below). Seen in 2 or more threads: act on it.
4. Act on at most 3 groups. Each becomes a `ready-for-agent` Ticket with a done condition, linking the Retro issues it absorbs; those issues close when the Ticket closes as completed, and return to the backlog with their votes if it closes as not planned (or is abandoned). Prefer a check or hook over a new prose rule. A repeated group over the cap stays open and comes next at the next planning, after any group from step 8. Only the person may raise the cap, and only for that planning; the record notes the cap used and the reason.
5. **One item at a time.** The planning walks the person through the groups in order, the `wontfix` ones included, each with full details: how the workflow works today, the incident in each thread, the Scope and shared root cause, the vote count, the proposed verdict and reason, and whether to address the problem if it acts. It then invokes the complete `to-tickets` workflow to investigate, draft and obtain approval of the concrete solution before publication. Before the `to-tickets` workflow shows its proposed Ticket, each time it is shown and on resume too, the default branch is fetched and the current state of every issue, pull request and path its draft names is re-read and the draft corrected (votes stay as of the snapshot), because the walk can run for hours while the repo moves. A problem approval alone does not approve that solution. Several required Tickets return before publication for a spin-off decision. The planning carries out each call at once, then reconciles returned identifiers, source mappings and incomplete actions into the record before showing another group. Real Tickets count toward the cap even after partial failure; resume repairs their publication without duplicating them or discarding a declined solution. Closing or spinning off a proposed Ticket frees its slot for the next acting group; once the cap is full, each later acting group is shown, still one at a time, as held back. The mechanical closes (expiries, and issues whose Ticket closed as completed) come in one short list at the end.
6. An issue with no new vote across 2 plannings is closed with "reopen if seen again", unless it was held back only by the cap or is spun off.
7. **Spin-off.** A group the person wants to discuss further is not decided in this planning. It gets a separate planning thread (asked of the coordinator in a project, otherwise of the person), and each of its issues a comment naming that thread. A spun-off group does not count toward the cap, stays open and cannot expire. The owning thread ends by giving each issue a verdict: absorbed by a Ticket it files, or closed with a reason. It files no record of its own and leaves the spinning planning's record body alone; it comments each Ticket it files on that record, and later plannings read those comments with the record and recheck those fixes like any other. Until then, later plannings list those issues as "spun off, waiting" and skip them, as they skip issues waiting on an open Ticket.
8. Recheck whether the problem behind an earlier fix has come back. If it has, the fix did not work, and that group goes first.
9. The record lists the snapshot, the cap, every verdict and vote count, what was spun off and what arrived during the planning. The planning closes it at the end. A planning that pauses leaves it open and is resumed from it: the resumed run keeps the snapshot, first brings the record up to date with what was already done on the issues (closes, Tickets, spin-offs), redoes the grouping for the issues still without a verdict, and walks on from there. The next planning reads only closed records.

**One sighting is enough for a confirmed check** (#629, absorbing #616). The vote rule suits a skill-text problem, which the next review catches again; a missing CI step or checker test is not seen again until it bites, and #507 and #566 were closed as `wontfix` for that reason. So a one-thread group whose fix is a cheap deterministic check acts at its first sighting, counted toward the cap, after a fresh premium-tier subagent confirms the check would have failed on the real past mistake the issue describes and that nothing already catches it. The planning record shows the necessity check's verdict for the group (in the Verdicts row). A check that is not confirmed takes the one-thread `wontfix`; a prose rule or a judgement call is never checked, so it still does. A group held back by the cap is checked again at the next planning. A group seen in two threads acts on the vote alone. At a Release end the group is decided by agents like any other. The rule fits every project, so it lives in the skill, not in a repo's own docs.

The limits (at most 3 groups, 2 plannings) are the user's choices, not taken from a source. At a Release end (ADR 0004, ADR 0008) the 3-group cap and the walk with the person do not apply: agents decide every group at Release end (see `retro-planning`).

## Considered options

- **Keep suggestions in the report only.** Nothing tracks them, and no thread can see that two others hit the same problem.
- **File them as `needs-triage` issues.** `triage` and build threads would pick them up one at a time and act on one-offs; Retro issues need batch judgement across threads, which is what Retro planning is for.
- **Show one list of every verdict and approve it at once.** The first planning did this, and the person found every group, verdict and Ticket draft too much to judge together; one item at a time, acting on each call, keeps each judgement small, and the open record lets a long planning pause and resume.
- **Act on every one-sighting check without confirming it.** Every proposal would become a check and crowd out the cap; the necessity check keeps only the checks that would have caught a real mistake and that nothing else catches.
- **Act on every repeated suggestion.** A planning that turns many groups into Tickets crowds out feature work; a limit of 3 keeps the fixes small and makes each planning choose.
- **One shared backlog for every project.** Routing by where the fix lands keeps each repo's backlog about things that repo can change, and keeps `dev-skills` free of any one project's problems.

## Consequences

- `retro` gains filing, routing, votes (Patches; its trigger was removed by #570). `plugin.json` gains a `repository` field.
- A new skill of our own, `retro-planning`, lives under `plugins/dev-skills/skills/`, and `ask-matt` routes to it (a Patch).
- `triage` must skip issues labelled `retro`, since they carry no `needs-triage` and would otherwise look untriaged (a Patch). Since the amendment it skips only a `retro` issue that carries no state role, and triages one Retro planning handed over.
- `implement` and `implement-spec` end with `retro` (Patches).
- This repo gets a CI job running `scripts/check-plugin.sh` and `claude plugin validate .` on every pull request.

## Amendment 2026-11-14: one unattended sort, and repeated problems go through triage (Spec #157, Ticket #160)

The user wants a Milestone delivered by agents from planning to the end, with a person asked only for what the Boundary record requires. The planning above did not fit that: the walk with the person ran in none of the 12 records written outside the private archive (all 12 ran at a Release end), no spin-off or expiry was ever carried out, no earlier fix came back, and the necessity check ran 3 times. A one-off closed as `wontfix` lost its count when it came back: #43 closed on 2026-11-08 and the same kind returned as the new #106.

**The loop now.** `retro` only files, and reopens a closed match it sees again. At each Release end the Release thread runs Retro planning first and the Triage batch second; a Retro planning asked for at any other time runs the same way. It asks nobody and waits for nothing:

- It reads the open Retro issues, groups them by Scope and then root cause, merges duplicates into one kept issue per group, and counts the distinct threads that saw each group.
- A group seen in one thread and not severe closes as not planned with its reason, saying a new sighting reopens it.
- A group seen in two or more threads, a severe one, or one holding an issue reopened after its fix merged is **handed to triage**: the kept issue gets `needs-triage` and keeps `retro`. Retro planning writes no brief, files no Ticket and sets no `next-release`.
- It leaves alone a Retro issue that already carries a state role, and one whose latest `Absorbed by` comment names an open Ticket: that one closes with its Ticket.
- It still refiles a Retro whose Scope belongs in another tracker, and writes one record per run, closed at its end and linked from the release issue.

The Triage batch triages a handed-over Retro issue like any other issue, and the issue is the Ticket. Agents build its fix (`ready-for-agent` with a brief); a fix that needs a Spec waits at `ready-for-human` for the user's next Milestone planning; one that crosses the Boundary record or changes the Milestone's agreement goes to the user. `release` ranks a `retro` issue at `ready-for-agent` like a bug. A proposed check or `REVIEW.md` line is therefore added only after it is needed twice, or is severe, which settles #2.

**What left:** the walk with the person, the cap of 3 and "held back by the cap", spin-offs, expiry and its "plannings without a new vote" counts, the recheck of earlier fixes (the reopen replaces it), the necessity check, the `to-tickets` hand-over and its resume rules, the absorption records it wrote, "Goes to the user" and "Proposed to the user", the `next-release` marking, the dry run and the premium-tier line. The "one sighting is enough for a confirmed check" rule and the limits of 3 groups and 2 plannings above went with them. Records written before the amendment stay as they are and are not read.

**This repo's own rule.** In this repo one thing waits: a handed-over Retro whose fix changes what a skill tells agents to do stays at `ready-for-human` for the user's next Milestone planning, and only a broken skill (one that does not do what its own text, this repo's docs or a recorded decision say) is repaired by agents. The rule is in this repo's `CLAUDE.md`, not in a skill, because only the plugin's own repo receives `skill` Retros from every project, and much of what the 2026-11 skill walk removed had come in one sentence per Retro; the user's code projects build no skills and get the plain behaviour, agents fixing what repeated. The Triage batch needs no hook for it: a thread running it here has `CLAUDE.md` in front of it, and a repo's own rules win over the general rule.
