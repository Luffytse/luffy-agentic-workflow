# Build threads coordinate; subagents write the code

Every piece of work starts as a GitHub issue: a spec is one issue, its tickets are sub-issues of it, and a milestone groups the specs and tickets for one goal. The project coordinator hands each one to its own thread: a **spec** goes to a **spec thread**, which runs `implement-spec`, and a **lone ticket** (a ticket under no spec, such as a bug fix, a chore or CI/CD work) goes to a **ticket thread**, which runs `implement`. A build thread never writes code itself, not even to resolve a merge conflict. It starts **Implementer** subagents to build test-first and to fix, runs the review Rounds of [ADR 0003](0003-code-review-runs-find-verify-rank-in-rounds.md) with fresh reviewer subagents, talks to the user, and merges. We chose this because it keeps the thread's own context small enough to stay sharp for coordinating, and because each piece of work gets its own thread that the user can watch and steer.

## How a build thread works

- **Model tier.** `to-tickets` marks each ticket regular or premium (premium for heavy or tricky work), and its Implementer runs on that tier. A lone ticket runs on the regular tier unless its issue says premium. Spec-PR fixes that touch no ticket's files also run on the regular tier. Trivial jobs, such as running a test suite, go to cheap subagents.
- **Fixes.** The Implementer that built a ticket also fixes its review Findings, because it already knows the code; on a change that changes design, design Findings are answered first, by the user or, inside a Milestone, by a premium-tier agent when the answer keeps what the user agreed, and the Implementer commits only the agreed answers ([agentic-review's ROUNDS.md](../../plugins/dev-skills/skills/agentic-review/ROUNDS.md#design-findings), [ADR 0003](0003-code-review-runs-find-verify-rank-in-rounds.md)). Findings on a spec's pull request, which can span tickets whose Implementers have finished, go to a new Implementer working on the spec branch, on the highest tier of the tickets the Finding touches. Merge conflicts go to an Implementer the same way. Reviewers stay fresh every Round.
- **Evidence.** Before a lone ticket's pull request opens, or before a spec's ticket is squash-merged, the Implementer shows that the work works: test output, the typecheck, and screenshots for anything visual. The thread checks it, and it goes into the pull request's Evidence section (the `pr` skill); a spec's pull request sums up each ticket's evidence there.
- **Inside a spec thread.** Each ticket gets its tests and a **ticket check** before it joins the spec branch, so problems surface while the ticket is fresh. A ticket check is one Review at Quick depth over the ticket branch's diff against the spec branch. It is not a Round: the Implementer fixes (design Findings on a ticket that changes design are answered first, as above) and the check runs again, with fresh reviewers, until no Important is open, at most 3 times; after a third check that still has an Important open, the thread brings the ticket to the user, or inside a Milestone parks it (below). The Implementer also fixes "fix" Nits; "skip" Nits are dropped. Pre-existing Findings wait and are filed once, after the spec pull request's last Round. The spec pull request's Rounds treat ticket-check Findings as already raised, so they are never repeated. Each check's Findings are recorded as a comment on the spec's pull request (the first ticket's once the draft opens), so `retro` sees them. The full Rounds then run once over the spec's pull request.
- **Parallel work.** Up to 3 build threads run at once, so usage stays predictable and pull requests don't pile up conflicts. Implementer subagents inside a thread don't count toward this; a spec thread runs at most 3 Implementers at once.

## When the user must review

The thread merges its own pull request once the review is clean and CI is green, unless it must bring it to the user. Which cases send it to the user depends on whether the pull request is inside a Milestone (amended 2026-11-01, Spec #398, from [#385](https://github.com/Luffytse/luffy-dev-skills/issues/385#issuecomment-6556848716): Deep is a review depth, not an approval, and [boundaries are per repo](https://github.com/Luffytse/luffy-dev-skills/issues/385#issuecomment-6564185667)).

**Membership.** A pull request is inside a Milestone when its issue (for a spec's pull request, the spec) carries the Milestone's membership label, in the form the repo's **Boundary record** (`docs/agents/boundaries.md`, written by `setup-dev-skills`) names; the Milestone issue carries the same label. With no Boundary record, or no such label, the pull request is outside a Milestone. `to-tickets` copies the Spec's membership label to each Ticket it splits from it, so each Ticket is inside the Milestone too (its ticket check and any pull request of its own included), and publishes a Milestone Spec's breakdown without asking the user when the Tickets keep the Spec's scope (amended 2026-11-02, Ticket #458). A retro's check pull request, which has no issue of its own, records `Retro origin: <Ticket or Spec issue link>` in its body before Review. Review and merge both read that originating issue's labels against the Boundary record; the Review records its membership and source, and the merge rechecks them. The origin supplies the agreement and destination for agent design answers, without becoming an issue the check builds or supplying its attempt history. An unrelated no-issue pull request remains outside; the corrective check still parks on its first failed attempt with its record on the pull request (amended 2026-11-02, #476).

**Inside a Milestone**, the thread brings the pull request to the user only if:

- it crosses a boundary: it takes, or its merge would take, an action the Milestone issue forbids or says needs the user's approval, or one the Boundary record says needs the user's approval and the Milestone issue does not explicitly allow; or it is a one-way door (below) and, for any of its irreversible actions, the Milestone issue does not explicitly allow agents to take it (or, where the Milestone issue does not mention it, the record does not). The Milestone issue's allowed and forbidden actions win over the record's for its own issues;
- the repo's own rules (its `CLAUDE.md`, the project instructions, its docs) say a person merges it.

A review that will not settle is never on either list (amended 2026-11-02, #448): it ends its attempt ([ADR 0003](0003-code-review-runs-find-verify-rank-in-rounds.md)), and the second failed attempt is a **park** (Spec #400, piece B4). A pull request with no issue of its own (a retro's check) cannot be rebuilt as a Ticket: its first failed attempt is a park, with the attempt record and the `parked` label on the pull request itself. Inside a Milestone, an agreed design change received after a clean late design or late merge-only Round also ends the attempt, without a new Round, even if the other late allowance is unused; the thread follows the Review's recorded restart or park and skips merge (#481). Outside a Milestone the merge list below still brings that unreviewed change to the user. The first failed attempt is a **restart**: the thread closes the pull request unmerged with a link to the attempt record, keeps the parts no open Finding touches (the files on the record's `Untouched` line; a lone ticket splits off those that stand alone into their own pull request, reviewed and merged as usual), and has a new Implementer rebuild the rest once on a fresh branch from main, with a fixed name so a resumed thread finds it, briefed with the attempt history. The rebuild opens a new pull request, whose Review starts at Round 1 with a full Round budget; a spec thread restarts the same way on a fresh spec branch ([ADR 0005](0005-a-spec-is-one-long-lived-branch.md)). The user hears nothing of a restart until the thread's report. On a park, the thread leaves the pull request unmerged, marks its issue parked with the tracker doc's **Park** operation, and tells the user once, in one message, with the link to the attempt history. It does not bring the pull request to the user as a merge decision, and the build ends as reported. In a spec thread, a ticket whose third ticket check still has an Important open is parked the same way, with an attempt record on the ticket: the tickets it blocks are not started, the others still land, and the spec's pull request stays a draft until the user decides. Deep depth alone, and a change to an ADR, the glossary, a `CLAUDE.md` or a `REVIEW.md`, are agent merges; the thread lists each such file it merged in the pull request body (`Milestone review: <files>`) and in its report, with each design answer an agent gave on the pull request, so the user can read them at the Milestone review.

**Outside a Milestone**, the thread brings the pull request to the user if any of these holds:

- it ran at Deep depth (security, money, deleting data);
- it is a **one-way door**: reverting the change would not undo it (a data migration, deleted data, a public interface others depend on, a message sent outside the project). Each Implementer says so with its evidence, the `pr` skill marks it on the pull request, and a spec's pull request is a one-way door if any of its tickets is;
- it changes an ADR, the glossary, a `CLAUDE.md` or a `REVIEW.md`, or anything else the repo's own rules (its `CLAUDE.md`, the project instructions, its docs) say a person merges;
- an agreed answer to a design Finding that changes the pull request came with no Round left to review it.

A repo's own rules may add cases; the skills name only the general ones.

Where each pull request bumps the version ([ADR 0008](0008-each-skill-change-bumps-the-plugin-version.md)), the bump merged with it is not a published release, and it does not make the pull request a one-way door on its own: a bad change is walked back by a revert that takes the next number. A Release that publishes a version, where Releases bump, still is one.

Either way, a thread that brings a pull request to the user names what stops the merge (the boundary and where it is listed, the rule and its file, or the case on the list), so the user can decide quickly. The user then merges, or tells the thread to. This follows the Claude Code team's practice of setting human review by the risk of the change, not by who wrote it.

## Considered options

- **Upstream's `implement` as-is:** the session builds and commits to the current branch itself, with no pull request. Its context fills with code, and nothing reaches the user for review.
- **Dropping `implement-spec`** in favour of one thread per ticket: the user preferred one thread per spec, with subagents doing the tickets and one review over the whole spec.
- **Always asking the user to merge:** safe, but the user becomes the bottleneck on low-risk work.
- **Bringing a stuck review to the user as a merge decision:** a pull request the Review could not settle in two attempts lands on the user as a merge to judge without a clean review behind it; parking it tells the user at once, keeps the history on the issue and lets other work go on (2026-11-02, #400).
- **Reusing the pull request for the rebuild:** one link for the user, but Round comments are numbered per pull request, so the rebuild's Rounds would mix with the failed attempt's and start part-spent; a new pull request starts at Round 1, and the closed one keeps the failed attempt's Rounds readable as history (2026-11-02, #400).
- **Keeping Deep depth and ADR, glossary, `CLAUDE.md` and `REVIEW.md` changes as user merges inside a Milestone:** most such merges need no decision from the user, who reads them at the Milestone review instead; Deep adds scrutiny, not a wait (2026-11-01, #385).

## Consequences

- On a restart, the failed attempt's branch stays on the remote with its closed pull request; a lone ticket's rebuild and split-off are new branches off main, and its old Implementer is not reused, so the rebuild starts from the lesson rather than the old approach.
- `implement` and `implement-spec` read the Boundary record and the issue's labels in their merge step and pick the inside or outside list; a Milestone's agent merges of ADR, glossary, `CLAUDE.md` and `REVIEW.md` changes are listed for the Milestone review (#423), and so are the design answers an agent gave on a merged pull request (ADR 0003).
- `implement` and `implement-spec` are rewritten as coordinator skills. `to-tickets` adds a model tier to each ticket, `pr` gains an Evidence section and a one-way-door marker, and `to-tickets` and `wayfinder` end by offering `setup-project`. All of these are Patches (`PATCHES.md`).
- A new skill, `setup-project`, writes the project instructions that tell the coordinator how to brief build threads (which skill, model tier, repo, review depth). It runs `grilling` inside, so it asks at most 3 questions at a time. The user runs it by hand, and `wayfinder` and `to-tickets` offer it to the user at their end only when planning added a repo, a kind of thread or a standing rule. The instructions say how threads work and carry the user's tier-to-model map; they never hold the state of the work, and tell the coordinator to find open specs, plannings and tickets on the tracker. Once the user approves the text, the thread sends it to the coordinator, which saves it.
