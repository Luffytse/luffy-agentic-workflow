# agentic-review runs Find, Verify and Rank, in rounds of 2 to 5

Our `agentic-review` skill follows the shape of Claude Code's own Code Review (several Finders, then a verify step that drops false positives, then ranking by Severity), adapted to agents that review their own pull requests in a session. We kept Upstream's two Finders (standards and spec) and added cheap adversarial Finders, a regular-tier Verifier, and Rounds that stop early once nothing Important remains. Issue #51 later took over more of the built-in review's strengths: Failure scenarios, more adversarial angles, unsure candidates passed on to Verify, keeping realistic rare paths, the Gap sweep, and uncommitted work in a Review since a fixed point.

## How a Review runs

1. **Find.** The standards Finder and spec Finder (regular tier) run in parallel with 2 adversarial Finders (cheap tier). When there is no spec or ticket, the spec Finder is skipped and the Review says so. Each adversarial Finder takes one angle chosen to fit the pull request, such as bugs and edge cases, security and privacy, or contradictions with the ADRs and glossary. Unchanged lines inside a function the change touches are in scope. Every Finding proposes a Severity, names its Bug class, states its **failure scenario** (the inputs or state, then the wrong result; a cleanup Finding states its cost instead), and lists every place in the pull request where that class occurs (in commit Rounds too, not only in the new commits). A Finder passes on a candidate it only half believes, marked unsure, for Verify to judge.
2. **Verify.** For each candidate Finding, a Verifier (regular tier) opens the cited file and line and checks the claim against the code itself, not against names. It makes the final call on four things, with one line of reasoning each: whether the Finding is real (keep or drop); whether this pull request caused it (if not, its Severity is Pre-existing); whether it is Important or a Nit, confirming or changing the Finder's proposal; and, for a Nit, whether to "fix" or "skip" it. A realistic rare path (an error handler, a race, a falsy zero) is kept: rare is no reason to drop. On Quick and Standard, one Verifier agent checks all the Findings of a Review. On Deep, three Verifiers each check every Finding: a Finding is kept only when at least two say it is real, and the Verifiers who said it is real decide the other calls by majority. If they tie, or Severity splits three ways, the more cautious value wins (Important over Nit, caused-by-this-pull-request over Pre-existing, "fix" over "skip").
3. **Rank.** The kept Findings are deduplicated and matched against earlier Rounds and Ticket checks location by location. Every match, in all three steps, is by overlapping lines in one file and the same claim, whatever Bug class the Finder gave; an earlier row's lines are first brought to this Review's head by the diff from the head they were counted at, `git diff -U0` so hunks hold only changed lines (shifted by the lines added and removed above them; a line inside a changed hunk becomes that hunk's lines); a renamed file is followed to its new path (`git diff -M --name-status`), and a location in a file deleted since matches nothing, though an open Important there still goes to the Verifier, and the lines a still-open answer cites stand in for it. A location matching a Finding already dismissed in an earlier Round or Ticket check (dropped by Verify, an earlier Important a Verifier dismissed as never real, Nits marked "skip", or design Findings the user, or inside a Milestone an agent, kept) is dropped only while neither the code at that Finding's locations nor the code its Note cites has changed since the head of the comment that dismissed it, tested by a diff from that head to HEAD (the Verifier names the lines its reason rests on; a Verifier's dismissal citing none is judged afresh when a file of its locations changed, while a design Finding the user or an agent kept binds while its locations are unchanged; a touched line, or a "skip" Nit that now reads as Important, makes the location judged afresh); the Finding's other locations stay, and a Finding left with none is dropped. A Finding matching one still open from earlier keeps that id and stays open until the row closes (fixed, dismissed by a Verifier as never real or because the user or an agent kept the design, or merged), with its new locations added, save a location an earlier fix closed, which is a regression (an unfixed Important still blocks the stop; a fixed one holds nothing, so a regression is new); when this Round's Verifier rates it higher (Nit to Important, Pre-existing to caused by this change), the open row is raised under its id and counts toward the stop, while a lower rating changes nothing. A Finding matching two or more open rows is held by the one raised first, and the others are merged into it (their live locations move to its Locations, their fixed ones to its Note, and they become `dismissed`, "merged into" its id), so one problem never counts as two open Importants. A Finding fixed at only some locations stays open at the rest. Every earlier Important still open after Verify is reported again under its id, counted once, so a failed fix goes back to the owner; a partly fixed "fix" Nit is reported again too, within the cap of 5 Nits; any other held Nit or Pre-existing Finding is reported again only when raised. The rest are sorted by Severity. At most 5 Nits are reported, "fix" Nits first.

Without a `REVIEW.md` saying otherwise, **Important** means the change would break behaviour, lose or leak data, contradict the spec or an ADR, or make a rollback unsafe; anything else real is a **Nit**.

Each Review keeps a record of every Finding raised or dismissed in its pull request, so later Rounds can drop repeats and `retro` can see which Bug classes came up more than once. Each Round posts one comment on the pull request listing the Findings it raised and dismissed, and that is the record; `retro` reads all of them.

Every Round starts brand-new Finder and Verifier agents; none is reused from an earlier Round, so each Round reads the code with fresh eyes.

## Review depth

- **Quick:** the standards and spec Finders only, one Verifier.
- **Standard (default):** all four Finders, one Verifier.
- **Deep:** the Finders above plus a **security Finder** on the premium tier, and three Verifiers that each take a different stance: a **tracer** that follows the code path to show the bug happens, a **skeptic** that argues it is a false positive, and a **spec checker** that judges it against the spec, ADRs and tests. Every Finding, the security Finder's included, is kept only when at least two of the three agree. After Verify, a **gap sweep** Finder (premium tier) gets the kept Findings and looks only for what the change is missing, such as moved code that dropped a guard, a flipped default, or setup with no matching teardown. Its Findings go through a second three-stance vote.

Deep is for risky pull requests (security, money, deleting data, or anything the user marks), Quick for docs-only or trivial ones, and Standard for the rest. The depth is chosen once per pull request and stays the same across its Rounds unless the user changes it, except that a merge-only Round (a later Round that reviews only a merge from main whose conflicts are only text) runs at Quick unless the resolutions touch logic.

A Review since a fixed point, outside a pull request, also reads uncommitted work: staged, unstaged and untracked new files. Pull-request Rounds review commits only.

A repo can add a short `REVIEW.md` at its root saying what Important means there, what to skip, and what to always check.

## Rounds

Rounds 1 and 2 review the whole pull request. Rounds 3 to 5 review only the commits added since the previous Round. In every Round, the Verifier also re-checks each **open Important** (one raised in an earlier Round and not yet closed) against the current code, given its locations already brought to this head as Rank brings them and told to find the code by its claim, not by line number alone, and closes it once the fix is there, or as dismissed when it was never real.

A Round is **clean** when, after its Verify, no Important is open: it found no new Important (a design Finding the user, or inside a Milestone an agent, kept counts as none), and every earlier one is confirmed fixed, dismissed by a Verifier as never real or because the user or an agent kept the design, or merged into another row.

- **Round 1** always leads to Round 2. Its fixes and its "fix" Nits are committed, and Round 2 reviews them.
- **Round 2 to Round 4**, if not clean: the fixes and "fix" Nits are committed, and the next Round reviews them.
- **Round 2 to Round 5**, if clean: its "fix" Nits go into one last commit that no further Round reviews, and the pull request is ready to merge; an agreed change to the design gets one more Round instead.
- **Round 5**, if not clean: the attempt ends, and an agreed change to the design that comes at Round 5 gets one late design Round (below). Neither goes to the user as a merge decision, inside a Milestone or outside one (amended 2026-11-02, #448).
- **A merge from main with conflicts** once no Round is left (after a clean Round 5 or late design Round): one late merge-only Round (below), not the user (amended 2026-11-02, #447).

On a pull request that changes design (one that adds or edits an ADR, the glossary, a spec or a design doc, a lone Ticket's pull request that edits one included), a Finding that questions the design goes to the user as a grilling question with a recommended answer, at most 3 at a time, and only the agreed answer is committed; a design Finding the user settles by keeping the design is `dismissed`, with "user keeps the design" in its Note, and when the user keeps the design on every open one and no other Important is open, the Round counts as clean, Round 1 included. Round 1 still leads to Round 2. In Rounds 2 to 5, commit the remaining text "fix" Nits and check every location before posting the clean comment or editing an already posted comment to `clean`; record fully fixed Nits as `fixed` with the commit and keep partly fixed ones `open` at their live locations. An agreed answer that changes the pull request gets one more Round, within the 5-Round cap, even after a clean Round; at Round 5 it gets the late design Round (below). Findings about the text are fixed as usual (issue #112). Agreement with the user at the end matters more than fewer Rounds. Fixing design Findings alone wrote rules the user never agreed into ADRs.

Inside a Milestone (amended 2026-11-02, from [#385 item 5](https://github.com/Luffytse/luffy-dev-skills/issues/385#issuecomment-6556848716)), the user has already agreed the Milestone's goal, each feature's acceptance criteria and the exclusions, so a design Finding goes to the user only if answering it would change one of them. Every design Finding first goes to a new premium-tier agent that checks it against the Milestone issue and the feature's spec. When its answer keeps the agreement (keep the design, or a change to make), it is recorded as a comment on the spec issue, and in an ADR in the pull request when it is a lasting decision; the row says "agent keeps the design" (`dismissed`) or "agent answers" (`open`, the owner commits the change), and the Review goes on, an answer that changes the pull request getting one more Round as a user's does. When the answer would change the agreement, or the agent is unsure, the Finding goes to the user as above, saying which part it would change. A design an agent kept counts everywhere a design the user kept counts: the clean Round, Rank's drop and closing rules, Ticket checks and the record's status. Membership is decided as the build skills decide it (ADR 0004); a no-issue corrective check uses its recorded Retro origin for membership, agreement and design-answer comments, while its attempt history stays on the check pull request. The agent answers are listed for the Milestone review. Outside a Milestone nothing changes.

Inside a Milestone (amended 2026-11-02, from [#385 item 4](https://github.com/Luffytse/luffy-dev-skills/issues/385#issuecomment-6556848716)), a fixer who believes an Important is wrong may **rebut** it instead of fixing it, so a false alarm cannot block a merge forever: the rebuttal says why the Finding is wrong, with evidence (`file:line`, a test run or command output). A brand-new Verifier on the **premium** tier, at every depth, gets the Finding, its evidence and the rebuttal, judges at the head of the Review the rebuttal answers, reruns what the rebuttal quotes, and makes the final call. It dismisses the Finding only when the rebuttal shows the claim does not hold; the row becomes `dismissed`, with "rebuttal upheld", the reason and the lines it rests on in its Note, and counts as a Verifier's dismissal as never real everywhere (the clean Round, Rank's drop and closing rules, Ticket checks and the record's status). Otherwise, an argument that the problem is only rare, small or out of scope and any doubt included, it upholds the Finding: the row stays `open` with "rebuttal rejected" in its Note, must be fixed (a later Verifier cannot dismiss it), and cannot be rebutted again. A rebuttal changes no code, so it takes no Round. A design Finding is answered by the design-answer rules, never rebutted. Rounds and Ticket checks follow the same rule; outside a Milestone the owner fixes every Important, as before.

For every pull request, inside a Milestone or outside one (amended 2026-11-02, #448: the user decided that the rule does not depend on membership; first written for Milestones from [#385 item 4](https://github.com/Luffytse/luffy-dev-skills/issues/385#issuecomment-6556848716), [late design answers stay bounded](https://github.com/Luffytse/luffy-dev-skills/issues/385#issuecomment-6564032768), [#386 repair loops](https://github.com/Luffytse/luffy-dev-skills/issues/386#issuecomment-6557091266) and [attempt history follows the problem](https://github.com/Luffytse/luffy-dev-skills/issues/386#issuecomment-6563990584)), a review that will not settle never becomes the user's merge. From Round 2, after Rank, a **convergence check** looks at each Important caused by the change: it **returned** when it matches, by Rank's match rule, a row an earlier Round or Ticket check marked `fixed` (Rank already calls it a regression; a Finding held under a still-open row does not count), and it **flipped** when its fix would undo an earlier row's fix (it overlaps a line that row's fixing commit changed, and doing what it asks would make that row's claim true again). When unsure, neither: a false match ends a healthy review, a missed one costs only Rounds the cap still bounds. A returned or flipped Finding, or a Round 5 that is not clean, ends the Rounds of the **attempt** (one build of the change and its Rounds): nothing more is fixed, the Round's Result reads `attempt ended: restart (<cause>)` or `attempt ended: park (<cause>)`, its Pre-existing Findings are filed as after any last Round, and an **attempt record** goes on the issue the pull request builds (the lone Ticket or the Spec; on the pull request itself when it builds no issue, a retro's check pull request, say), in the shape `review-record` owns: the attempt number, the pull request, the Rounds, the Findings it ended on with the rows they returned to or flipped, what was tried, the lesson, and the files no open Finding touches (candidates to split off). The record sits on the issue, not the pull request, because the history follows the problem across pull requests, Tickets, agents and restarts: a later attempt's Review reads every earlier record, and a Finding with the same claim in the same file as a returned or flipped row there counts as returned. The outcome goes to the caller: `restart` when the issue held no earlier record, `park` when it held one, and `park` for a pull request with no issue (nothing to rebuild a Ticket from); what a restart and a park do is the build skills' ([ADR 0004](0004-build-threads-coordinate-and-subagents-code.md)). A rebuttal changes only a row's status: a row dismissed by an upheld rebuttal is never `fixed`, so nothing returns to it or flips it; a row whose rebuttal was rejected counts once it is `fixed`; and the check runs before this Round's fixes or rebuttals, so a returned or flipped Finding is not rebutted. An agreed design answer that changes the pull request after Round 5 gets one **late design Round** (Round 6) rather than going in unreviewed, at most one per attempt, carrying the attempt's rows; if it is not clean or brings another such change, the attempt ends. Conflicts in the merge from main just before merge, when no Round is left, get one **late merge-only Round** (Round 6, or 7 after a late design Round; amended 2026-11-02, #447), at most one per attempt: clean means ready to merge; not clean, or conflicts again after it ran, ends the attempt with the cause `merge-only Round did not settle`, and the pull request never goes to the user for it, inside a Milestone or outside one. Who answers design Findings and whether an Important can be rebutted still depend on membership, as above.

Every Finder and Verifier also gets the **settled designs**: the decisions the spec records, the kept-design rows of earlier Rounds and Ticket checks whose locations are unchanged since they were dismissed (the same test as Rank's drop rule), and inside a Milestone the agent answers on the spec issue, with "do not propose an alternative a settled decision rejected": a Finding that the chosen design is imperfect is real only if the text overclaims or contradicts itself or the repo, or the Finding shows the decision breaks what the user agreed (then it is a design Finding) (#217: Finders raised a decision the user had made, Round after Round, and only a Verifier told the decision by hand dropped it).

Once the pull request's last Round is done (an attempt's last Round included), each Pre-existing Bug class becomes one GitHub issue labelled `needs-triage`, so it is tracked without blocking the pull request. When a Bug class had more than one instance in a pull request (in one Finding or across Rounds), `retro` turns it into a deterministic check or a `REVIEW.md` line, so later Reviews do not have to catch it again.

## Considered options

- **Cheap Verifiers.** Cheaper, but verifying is a judgement task, and cheap Verifiers checking cheap Finders tend to share their blind spots. A Verifier reads one Finding and the files it cites, so the regular tier costs little extra.
- **Two Verifiers that must both agree on Deep.** One wrong Verifier would drop a real bug. Three with a majority, each with a different stance, gives votes that are more independent than three copies of the same prompt.
- **A separate premium whole-design review.** The Claude Code team's process (blog post "How the Claude Code team does code review", 2026-10-15) has no such reviewer: people keep direction and architecture. Design questions come to the user during grilling, the spec Finder and adversarial angles check ADRs, and Deep covers risky pull requests.
- **A regular-tier gap sweep.** Cheaper, but seeing what is absent is harder than checking what is there, and it runs once per Review, on Deep only, where the change is risky. Premium matches the security Finder.
- **A regular-tier Verifier for rebuttals, or the fixer's word.** A rebuttal is the one way an Important closes without a fix, inside a Milestone where no person checks the merge, so taking the fixer's word would make it an easy way around review, and a regular Verifier on the same tier as the one that kept the Finding would mostly repeat its call. A premium Verifier reads one Finding and its rebuttal, so the cost is small (#385).
- **Every design Finding to the user, inside a Milestone too.** Safe, but the pull request waits on the user for questions the agreement already answers, which is what a Milestone's agreement is for (#385).
- **Running to Round 5, then the user.** The rule outside a Milestone until 2026-11-02, but a Finding that keeps coming back or a fix that undoes another rarely settles with more patching, and the user should not be the way out of a stuck review, whether or not the pull request is inside a Milestone (#385, #448).
- **Matching a returned Finding by Bug class, or by file alone.** Wider, but two different problems on the same lines would end a healthy review; Rank's match rule (same lines, same claim) is already how a regression is told apart from a new Finding. Across attempts lines cannot be compared, so the claim and the file are.
- **Claude Code's cap of 3 Rounds** (after three Rounds their reviewer asks the author to reconsider the approach, per the same post). Their review prompts and project history let most pull requests pass in one Round. We keep two full-PR Rounds and a cap of 5, with the later Rounds limited to new commits.
