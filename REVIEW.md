# Review rules

## Important

The default meaning of Important in `agentic-review` applies.

## Skip

- **wording edge case that needs a new clause**: in skill or doc text, an edge case whose fix adds a clause is a Nit (skip) unless an agent following the text literally would produce a wrong result. When the Ticket asks for a minimal change, weigh the clause's length against that.

## Always check

- **related text not updated when a rule changes**: for a Shared rule (the glossary's ownership term), check every consumer, record shape, glossary entry and ADR that uses or describes the changed contract, invoked workflow rule or project configuration. Similar independent rules may differ. For every changed rule, shared or independent, also check parallel sentences in the edited file for contradictions. For rule changes and repository layout or packaging changes, check repository descriptions and contributor recipes for stale claims, including those in `CLAUDE.md`/`AGENTS.md` and READMEs and their quoted counts and names. Keep these protections for existing links and unmigrated shared copies; ownership does not retire a live rule.
- **a step asks for data its input does not carry**: every field a step writes (an issue body, a report line, a comment row) comes from an output or record that carries it.
- **skill description collides with another skill or with the router's routing**: when a change edits a skill's description or `ask-matt`'s routing, check the description's "Use when" branches against every other `plugins/dev-skills/*/*/SKILL.md` description and against `ask-matt/SKILL.md`; no realistic user phrase may match two descriptions (two claiming the same trigger) and none may contradict what `ask-matt` says about that skill.
- **shared record written by more than one thread**: when a skill has more than one thread or agent write the same issue body, file or record, check that one writer owns it and the others only append (comments, new files), or that the text gives a mechanism that stops a stale write (a lock, a version check, a single merge step), not only a re-read; a "re-read before editing" rule does not stop a write from a stale copy dropping another thread's lines.
- **results entry out of date with its own PR**: when a change adds or edits an eval `RESULTS.md` entry, check that every number, SHA, Round and "not exercised" claim in it agrees with the rest of the entry and with the repo as of the entry's own commit and the pull request's final state; values the entry labels as its base are not stale.
- **skill text that only fits this repo**: when a change edits anything under `plugins/dev-skills/` that agents load (skills, their reference files, seeds and templates), check that it names no path, file, ADR, issue, person, project or rule that exists only in this repo (for example `scripts/check-plugin.sh`, an ADR number, or a merge rule only this repo has), because every project that loads the plugin reads that text. Such a rule goes in this repo's `CLAUDE.md` or `REVIEW.md`, and the skill gives only the general case. The check `repo-free-skill-text` in `scripts/check-plugin.sh` catches this repo's ADR numbers, "Upstream", its project, repo and person names and the paths of its own tooling; this line covers the rest.
- **rule names a condition no command can read**: when a change states a rule whose condition an agent must test (merged, approved, owned by, closed by), check that the text gives the command, field or route that reads that condition, that every parallel recipe in the file applies the same rule, and that a negative marker alone (for example "a `wontfix` label") is not offered as the test of a positive condition.
- **command that decides a step never run on real data**: when a change adds or edits a `gh`, `git` or `jq` command (or a regex) whose output decides a step (shipped, merged, found, matches), check that the pull request shows the command's output on a real example of each outcome from the repo's own history (the Finder or Verifier runs it if the pull request does not), because a command can parse and still read a field that is often empty (an issue's `closed` event without a `commit_id`) or match more than the rule says (a keyword inside another word).
- **eval scoring that does not test what it says**: when a change edits an eval's expected results or planted candidates (`EXPECTED.md`, `VERIFY-ONLY.md`, not `RESULTS.md`), check that each pass list states every condition its own "why expected" text names, that each Severity it expects follows the meaning of Important the fixture uses, and that no planted false candidate quotes in its Evidence the line that refutes its Claim.
- **glossary term written in another form**: when a change adds or edits text that uses a term `GLOSSARY.md` defines, check every use in the diff is spelled and capitalised as the glossary defines it (for example "Release planning", not "release planning"), apart from the ordinary English word in its ordinary sense.
- **decision recorded as in force before its rule change lands**: when a change adds an ADR or glossary entry whose rule replaces one still stated in `CLAUDE.md`, a skill or a check, and the replacement lands in a later change, check that the new text says the old rule governs until then, in every place it states the new rule.
- **step re-entered with state recorded earlier**: when a change adds or edits a step an agent can stop before and re-enter later (a resume path, a rerun, a version or number taken once), check that the text re-reads the state that may have changed since (main's version, whether a pull request merged or is still open, other open Releases) at the point of use, and says what a rerun does when the step already happened; and that the test it uses still works once a later change has moved the state past it (an equality test on a version fails once a newer version is on main), in the first run and in every resume path.
