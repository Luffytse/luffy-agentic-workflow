# Issue tracker: GitHub

Issues and specs for this repo live as GitHub issues in [`<owner>/<repo>`](https://github.com/<owner>/<repo>). Use the `gh` CLI for all operations. A session without `gh` (some cloud sessions) does the same operations with the GitHub tools it has.

Some cloud sessions have `gh` but no GraphQL: `gh repo view`, `gh issue view`, `gh issue list` and the other `gh issue` subcommands, and `gh label list`, fail with "GraphQL is not available". `gh api repos/<owner>/<repo>/...` (REST) still works, so each operation below also gives its REST route; use that route there, or the session's GitHub tools. `gh api repos/<owner>/<repo>/labels --paginate --jq '.[].name'` lists labels, and `gh api repos/<owner>/<repo>` checks that the repo is reachable.

## Conventions

- **Create an issue**: `gh issue create --title "..." --body "..."`. Use a heredoc for multi-line bodies. REST: `gh api --method POST repos/<owner>/<repo>/issues -f title="..." -f 'labels[]=<label>' -F body=@- <<'EOF'` with the body on the lines after it, ended by `EOF` (`-F body=@-` reads the body from stdin; repeat `-f 'labels[]=...'` for more labels).
- **Read an issue**: `gh issue view <number> --json number,title,body,labels,comments`. REST: `gh api repos/<owner>/<repo>/issues/<number>` for the issue and `gh api --paginate repos/<owner>/<repo>/issues/<number>/comments` for its comments.
- **List issues**: `gh issue list --state open --json number,title,body,labels,comments --jq '[.[] | {number, title, body, labels: [.labels[].name], comments: [.comments[].body]}]'` with appropriate `--label` and `--state` filters. REST: `gh api --paginate 'repos/<owner>/<repo>/issues?state=open&labels=<label>' --jq '.[] | select(.pull_request | not) | {number, title, body, labels: [.labels[].name]}'` (`state` is `open`, `closed` or `all`; `labels` is a comma-separated list that must all match; this route also returns pull requests, so the `select` drops them). It carries only a comment count, so read the comments of each issue you need with the **Read an issue** route.
- **Make an issue a sub-issue of a parent**: `gh issue create --parent <parent> ...`, or `gh issue edit <parent> --add-sub-issue <child>` afterwards (`gh` 2.94+). Older `gh`, or a session without GraphQL: make the new child with the **Create an issue** route, then link it with `gh api --method POST repos/<owner>/<repo>/issues/<parent>/sub_issues -F sub_issue_id=<child-db-id>` (database id, as in **Blocking** below). Without sub-issues, put `Part of #<parent>` at the top of the child body.
- **Blocking**: GitHub's **native issue dependencies**, the canonical, UI-visible representation. Add an edge with `gh issue create --blocked-by <n>,<n> ...` or `gh issue edit <child> --add-blocked-by <blocker>` (`gh` 2.94+). Older `gh`, or a session without GraphQL: `gh api --method POST repos/<owner>/<repo>/issues/<child>/dependencies/blocked_by -F issue_id=<blocker-db-id>`, where `<blocker-db-id>` is the blocker's numeric **database id** (`gh api repos/<owner>/<repo>/issues/<n> --jq .id`, _not_ the `#number` or `node_id`). Where dependencies aren't available, fall back to a `Blocked by: #<n>, #<n>` line at the top of the child body. A ticket is unblocked when every blocker is closed by a merged change; a blocker closed without a merge (for example as wontfix) does not unblock it. This is the rule for tickets that a change builds; a wayfinding ticket follows the wayfinding skill.
- **Count open blockers**: first read a `Blocked by: #<n>` line at the top of the issue body (count those issues that are still open). Then `gh api repos/<owner>/<repo>/issues/<n> --jq .issue_dependencies_summary.blocked_by` (open native blockers only). To list the blockers with their state, `gh api --paginate repos/<owner>/<repo>/issues/<n>/dependencies/blocked_by --jq '.[] | {number, state}'` (REST, no GraphQL). It lists closed blockers too, so show only open ones: `--jq '.[] | select(.state == "open") | .number'` (no output means none open). `gh issue view <n> --json blockedBy` needs GraphQL and a `gh` that has that field; it also lists closed blockers, so filter it: `--jq '[.blockedBy.nodes[] | select(.state == "OPEN")] | length'`. Startable only when no `Blocked by` issue is open and the native blockers are 0. These counts see only open or closed, so they treat every closed blocker as cleared. If the blocked ticket is built by a change (not a wayfinding ticket, label `wayfinder:<type>`), also check how each closed blocker was closed: `gh api --paginate repos/<owner>/<repo>/issues/<blocker>/timeline --jq '.[] | select(.event == "closed") | .commit_id'` prints a commit SHA when a merged change closed it and an empty line (JSON `null`) when it was closed by hand. A blocker with no SHA, a `wontfix` label or `state_reason` `not_planned` was closed without a merge: do not start the dependent and tell the user. A wayfinding ticket's blockers are cleared once closed.
- **Comment on an issue**: `gh issue comment <number> --body "..."`. REST: `gh api --method POST repos/<owner>/<repo>/issues/<number>/comments -f body="..."`.
- **Apply / remove labels**: `gh issue edit <number> --add-label "..."` / `--remove-label "..."`. REST: `gh api --method POST repos/<owner>/<repo>/issues/<number>/labels -f 'labels[]=<label>'` to add and `gh api --method DELETE repos/<owner>/<repo>/issues/<number>/labels/<label>` to remove (URL-encode a label with spaces or a colon, as `wayfinder%3Amap`).
- **Close**: post the explanation with `gh issue comment <number> --body "..."`, then `gh issue close <number>`. REST: post the comment as in **Comment on an issue**, then `gh api --method PATCH repos/<owner>/<repo>/issues/<number> -f state=closed -f state_reason=completed` (`not_planned` for a wontfix close). On an already-closed issue, `gh issue close --comment` drops the comment and still exits 0.
- **Assign yourself**: `gh issue edit <number> --add-assignee @me`. REST: `gh api --method POST repos/<owner>/<repo>/issues/<number>/assignees -f "assignees[]=$(gh api user --jq .login)"`.

Infer the repo from `git remote -v`; `gh` does this automatically when run inside a clone.

File issues only into the user's own repo. Never file into the plugin's own repo (where these skills come from) unless the user owns it. In a fork, `gh` can default to the upstream parent, so before the first `gh issue create` of a session, check the target with `gh api repos/<owner>/<repo> --jq '.parent.full_name // empty'` (REST; a non-empty answer means a fork), or `gh repo view --json nameWithOwner` where GraphQL works, and confirm it with the user if it is not their repo.

## Pull requests as a triage surface

**PRs as a request surface: no.** _(Set to `yes` if this repo treats external PRs as feature requests; `triage` reads this flag.)_

When set to `yes`, PRs run through the same labels and states as issues, using the `gh pr` equivalents. `gh pr view`, `gh pr comment`, `gh pr edit` and `gh pr close` need GraphQL or fail the same way in a session without it, and `gh pr diff` can fail; each has a REST route below (a PR is an issue for comments, labels and state):

- **Read a PR**: `gh pr view <number>`, then `gh pr view <number> --comments` (off a TTY, `--comments` prints only the comments, not the body), and `gh pr diff <number>` for the diff. REST: `gh api repos/<owner>/<repo>/pulls/<number>` for the PR, `gh api repos/<owner>/<repo>/issues/<number>/comments` for its comments, `gh api repos/<owner>/<repo>/pulls/<number>/comments` for its review comments on the diff, `gh api repos/<owner>/<repo>/pulls/<number>/files` for the changed files and `gh api repos/<owner>/<repo>/pulls/<number> -H 'Accept: application/vnd.github.diff'` for the diff.
- **List external PRs for triage**: `gh api --paginate 'repos/{owner}/{repo}/pulls?state=open' --jq '.[] | select(.author_association | IN("OWNER","MEMBER","COLLABORATOR") | not) | {number, title, author: .user.login, author_association, labels: [.labels[].name]}'`.
- **Comment / label / close**: `gh pr comment`, `gh pr edit --add-label`/`--remove-label`, `gh pr close`. REST: `gh api --method POST repos/<owner>/<repo>/issues/<number>/comments -f body="..."`, `gh api --method POST repos/<owner>/<repo>/issues/<number>/labels -f 'labels[]=<label>'` to add and `gh api --method DELETE repos/<owner>/<repo>/issues/<number>/labels/<label>` to remove, and `gh api --method PATCH repos/<owner>/<repo>/issues/<number> -f state=closed` to close.

GitHub shares one number space across issues and PRs, so a bare `#42` may be either: resolve with `gh pr view 42` and fall back to `gh issue view 42`. REST: `gh api repos/<owner>/<repo>/issues/42` answers for both, and it is a PR when the response has a `pull_request` key.

## Wayfinding operations

Used by `wayfinder`. The **map** is a single issue with **child** issues as tickets.

- **Map**: a single issue labelled `wayfinder:map`, holding the Notes / Decisions-so-far / Fog body. `gh issue create --label wayfinder:map`. REST: create it as in **Create an issue** with `-f 'labels[]=wayfinder:map'`.
- **Child ticket**: an issue linked to the map as a GitHub sub-issue (see **Make an issue a sub-issue of a parent**). Where sub-issues aren't enabled, add the child to a task list in the map body and put `Part of #<map>` at the top of the child body. Labels: `wayfinder:<type>` (`research`/`prototype`/`grilling`/`task`). Once claimed, the ticket is assigned to the driving dev.
- **Blocking**: see **Blocking** under Conventions.
- **Frontier query**: list the map's open children (`gh issue list --state open`, scoped to the map's sub-issues / task list), drop any with an open blocker (see **Count open blockers**, or an open issue in the `Blocked by` line) or an assignee; first in map order wins. REST: `gh api --paginate repos/<owner>/<repo>/issues/<map>/sub_issues --jq '.[] | select(.state == "open") | {number, title, assignees: [.assignees[].login]}'` lists the open sub-issues with their assignees (the order is the map order).
- **Claim**: `gh issue edit <n> --add-assignee @me`, the session's first write. REST: as in **Assign yourself**.
- **Resolve**: `gh issue comment <n> --body "<answer>"`, then `gh issue close <n>` (REST: as in **Comment on an issue** and **Close**), then append a context pointer (gist + link) to the map's Decisions-so-far (REST: read the current body with `gh api repos/<owner>/<repo>/issues/<map> --jq '.body // empty'`, append to it, and write it back with `gh api --method PATCH repos/<owner>/<repo>/issues/<map> -F body=@-`).
