# Issue tracker: GitHub

Issues and specs for this repo live as GitHub issues in [`<owner>/<repo>`](https://github.com/<owner>/<repo>). Use the `gh` CLI for all operations. A session without `gh` (some cloud sessions) does the same operations with the GitHub tools it has.

Some cloud sessions have `gh` but no GraphQL: `gh repo view`, `gh issue view`, `gh issue list` and the other `gh issue` subcommands, and `gh label list`, fail with "GraphQL is not available". `gh api repos/<owner>/<repo>/...` (REST) still works, so each operation below also gives its REST route; use that route there, or the session's GitHub tools.

## Conventions

- **Create an issue**: `gh issue create --title "..." --body "..."`. Use a heredoc for multi-line bodies. REST: `gh api --method POST repos/<owner>/<repo>/issues -f title="..." -f 'labels[]=<label>' -F body=@- <<'EOF'` with the body on the lines after it, ended by `EOF` (`-F body=@-` reads the body from stdin; repeat `-f 'labels[]=...'` for more labels).
- **Read an issue**: `gh issue view <number> --json number,title,body,labels,comments`. REST: `gh api repos/<owner>/<repo>/issues/<number>` for the issue and `gh api --paginate repos/<owner>/<repo>/issues/<number>/comments` for its comments.
- **List issues**: `gh issue list --state open --json number,title,body,labels,comments --jq '[.[] | {number, title, body, labels: [.labels[].name], comments: [.comments[].body]}]'` with appropriate `--label` and `--state` filters. REST: `gh api --paginate 'repos/<owner>/<repo>/issues?state=open&labels=<label>' --jq '.[] | select(.pull_request | not) | {number, title, body, labels: [.labels[].name]}'` (`state` is `open`, `closed` or `all`; `labels` is a comma-separated list that must all match; this route also returns pull requests, so the `select` drops them). It carries only a comment count, so read the comments of each issue you need with the **Read an issue** route.
- **Make an issue a sub-issue of a parent**: `gh issue create --parent <parent> ...`, or `gh issue edit <parent> --add-sub-issue <child>` afterwards (`gh` 2.94+). Older `gh`, or a session without GraphQL: make the new child with the **Create an issue** route, then link it with `gh api --method POST repos/<owner>/<repo>/issues/<parent>/sub_issues -F sub_issue_id=<child-db-id>` (database id, as in **Blocking** below). Without sub-issues, put `Part of #<parent>` on the line after the `Blocked by:` line (the second line of the child body), or as the first line when the child has no `Blocked by:` line (on a child that already exists, see **Add a line to an issue body**).
- **Check a sub-issue link**: the child is linked when either form is present. Native: `gh api --paginate repos/<owner>/<repo>/issues/<parent>/sub_issues --jq '.[].number'` lists the parent's sub-issues and must include the child. Fallback: the child body has a `Part of #<parent>` line (`gh api repos/<owner>/<repo>/issues/<child> --jq .body`).
- **Blocking**: GitHub's **native issue dependencies**, the canonical, UI-visible representation. Add an edge with `gh issue create --blocked-by <n>,<n> ...` or `gh issue edit <child> --add-blocked-by <blocker>` (`gh` 2.94+). Older `gh`, or a session without GraphQL: `gh api --method POST repos/<owner>/<repo>/issues/<child>/dependencies/blocked_by -F issue_id=<blocker-db-id>`, where `<blocker-db-id>` is the blocker's numeric **database id** (`gh api repos/<owner>/<repo>/issues/<n> --jq .id`, _not_ the `#number` or `node_id`). Where dependencies aren't available, fall back to a `Blocked by: #<n>, #<n>` line as the first line of the child body; a `Part of #<parent>` line, if the child needs one, is the second line. The same applies when a native write fails at run time: add the line to the existing ticket (see **Add a line to an issue body**), listing every blocker of the ticket, then check with **Count open blockers** that every blocker is in place in one form or the other. A ticket is unblocked when every blocker is closed, except a blocker closed without the work being done (`state_reason` `not_planned` or `duplicate`, or the `wontfix` label), which does not unblock it. A close as completed counts as done, because GitHub records no reliable link from a blocker to the merged change that built it. This is the rule for tickets that a change builds; a blocker that is itself a wayfinding ticket (label `wayfinder:<type>`) is cleared once closed, and a wayfinding ticket's own blockers follow the wayfinding skill.
- **Count open blockers**: first read a `Blocked by: #<n>` line if the first or second line of the issue body is one (read each named issue's state with `gh api repos/<owner>/<repo>/issues/<n> --jq .state`, and count those that are `open`). It is written first, but a body can have a `Part of #<parent>` line first and the `Blocked by:` line second, so look at both lines. Then `gh api repos/<owner>/<repo>/issues/<n> --jq .issue_dependencies_summary.blocked_by` (open native blockers only). To list the native blockers with their state and how each closed one was closed, `gh api --paginate repos/<owner>/<repo>/issues/<n>/dependencies/blocked_by --jq '.[] | {number, state, state_reason, labels: [.labels[].name]}'` (REST, no GraphQL). It lists closed blockers too; to show only the open ones, `--jq '.[] | select(.state == "open") | .number'` (when the call succeeds, no output means none open). `gh issue view <n> --json blockedBy` needs GraphQL and a `gh` that has that field; it also lists closed blockers, so filter it: `--jq '[.blockedBy.nodes[] | select(.state == "OPEN")] | length'`. Startable only when no `Blocked by` issue is open and the native blockers are 0. These counts see only open or closed, so they treat every closed blocker as cleared. If the blocked ticket is built by a change (not a wayfinding ticket, label `wayfinder:<type>`), also check how each closed blocker, from either source, was closed, unless the blocker is itself a wayfinding ticket (cleared once closed). For a native blocker the listing above already gives `state_reason` and the labels; for a `Blocked by:` line blocker read them with `gh api repos/<owner>/<repo>/issues/<blocker> --jq '{state_reason, labels: [.labels[].name]}'`. A blocker with `state_reason` `not_planned` or `duplicate`, or the `wontfix` label, was closed without the work being done: do not start the dependent and tell the user. Any other closed blocker counts as cleared (the closed event's `commit_id` is often null even when a merged pull request closed the issue, so it cannot tell a merge from a hand close). If a read in this operation fails, or a count prints `null` or something that is not a number, stop and tell the user; do not read it as cleared.
- **Add a line to an issue body**: for a fallback line (`Blocked by:` or `Part of #<parent>`) on an issue that already exists. `gh issue edit --body` replaces the whole body, so never run it with only the new line. Read the current body (**Read an issue**); if the read fails or comes back empty, stop and tell the user, and do not write. Then put the new line where the rules say: a `Blocked by:` line first; a `Part of #<parent>` line second, after the `Blocked by:` line, or first when there is none. If the body already has a `Blocked by:` line, replace that line with one listing every blocker rather than adding a second. Write the WHOLE body back (the original text with the new line in place) with `gh issue edit <number> --body-file <file>`. REST: write the whole body with `gh api --method PATCH repos/<owner>/<repo>/issues/<number> -F body=@<file>` and read it back with the **Read an issue** REST route. Then read the body back and check that the rest of the original text (everything except a replaced `Blocked by:` line) is still there and the new line is in place; if not, tell the user, write the original body back once if you still have it (and say so), and do not report the ticket published (or the link made).
- **Comment on an issue**: `gh issue comment <number> --body "..."`. REST: `gh api --method POST repos/<owner>/<repo>/issues/<number>/comments -f body="..."`.
- **Apply / remove labels**: `gh issue edit <number> --add-label "..."` / `--remove-label "..."`. REST: `gh api --method POST repos/<owner>/<repo>/issues/<number>/labels -f 'labels[]=<label>'` to add and `gh api --method DELETE repos/<owner>/<repo>/issues/<number>/labels/<label>` to remove (URL-encode a label with spaces or a colon, as `wayfinder%3Amap`).
- **Close**: post the explanation with `gh issue comment <number> --body "..."`, then `gh issue close <number>`. REST: post the comment as in **Comment on an issue**, then `gh api --method PATCH repos/<owner>/<repo>/issues/<number> -f state=closed -f state_reason=completed` (`not_planned` for a wontfix close). On an already-closed issue, `gh issue close --comment` drops the comment and still exits 0.
- **Park**: mark an issue as parked, or read whether it is. To mark it, add the `parked` label (**Apply / remove labels**), then comment on the issue (**Comment on an issue**) saying why, with a link to the records of the stall that parked it and the pull request, if there is one; a build thread that parks its own issue on a decision gives the question, the options and its recommendation instead of stall records. To read it, an issue is parked when its labels (**Read an issue**) include `parked`. A parked issue waits on the user: no skill builds it, reviews it or merges its pull request until the user removes the label (**Apply / remove labels**), which lifts the park.
- **Check the repo is reachable**: `gh api repos/<owner>/<repo>` answers for a repo the session can read. Use this REST call, not `gh repo view`.
- **List labels**: `gh api repos/<owner>/<repo>/labels --paginate --jq '.[].name'`.
- **Create a label**: `gh api --method POST repos/<owner>/<repo>/labels -f name=<label>`. `gh label create` needs GraphQL.
- **Read repo settings**: `gh api repos/<owner>/<repo>` returns `private`, `default_branch`, `allow_squash_merge` and `allow_merge_commit`. `gh api repos/<owner>/<repo>/branches/<default>/protection` and `gh api repos/<owner>/<repo>/rules/branches/<default>` return the branch protection and branch rules: a 404 from the first means no classic protection; a 403 with the "Upgrade to GitHub Pro" message means a free private repo, where branch rules cannot be enforced; any other 403 means the session cannot read them. `gh api repos/<owner>/<repo>/issues/<n>` on any issue returns `issue_dependencies_summary` and `sub_issues_summary`; `gh --version` 2.94+ has the `--parent` and `--blocked-by` flags.
- **Assign yourself**: `gh issue edit <number> --add-assignee @me`. REST: `gh api --method POST repos/<owner>/<repo>/issues/<number>/assignees -f "assignees[]=$(gh api user --jq .login)"`.

Infer the repo from `git remote -v`; `gh` does this automatically when run inside a clone.

File issues only into the user's own repo. Never file into the plugin's own repo (where these skills come from) unless the user owns it. In a fork, `gh` can default to the upstream parent, so before the first `gh issue create` of a session, check the target with `gh api repos/<owner>/<repo> --jq '.parent.full_name // empty'` (REST; a non-empty answer means a fork), or `gh repo view --json nameWithOwner` where GraphQL works, and confirm it with the user if it is not their repo.

## Pull requests as a triage surface

**PRs as a request surface: no.** _(Set to `yes` if this repo treats external PRs as feature requests; `triage` reads this flag.)_

When set to `yes`, PRs run through the same labels and states as issues, using the `gh pr` equivalents. `gh pr view`, `gh pr comment`, `gh pr edit` and `gh pr close` need GraphQL or fail the same way in a session without it, and `gh pr diff` can fail; each has a REST route below (a PR is an issue for comments, labels and state):

- **Read a PR**: `gh pr view <number>`, then `gh pr view <number> --comments` (off a TTY, `--comments` prints only the comments, not the body), and `gh pr diff <number>` for the diff. REST: `gh api repos/<owner>/<repo>/pulls/<number>` for the PR, `gh api repos/<owner>/<repo>/issues/<number>/comments` for its comments, `gh api repos/<owner>/<repo>/pulls/<number>/comments` for its review comments on the diff, `gh api repos/<owner>/<repo>/pulls/<number>/files` for the changed files and `gh api repos/<owner>/<repo>/pulls/<number> -H 'Accept: application/vnd.github.diff'` for the diff.
- **List external PRs for triage**: `gh api --paginate 'repos/{owner}/{repo}/pulls?state=open' --jq '.[] | select(.author_association | IN("OWNER","MEMBER","COLLABORATOR") | not) | {number, title, author: .user.login, author_association, labels: [.labels[].name]}'`.
- **Comment / label / close**: `gh pr comment`, `gh pr edit --add-label`/`--remove-label`, `gh pr close`. REST: `gh api --method POST repos/<owner>/<repo>/issues/<number>/comments -f body="..."`, `gh api --method POST repos/<owner>/<repo>/issues/<number>/labels -f 'labels[]=<label>'` to add and `gh api --method DELETE repos/<owner>/<repo>/issues/<number>/labels/<label>` to remove, and `gh api --method PATCH repos/<owner>/<repo>/issues/<number> -f state=closed` to close.

GitHub shares one number space across issues and PRs, so a bare `#42` may be either: resolve with `gh pr view 42` and fall back to `gh issue view 42`. REST: `gh api repos/<owner>/<repo>/issues/42` answers for both, and it is a PR when the response has a `pull_request` key.

## Merging a pull request

- **Merge a PR**: with the pull request's number, the method and the title the caller names. A squash takes the pull request's body as its commit message: save the body with `gh pr view <number> --json body --jq .body > <file>`, then `gh pr merge <number> --squash --subject '<title>' --body-file <file>`. A merge commit: `gh pr merge <number> --merge --subject '<title>'`. The single quotes and the file keep the shell from expanding backticks and `$(...)` in them; an apostrophe in the title is written as `'\''`. REST, where `gh pr` fails for lack of GraphQL: read the body with `gh api repos/<owner>/<repo>/pulls/<number> --jq '.body // ""' > <file>`, then `gh api --method PUT repos/<owner>/<repo>/pulls/<number>/merge -f merge_method=squash -f commit_title='<title>' -F commit_message=@<file>`, or `-f merge_method=merge -f commit_title='<title>'` for a merge commit.
- **Read whether a PR merged**: `gh api repos/<owner>/<repo>/pulls/<number> --jq .merged` prints `true` only for a merged pull request. A failed read or any other output means not merged.

Create a GitHub issue.

## When a skill says "fetch the relevant ticket"

Read it as in **Read an issue** above.

## Wayfinding operations

Used by `wayfinder`. The **map** is a single issue with **child** issues as tickets.

- **Map**: a single issue labelled `wayfinder:map`, holding the Notes / Decisions-so-far / Fog body. `gh issue create --label wayfinder:map`. REST: create it as in **Create an issue** with `-f 'labels[]=wayfinder:map'`.
- **Child ticket**: an issue linked to the map as a GitHub sub-issue (see **Make an issue a sub-issue of a parent**). Where sub-issues aren't enabled, add the child to a task list in the map body and put `Part of #<map>` on the line after the child's `Blocked by:` line (the second line of the body), or as its first line when the child has no `Blocked by:` line (on a child that already exists, see **Add a line to an issue body**). Labels: `wayfinder:<type>` (`research`/`prototype`/`grilling`/`task`). Once claimed, the ticket is assigned to the driving dev.
- **Blocking**: see **Blocking** under Conventions.
- **Frontier query**: list the map's open children (`gh issue list --state open`, scoped to the map's sub-issues / task list), drop any with an open blocker (see **Count open blockers**, or an open issue in the `Blocked by` line, first or second line of the body) or an assignee; first in map order wins. REST: `gh api --paginate repos/<owner>/<repo>/issues/<map>/sub_issues --jq '.[] | select(.state == "open") | {number, title, assignees: [.assignees[].login]}'` lists the open sub-issues with their assignees (the order is the map order).
- **Claim**: `gh issue edit <n> --add-assignee @me`, the session's first write. REST: as in **Assign yourself**.
- **Resolve**: `gh issue comment <n> --body "<answer>"`, then `gh issue close <n>` (REST: as in **Comment on an issue** and **Close**), then append a context pointer (gist + link) to the map's Decisions-so-far (REST: read the current body with `gh api repos/<owner>/<repo>/issues/<map> --jq '.body // empty'`, append to it, and write it back with `gh api --method PATCH repos/<owner>/<repo>/issues/<map> -F body=@-`). Both routes write the whole body from a copy read earlier, so a session resolving another ticket of the same map at the same time can overwrite the pointer. After writing, read the body back with the REST read above (`gh issue view` can fail). If the read fails or comes back empty, stop and tell the user. If the body lacks this session's pointer (match its ticket link as a fixed string), read again, append only if it is still missing, write, and check again until the line is there.
