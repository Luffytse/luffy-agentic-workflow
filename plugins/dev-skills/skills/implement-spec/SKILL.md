---
name: implement-spec
description: "Build one Spec as its Spec thread: Implementer subagents build its Tickets test-first in local worktrees off one Spec branch, each Ticket passes a ticket check and is squash-merged in, you open the Spec pull request with pr as a draft after the first Ticket lands, then run the review with agentic-review once the last has landed, and merge it into main with a merge commit or bring it to the user. Use when you are handed a Spec (the result of to-spec and to-tickets) to build and ship."
---

You are the **Spec thread**: you coordinate one Spec from its tickets to a merged pull request. **Implementers write the code.** You make the worktrees, brief the Implementers, check their evidence, run the ticket checks and the Review, merge, talk to the user. You never write or edit code yourself, not even to resolve a merge conflict.

Read the configured project issue-tracker doc before tracker operations. If none was provided, tell the user to run `setup-dev-skills`.

The tickets are not a list of steps. They are a **task graph** with blocking relationships between them, so there is always a **frontier** of tickets whose blockers have all landed.

Start every subagent with a fresh context window. Keep communication to and from subagents sparse: pass **context pointers** (the spec, tickets, notes, commits), never copies of what a pointer already gives. Run Implementers in the background, so the frontier is built at the same time. Give trivial jobs, such as rerunning a test suite, to a cheap subagent.

## 1. Read the spec and its tickets

Fetch the spec and every ticket under it from the issue tracker and state the spec's title. If the reference is ambiguous, ask.

- If it is a lone Ticket (under no Spec), stop and use `implement` instead.
- Map the blocking edges into the task graph using the tracker doc's **Count open blockers** operation and its completion rules. If any blocker outside the Spec remains uncleared, stop and tell the user (or the coordinator) which.
- Read whether the Spec, or a ticket, is parked with the tracker doc's **Park** operation. A parked Spec: stop and tell the user (or the coordinator); it waits on the user, who lifts the park. A parked ticket is not on the frontier, and the tickets it blocks stay blocked while it is open.
- Read each ticket's agent label (the tracker label doc's agent-only role). A ticket labelled for an agent other than the coding agent you run in is a **foreign ticket**: you never build it, brief an Implementer on it or run its ticket check; it goes by **Continuation** below (continuation.md).
- A ticket is **landed** when the pushed Spec branch or main holds its squash commit (the message names the ticket), or the body of a merged pull request closes it (the Spec pull request or a continuation one, or the one the tracker shows closing the ticket; merged as step 8.3 reads it). A landed ticket is never rebuilt or checked again.
- On every entry, re-entry included, fetch the Spec branch if it exists and read the tracker before starting anything: each ticket's state and comments (handoff records among them), and the Spec pull request with its ticket-check comments.

Start at `docs/dev-skills/index.md` and open only the docs that fit (with no index, fall back to `docs/dev-skills/glossary.md` and `docs/dev-skills/adr/`).

Optionally, start an **exploration subagent** for what the tickets need explored (codebase files, external docs). It saves its notes as Markdown in a directory outside the repo, so every later subagent can read them and Implementers can focus on building.

### Continuation

Read [continuation.md](continuation.md), only when the tracker label doc maps an agent-only role and a ticket carries another agent's label, you were handed one ticket under a Spec or a continuation handoff is present, or the Spec is closed with a ticket not landed. Otherwise skip it: the rest of this skill holds when every ticket is for you.

Done when you have stated the title, know the graph, the frontier, the foreign and the landed tickets, and know each ticket's **Model tier** (its "Model tier" line, set by `to-tickets`; regular if it has none).

## 2. Make the Spec branch

Create the Spec branch from an up-to-date main and push it (on re-entry, use the pushed one; a closed Spec's, as continuation.md says). Keep your own checkout on it: any Implementer working on the Spec branch itself (steps 6.1, 7 and 8.1) works there, and while one does, you run no git commands that change that checkout (merge, squash, commit, checkout, switch, stash, reset); `git worktree add` and `git worktree remove` are fine. To read a head, fetch and use `git show` or `git diff`, or `git archive` it into a scratch directory. Here and below, "fetch main" means `git fetch origin <default-branch>`; merge, diff and compare against `origin/<default-branch>` (also as the review's `<base>`), never a local `main` that may be stale. **Rejected push.** Any push to the Spec branch (yours, a Worker's, a Spec-branch Implementer's) rejected because the branch moved: fetch, merge it in (never a rebase), rerun the tests and push again; never force. Done when the branch exists on the remote.

## 3. Start an Implementer per frontier ticket

Run at most **3 Implementers at once**, counting every Implementer that is working: building a ticket, fixing Findings or conflicts, or on the Spec branch. Before starting or resuming one, wait for a free slot. For each frontier ticket that is neither foreign nor landed, when a slot is free:

1. Make its worktree yourself: `git worktree add <path> -b <ticket-branch> <spec-branch>`, with `<path>` outside your checkout. Claude Code's own subagent worktrees start only from the default branch or HEAD, so don't use them. The Ticket branch stays local and is **never pushed** (a pushed branch would have to be deleted afterwards, and where the remote cannot delete branches they would pile up).
2. Start one Implementer on the ticket's tier. Load `model-tiers` by name for the model each tier is in your coding agent; the project's own tier map overrides it. Brief it with pointers, not copies:
   - the ticket link, its worktree path and Ticket branch, and that it commits there and never pushes, running every git command as `git -C <path> ...` (a shell may start each command back in your checkout);
   - start at `docs/dev-skills/index.md`, plus the exploration notes if any;
   - the worktree is a fresh checkout and may need its dependencies installed again;
   - build test-first with the `tdd` skill, at seams agreed before the first test;
   - before reporting, read the repo's review rules file, if any, and check your diff against each Always-check line as the reviewer will;
   - when the change adds a rule that runs over a sequence of Rounds or steps, before Round 1 list the sequences (each ordering of the events the rule touches, including "it happens again") and write what the text tells the reader to do for each;
   - when an acceptance criterion names a run that needs tools you do not hold (scheduling a check-in, stopping a worker, a recorded run only the top-level session can make), the Spec thread produces that evidence, not you: build everything else, draft the criterion's eval or record entry with a `PENDING: <the run>` marker in place of each runtime fact you cannot read (for example where skills load from), report the criterion as owed, and never claim it or leave a marker in an entry you call done;
   - it never pushes, but before each commit `git status -sb` must show its Ticket branch (never a detached HEAD), so no commit lands off the branch;
   - leave the version as it is on main until the merge step: a Ticket never bumps, and the merge step adds any bump the release doc calls for to the Spec pull request, with the number the repo's own docs say how to get;
   - before reporting, merge the Spec branch tip into its Ticket branch (a merge, never a rebase) and rerun the tests;
   - report its evidence: the tests that fail before and pass after, the typecheck or the repo's checks, screenshots for anything visual (or "not visual"), and its one-way-door call (would reverting its commits undo everything the change did, including anything outside git?).

You run no `git checkout`, `switch`, `stash` or `reset` in a ticket worktree either, because they move the checkout under its Implementer; read its Ticket branch with `git show` or `git diff`, or from a `git archive` copy. Keep that same Implementer for every later fix and merge conflict on its ticket: continue it by message. If it can no longer be reached, start a new one on the same tier with a handoff (ticket, worktree, branch, what is done, what is open), and tell the user you did. If the worktree is gone (for example the machine was reclaimed), its unpushed work is gone too: redo the ticket from step 3.1.

## 4. Check the evidence

Read the Implementer's report against the ticket's acceptance criteria and rerun the checks in its worktree (a cheap subagent can, running no git command that moves the checkout). Anything missing or failing goes back to the Implementer. For each criterion the Implementer reported as owed, make the run yourself with your own tools (it is evidence, not code), then message the Implementer the output as observed; it replaces that entry's pending markers with it and commits. A run that fails, or whose result contradicts the entry, goes back as a fix; after any fix that could change what the run showed (step 5's fixes included), make the run again. If you cannot make the run either, ask the user for it and the ticket waits. Done when every acceptance criterion has evidence, no added line holds a `PENDING:` marker (grep the diff against the Spec branch), and the checks pass on the Ticket branch's head, or, when the repo has no checks, the evidence says what was checked instead.

## 5. Run the ticket check

Run `agentic-review`'s Ticket check in this thread: one Quick Round, as `review-rounds` says, on the Ticket branch against the Spec branch. Supply the Ticket and Spec, the Ticket worktree path and branch, the Spec branch as base, and any earlier Ticket-check Findings on this ticket. Run your git reads as `git -C <path> ...`; pass the worktree path to the review for its reviewers. Record the check on the Spec pull request; until the draft opens (step 6), keep the comment and post it once it does.

Route the check's open Importants and "fix" Nits to the ticket's same Implementer; it fixes and commits, or disputes a Finding with its evidence. Rerun step 4. Done when each open Important is fixed or disputed: the ticket then lands, and the Spec pull request's Round 1 carries the check's open Findings and decides them. A ticket redone from step 3.1 gets a new check.

## 6. Land the ticket

Land one ticket at a time, and none while an Implementer is working on the Spec branch itself.

1. Fetch main. If it moved, merge main into the Spec branch (a merge, never a rebase). If that conflicts, abort it and start a **new** Implementer on the Spec branch, on the highest tier of the tickets whose files conflict (regular if none), to merge and resolve; brief it with the same push check as step 7's Implementer (`git status -sb` shows the Spec branch before each push; after it, report that `git rev-parse origin/<branch>` equals `HEAD`; a rejected push as step 2 says).
2. If the Spec branch moved since the Implementer last merged it in, have it merge the tip in again and rerun its tests. Conflict resolutions from this re-merge need no new ticket check: the Spec pull request's Round 1 reviews the whole pull request, them included.
3. Squash-merge the Ticket branch into the Spec branch as one commit (no pull request), with a typed title (`<type>: <summary>`, the types and the `!` mark as `pr` says) and a message that summarises the ticket and names it. Where the repo's own rules set another title convention, use that. **Push the Spec branch straight away** (a rejected push as step 2 says).
4. Remove the worktree (`git worktree remove <path>`) and delete the local Ticket branch.
5. Load `issue-absorption` when selecting or maintaining absorbed-source closing lines throughout this step and step 9. After the first ticket lands, write the title and body with the `pr` skill and open the Spec pull request as a **draft**: it closes the spec and every ticket that has landed on the Spec branch (one `Closes #<n>` line each, as `pr` says; select absorbed-source lines under `issue-absorption`), carries each ticket's evidence in its Evidence section, and its Door is one-way if any ticket's call is. Then post the ticket-check comments kept from step 5. After each later ticket, add its lines to the body (a ticket that waited on the user and later lands gets its lines when it lands). When the user drops a ticket (takes it out of the task graph), remove its `Closes` line, and those of the issues it absorbed, from the body at once (retain source lines only as `issue-absorption` allows): the thread never closes a dropped ticket as completed, so it stays open or the user closes it as not planned, and its source issues follow `issue-absorption`.
6. Start Implementers (step 3) on any tickets this unblocked.

Done when every ticket left in the task graph has landed. Then check the body's `Closes` lines against the landed tickets, remove the line of any ticket that did not land (and maintain its absorbed-source lines under `issue-absorption`), and mark the pull request ready. If every ticket that can land has landed and the rest wait on the user, on an incomplete handoff or on another agent's worker, go to step 9 and report instead; if no ticket landed, open no draft and put the kept check comments in that report. A ticket the user drops comes out of the task graph.

## 7. Review

Run `agentic-review` on the Spec pull request in this thread: its Round 0 picks the level and, above None, hands over to `review-rounds`, which runs at most 3 Rounds. Supply the Spec and Tickets, pull request, Spec worktree path and branch, base, any level the user asked for, and every Ticket-check record, Pre-existing Findings included.

Before each Round, fetch main and, if it moved, merge it into the Spec branch as in step 6.1, and push; the next Round reviews the resolutions.

Route each Round's open Importants and "fix" Nits to a **new** Implementer on the Spec branch, on the highest tier of the tickets those Findings touch (regular if they touch no ticket's files). Brief it to check before each push that `git status -sb` shows the Spec branch, and afterwards report that `git rev-parse origin/<branch>` equals `HEAD`, handling a rejected push as step 2 says. It fixes, commits and pushes, or disputes a Finding with its evidence, as `review-rounds` says; a later Round may continue it by message if its Findings need no higher tier. For a criterion a ticket's Implementer reported as owed, give the new Implementer it in its handoff (one clause), and after a fix that could change what an owed run showed, return to step 4 and make the run again before the next Round or the merge. Continue the review to its end, its after-Round-3 sort, design answers and Pre-existing filing included. Review policy belongs to `review-rounds`; the merge decision below remains yours.

The review ends **ready to merge**, or **waiting on a boundary** when a fix, a design answer, a bug Ticket or the merge would cross the Boundary record: then the merge waits, and you bring the pull request to the user as step 8 says, naming the Finding and the boundary. Each bug Ticket the after-Round-3 sort creates is built straight after the Spec pull request merges, as a lone Ticket, with `implement`.

## 8. Merge, or bring it to the user

Read the Boundary record (`docs/dev-skills/boundaries.md`). With no Boundary record, read an empty one: no irreversible action is allowed to agents, no action needs the user's approval, and there is no Milestone label form. The record's Milestone label form and the Spec's labels decide one thing: whether a Milestone issue's own boundaries apply. They apply when the Spec carries a label in that form; then read the Milestone issue (the issue that carries the same label and holds the Milestone's goal) for allowed or forbidden actions of its own, which win over the record's for this Spec. Otherwise the record applies exactly as written. The same rule decides every merge, inside a Milestone or not.

Bring the pull request to the user, and do not merge it, only if any of these holds:

- it crosses a boundary: it takes, or its merge would take, an action that the Milestone issue (where one applies) forbids or says needs the user's approval, or one the Boundary record says needs the user's approval and the Milestone issue does not explicitly allow; or its Door is one-way (any ticket's one-way call makes it so) and, for any of its irreversible actions, the Milestone issue (where one applies) does not explicitly allow agents to take it (or, where the Milestone issue does not mention it, the record does not);
- the repo's own rules (its `CLAUDE.md`, the project instructions, its docs) say a person merges it.

A Deep review alone does not stop the merge, and neither does a change to an ADR, the glossary, a `CLAUDE.md`, an `AGENTS.md` or a `REVIEW.md`. When you merge such a change yourself, or a pull request on which an agent answered design Findings (`review-rounds` lists them, each by its row id and the link to its record), list it: before the merge, add one line to the pull request body, `Agent-merged rules: <files>; design answers: <id> <link>, ...`, naming each ADR, glossary, `CLAUDE.md`, `AGENTS.md` and `REVIEW.md` file the pull request changes and each agent design answer on it (leave out the files part, or the design-answers part, when there is none), and name the same items in your report (step 9).

When you bring the pull request to the user, name what stops the merge, so the user can decide quickly: the boundary (the action, and whether the Milestone issue or the Boundary record lists it), the repo rule (and the file it is in), or the Finding whose fix or answer the review is waiting on. The user then merges, or tells you to. Step 1 below runs last, just before the merge, on this path too: when the user tells you to merge, run it, then merge (step 2); when the user will merge it themselves, ask them to tell you first, so you can run it before they do. Otherwise merge it yourself once the review is ready to merge and CI is green (or the repo has no CI):

1. Re-read the pull request body and apply step 6.5's rule again: the spec's own line and the lines of tickets that landed stay; remove any other ticket's line and reconcile absorbed-source lines under `issue-absorption`. **Follow the repo's merge-time steps.** Read the repo's own docs for steps to take just before a merge (the repo's `CLAUDE.md` or `AGENTS.md`, and the release doc, `docs/dev-skills/release.md`) and take each one, in the order they give. **Bump the version, where pull requests bump:** when the release doc says pull requests bump the version and the Spec pull request changes what it says bumps, get the next version number just before the merge the way those docs say (from the user when they say nothing) and wait for it. Have an Implementer on the Spec branch (step 7's, or a new one briefed as there) add the bump as the pull request's last commit, with the release doc's bump-commit steps, and push. Only the Spec pull request bumps; a Ticket never did. Where the release doc says Releases bump, or the repo has no release doc, or the pull request changes nothing it says bumps, skip this part and change nothing. Then fetch main. If the Spec branch lacks commits from main, merge main in as in step 6.1, and push. If main was merged since the last Round's recorded head and that merge had conflicts, its resolutions are reviewed as `review-rounds` says under "Merges from main" (the next Round, or after Round 3 its one resolutions check, whose open Importants become bug Tickets); a merge without conflicts needs only the checks. Rerun the checks on the branch's head and wait for CI (if the repo has any). If main moves again before the merge, repeat this step. A repeat keeps an existing bump commit and its number when main's version is unchanged (get no new number, add no second bump commit). When main's version changed, get a new number; the Implementer merges main in, resolves the version file by taking main's, and redoes the bump as a new commit after the merge, superseding the old bump. "Last commit" means the last of the pull request's own work, so a merge of main after the bump is fine.
2. Merge into main with a **merge commit**, not a squash, so main keeps each ticket as its own commit. Set the merge commit's title to the Spec pull request's typed title, not GitHub's default "Merge pull request #n from ..." (`gh pr merge <n> --merge --subject '<title>'`, in single quotes so the shell expands nothing; in both forms an apostrophe in the title is written as `'\''`). Where `gh pr` fails for lack of GraphQL, use `gh api --method PUT repos/<owner>/<repo>/pulls/<n>/merge -f merge_method=merge -f commit_title='<title>'`.
3. Before completing issues, require `gh api repos/<owner>/<repo>/pulls/<n> --jq .merged` to print `true`, including when the user reports merging the pull request. A failed read or any other result does not authorize completion. Read its body and use the tracker doc's operations to read the state of each issue listed by its closing lines. For a tracker without pull-request closing support, use its configured completion operation for the Spec and each landed Ticket instead. Leave dropped or never-landed tickets and their sources unchanged. For absorbed sources, load `issue-absorption` and recheck closure eligibility. For each eligible issue still open, use the tracker doc's **Close** operation with a completed outcome and an explanation naming the pull request. If a read or close fails, stop and tell the user; do not treat it as closed.

## 9. Clean up and report

Remove any worktrees left (`git worktree list`, `git worktree remove`, `git worktree prune`) and their local Ticket branches. Tell the user (or the coordinator) the pull request link and the outcome: merged with its merge commit, waiting on a boundary (the Finding and the boundary), or waiting for the user and why (step 8's case), with any bug Tickets the review created and any ticket still waiting on the user or on another agent. A report of waiting is not your end: stay open and re-enter at step 1 on the answer, report or wake that ends the wait. For every merge of yours, also list each ADR, glossary, `CLAUDE.md`, `AGENTS.md` and `REVIEW.md` file it changed, and each agent design answer on it: the items of the `Agent-merged rules:` line.

## 10. Run the retro

Run the `retro` skill on this thread once the Spec pull request is merged and the spec and its landed tickets are closed, so the retro looks back on finished work. If you handed the pull request to the user, report as in step 9, stay open, and run the retro after they merge it or tell you that it is merged; if they drop it or close it unmerged, or no Spec pull request was opened because no ticket landed, ask whether they want a retro on what happened. If it finds a repeated Bug class to turn into a check, a regular-tier Implementer builds the check on a branch off main, in its own worktree made as in step 3.1 but off `origin/<default-branch>` (you still write no code), and you brief it as `implement` step 3 briefs one ([implement](../implement/SKILL.md)), not as in step 3.2: the branch is a lone one off main and is pushed, because the pull request needs it. Open its pull request with `pr`, its body recording `Retro origin: <Spec issue link>`; the check builds no issue, so its body is its spec. Review it as in step 7, with the check's own Implementer. At merge, step 8's rule applies, and its Milestone-issue test reads the Retro origin issue's current labels in place of the Spec's: a check that changes `REVIEW.md` is merged by you (squash-merge, as a lone pull request off main) unless step 8 stops it, and listed on its `Agent-merged rules:` line. Tell the user (or the coordinator) the retro's outcome.
