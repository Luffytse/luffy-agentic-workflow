---
name: implement-spec
description: "Build one Spec as its Spec thread: Implementers build its Tickets, then Spec pull request, review, merge. Use when you are handed a Spec (the result of to-spec and to-tickets) to build and ship."
---

You are the **Spec thread**: you coordinate one Spec from its tickets to a merged pull request. **Implementers write the code.** You make the worktrees, brief the Implementers, check their evidence, run the ticket checks and the Review, merge, talk to the user. You never write or edit code yourself, not even to resolve a merge conflict.

Read the configured project issue-tracker doc before tracker operations. If none was provided, tell the user to run `setup-dev-skills`.

The tickets are not a list of steps. They are a **task graph** with blocking relationships between them, so there is always a **frontier** of tickets whose blockers have all landed.

Start every subagent with a fresh context window. Keep communication to and from subagents sparse: pass **context pointers** (the spec, tickets, notes, commits), never copies of what a pointer already gives. Run Implementers in the background, so the frontier is built at the same time. Give trivial jobs, such as rerunning a test suite, to a cheap subagent.

## 1. Read the spec and its tickets

Fetch the spec and every ticket under it from the issue tracker and state the spec's title. If the reference is ambiguous, ask.

- If it is a lone Ticket (under no Spec), stop and use `implement` instead.
- If you were handed one ticket under a Spec, say so to whoever handed it to you and stop: a Spec's tickets are built by its Spec thread.
- Map the blocking edges into the task graph using the tracker doc's **Count open blockers** operation and its completion rules. If any blocker outside the Spec remains uncleared, stop and tell the user (or the coordinator) which.
- Read whether the Spec, or a ticket, is parked with the tracker doc's **Park** operation. A parked Spec: stop and tell the user (or the coordinator); it waits on the user, who lifts the park. A parked ticket is not on the frontier, and the tickets it blocks stay blocked while it is open.
- A ticket is **landed** when the pushed Spec branch or main holds its squash commit (the message names the ticket), or the body of a merged pull request closes it (the Spec pull request, or the one the tracker shows closing the ticket; merged as `merging`'s "After the merge" reads it). A landed ticket is never rebuilt or checked again.
- On every entry, re-entry included, fetch the Spec branch if it exists and read the tracker before starting anything: each ticket's state and comments, and the Spec pull request with its ticket-check comments.
- **Owner record.** The Spec thread that owns a Spec leaves an **owner record**: a comment on the Spec naming its thread or session, how to reach it, and the record it replaces (if any). The record **in force** is, among records replacing the same record, the earliest; a record that a later in-force record replaces is out. After that read, act on the one in force. None, or your own: you own the Spec. Another thread's: ask your coordinator (the user, when none runs) whether that thread is still running. Running: stop, build and start nothing, and tell the coordinator (or the user) the Spec is owned. Ended or unreachable, once the coordinator says so: you own it. The coordinator cannot say: ask the user and wait, building nothing, and treat the thread as ended only on the answer. Once you own it, post your owner record before step 2, then read the Spec's comments again once: if the record in force is another thread's, you stop as above. A thread re-entering as the one in force posts no second.

Start at `docs/dev-skills/index.md` and open only the docs that fit (with no index, fall back to `docs/dev-skills/glossary.md` and `docs/dev-skills/adr/`).

Optionally, start an **exploration subagent** for what the tickets need explored (codebase files, external docs). It saves its notes as Markdown in a directory outside the repo, so every later subagent can read them and Implementers can focus on building.

### Check against main

Once you own the Spec, before step 2 and on every entry, re-entry included, read the Spec and each ticket not landed against freshly fetched main: its code and docs, and the changes merged since it was written. This Spec's own branches and pull request are not evidence: the check is for what others merged. Give the Spec one verdict; a Spec part of whose tickets main already has is changed scope:

- **still valid**: main still has the problem, or does not yet do what it asks. Go on.
- **already fixed** or **obsolete**: main no longer has the problem or already does what it asks (reproduce it or read the code to confirm), or what it is about is gone from main. Write no code. Tell the coordinator (the user, when none runs) the verdict and its evidence, the file or text on main and the commit or pull request when you find it, so it can close the issue as completed naming where on main, and any branch or pull request you made; then stop. The coordinator closes or re-plans it.
- **changed scope**: part of it still holds, or it holds in another place or form. Tell the coordinator what changed, with the same evidence, and wait for its answer, building nothing; a change that would alter the Milestone's goal, acceptance or exclusions it takes to the user.
- **cannot tell**: the Spec, a ticket or main does not say enough to decide. Tell the coordinator what is missing and wait, as for changed scope.

On the coordinator's answer, re-enter at step 1. Its answer, on the issue or to you, settles this check: do as it says (build as the issues now read, or stop if it closed or re-planned them), checking again only what merged since.

Done when you own the Spec (or have stopped), have stated the title, know the graph, the frontier and the landed tickets, know each ticket's **Model tier** (its "Model tier" line, set by `to-tickets`; regular if it has none), and the check against main lets you build.

## 2. Make the Spec branch

Once you own the Spec, create the Spec branch from an up-to-date main and push it (on re-entry, use the pushed one). Keep your own checkout on it: any Implementer working on the Spec branch itself (steps 6.1, 7 and 8) works there, and while one does, you run no git commands that change that checkout (merge, squash, commit, checkout, switch, stash, reset); `git worktree add` and `git worktree remove` are fine. To read a head, fetch and use `git show` or `git diff`, or `git archive` it into a scratch directory. Here and below, "fetch main" means `git fetch origin <default-branch>`; merge, diff and compare against `origin/<default-branch>` (also as the review's `<base>`), never a local `main` that may be stale. **Rejected push.** Any push to the Spec branch (yours or a Spec-branch Implementer's) rejected because the branch moved: fetch, merge it in (never a rebase), rerun the tests and push again; never force. When the environment refuses an action the rules allow (a new branch off main, the merge itself, pushing a CI workflow file), the thread does not stall or work around it: it hands the action once, with the exact change, to the coordinator (for a fresh thread) or to the user, and records that it waits on it. Done when the branch exists on the remote.

## 3. Start an Implementer per frontier ticket

Run at most **3 Implementers at once**, counting every Implementer that is working: building a ticket, fixing Findings or conflicts, or on the Spec branch. Before starting or resuming one, wait for a free slot. For each frontier ticket that has not landed, when a slot is free:

1. Make its worktree yourself: `git worktree add <path> -b <ticket-branch> <spec-branch>`, with `<path>` outside your checkout. Claude Code's own subagent worktrees start only from the default branch or HEAD, so don't use them. The Ticket branch stays local and is **never pushed** (a pushed branch would have to be deleted afterwards, and where the remote cannot delete branches they would pile up). **On re-entry** the Ticket branch may already exist locally, left by a thread that died: never recreate it. Read what it holds ahead of the Spec branch, and whether the Spec branch already holds the ticket's squash commit. If it holds commits and the ticket has not landed, reuse it: add the worktree on the existing branch (no new branch; use its worktree if that is still there; step 9 keeps the branch of a ticket that waits), have the Implementer merge the Spec branch tip in first (a merge, never a rebase), and brief it with a handoff (ticket, worktree, branch, what is done, what is open). It continues; its evidence and step 5's check are still required, and nothing the branch holds is trusted unchecked. If the branch holds nothing, delete it and make it fresh. If the ticket has landed, it is no frontier ticket: delete the leftover branch and its worktree (step 6.4's part (a) only: later commits may have changed its files), and start no Implementer for it.
2. Start one Implementer on the ticket's tier. Load `model-tiers` by name for the model each tier is in your coding agent; the project's own tier map overrides it. Brief it with pointers, not copies:
   - the ticket link, its worktree path and Ticket branch, and that it commits there and never pushes, running every git command as `git -C <path> ...` (a shell may start each command back in your checkout);
   - start at `docs/dev-skills/index.md`, plus the exploration notes if any;
   - the worktree is a fresh checkout and may need its dependencies installed again;
   - build test-first with the `tdd` skill, at seams agreed before the first test (for instructions to an agent, see the next line);
   - When the change is instructions for an agent (a skill, a prompt, an agent instructions file), its test is an eval, not a grep for a sentence: a fresh agent run on a fixture, compared with the default branch's version and scored by scripts first; the repo's own docs say how to run one, and you choose its seam without the user.
   - before reporting, read the repo's review rules file, if any, and check your diff against each Always-check line as the reviewer will;
   - when the change adds a rule that runs over a sequence of Rounds or steps, before Round 1 list the sequences (each ordering of the events the rule touches, including "it happens again") and write what the text tells the reader to do for each;
   - when an acceptance criterion names a run that needs tools you do not hold (scheduling a check-in, stopping a worker, a recorded run only the top-level session can make), the Spec thread produces that evidence, not you: build everything else, draft the criterion's eval or record entry with a `PENDING: <the run>` marker in place of each runtime fact you cannot read (for example where skills load from), report the criterion as owed, and never claim it or leave a marker in an entry you call done;
   - it never pushes, but before each commit `git status -sb` must show its Ticket branch (never a detached HEAD), so no commit lands off the branch;
   - leave the version as it is on main: a Ticket never bumps. A bump is a merge-time step of the repo's own docs, which `merging` runs for the Spec pull request;
   - before reporting, merge the Spec branch tip into its Ticket branch (a merge, never a rebase) and rerun the tests;
   - report its evidence: the tests that fail before and pass after (for instructions to an agent, the eval run or its stated gap instead), the typecheck or the repo's checks, screenshots for anything visual (or "not visual"), and its one-way-door call (would reverting its commits undo everything the change did, including anything outside git?).

You run no `git checkout`, `switch`, `stash` or `reset` in a ticket worktree either, because they move the checkout under its Implementer; read its Ticket branch with `git show` or `git diff`, or from a `git archive` copy. Keep that same Implementer for every later fix and merge conflict on its ticket: continue it by message. If it can no longer be reached, start a new one on the same tier with a handoff (ticket, worktree, branch, what is done, what is open), and tell the user you did. If the worktree and the Ticket branch are both gone (for example the machine was reclaimed), its unpushed work is gone too: redo the ticket from step 3.1. A Ticket branch that survives without its worktree is not gone: step 3.1 says what to do with it.

## 4. Check the evidence

Read the Implementer's report against the ticket's acceptance criteria and rerun the checks in its worktree (a cheap subagent can, running no git command that moves the checkout). Anything missing or failing goes back to the Implementer. For each criterion the Implementer reported as owed, make the run yourself with your own tools (it is evidence, not code), then message the Implementer the output as observed; it replaces that entry's pending markers with it and commits. A run that fails, or whose result contradicts the entry, goes back as a fix; after any fix that could change what the run showed (step 5's fixes included), make the run again. If you cannot make the run either, ask the user for it and the ticket waits. Done when every acceptance criterion has evidence, no added line holds a `PENDING:` marker (grep the diff against the Spec branch), and the checks pass on the Ticket branch's head, or, when the repo has no checks, the evidence says what was checked instead.

## 5. Run the ticket check

Run `agentic-review`'s Ticket check in this thread: one Quick Round, as `review-rounds` says, on the Ticket branch against the Spec branch. Supply the Ticket and Spec, the Ticket worktree path and branch, the Spec branch as base, and any earlier Ticket-check Findings on this ticket. Run your git reads as `git -C <path> ...`; pass the worktree path to the review for its reviewers. Record the check on the Spec pull request; until the draft opens (step 6), keep the comment and post it once it does.

Route the check's open Importants and "fix" Nits to the ticket's same Implementer; it fixes and commits, or disputes a Finding with its evidence. Rerun step 4. Done when each open Important is fixed or disputed: the ticket then lands, and the Spec pull request's Round 1 carries the check's open Findings and decides them. A ticket redone from step 3.1 gets a new check.

## 6. Land the ticket

Land one ticket at a time, and none while an Implementer is working on the Spec branch itself.

1. Fetch main. If it moved, merge main into the Spec branch (a merge, never a rebase). If that conflicts, abort it and start a **new** Implementer on the Spec branch, on the highest tier of the tickets whose files conflict (regular if none), to merge and resolve; brief it with the same push check as step 7's Implementer (`git status -sb` shows the Spec branch before each push; after it, report that `git rev-parse origin/<branch>` equals `HEAD`; a rejected push as step 2 says).
2. If the Spec branch moved since the Implementer last merged it in, have it merge the tip in again and rerun its tests. Conflict resolutions from this re-merge need no new ticket check: the Spec pull request's Round 1 reviews the whole pull request, them included.
3. Squash-merge the Ticket branch into the Spec branch as one commit (no pull request), with a typed title (`<type>: <summary>`, the types and the `!` mark as `pr` says) and a message that summarises the ticket and names it. Where the repo's own rules set another title convention, use that. **Push the Spec branch straight away** (a rejected push as step 2 says).
4. Check the landing: (a) the pushed Spec branch holds the ticket's squash commit (the message names the ticket), and (b) right after step 6.3, before anything else touches the Spec branch, it shows no difference from the Ticket branch on the ticket's files. Only then remove the worktree (`git worktree remove <path>`) and delete the local Ticket branch. If the check fails, keep both and redo step 6.3: the Ticket branch is never pushed, so a wrong delete loses the work.
5. Load `issue-absorption` when selecting or maintaining absorbed-source closing lines throughout this step and step 9. After the first ticket lands, write the title and body with the `pr` skill and open the Spec pull request as a **draft**: it closes the spec and every ticket that has landed on the Spec branch (one `Closes #<n>` line each, as `pr` says; select absorbed-source lines under `issue-absorption`), carries each ticket's evidence in its Evidence section, and its Door is one-way if any ticket's call is. Then post the ticket-check comments kept from step 5. After each later ticket, add its lines to the body (a ticket that waited on the user and later lands gets its lines when it lands). When the user drops a ticket (takes it out of the task graph), remove its `Closes` line, and those of the issues it absorbed, from the body at once (retain source lines only as `issue-absorption` allows): the thread never closes a dropped ticket as completed, so it stays open or the user closes it as not planned, and its source issues follow `issue-absorption`.
6. Start Implementers (step 3) on any tickets this unblocked.

Done when every ticket that can land has landed. If all in the task graph have, check the body's `Closes` lines against the landed tickets, remove the line of any ticket that did not land (and maintain its absorbed-source lines under `issue-absorption`), and mark the pull request ready. If instead the rest wait on the user, go to step 9 and report; if no ticket landed, open no draft and put the kept check comments in that report. A ticket the user drops comes out of the task graph.

## 7. Review

Run `agentic-review` on the Spec pull request in this thread: its Round 0 picks the level and, above None, hands over to `review-rounds`, which runs at most 3 Rounds. Supply the Spec and Tickets, pull request, Spec worktree path and branch, base, any level the user asked for, and every Ticket-check record, Pre-existing Findings included.

Before each Round, fetch main and, if it moved, merge it into the Spec branch as in step 6.1, and push; the next Round reviews the resolutions.

Route each Round's open Importants and "fix" Nits to a **new** Implementer on the Spec branch, on the highest tier of the tickets those Findings touch (regular if they touch no ticket's files). Brief it to check before each push that `git status -sb` shows the Spec branch, and afterwards report that `git rev-parse origin/<branch>` equals `HEAD`, handling a rejected push as step 2 says. It fixes, commits and pushes, or disputes a Finding with its evidence, as `review-rounds` says; a later Round may continue it by message if its Findings need no higher tier. For a criterion a ticket's Implementer reported as owed, give the new Implementer it in its handoff (one clause), and after a fix that could change what an owed run showed, return to step 4 and make the run again before the next Round or the merge. Continue the review to its end, its after-Round-3 sort, design answers and Pre-existing filing included. Review policy belongs to `review-rounds`; the merge decision below remains yours.

The review ends **ready to merge**, or **waiting on a boundary** when a fix, a design answer, a bug Ticket or the merge would cross the Boundary record: then the merge waits, and `merging` brings the pull request to the user (step 8), naming the Finding and the boundary. Each bug Ticket the after-Round-3 sort creates is built straight after the Spec pull request merges, as a lone Ticket, with `implement`.

## 8. Merge, or bring it to the user

Load `merging` by name and follow it to its end: it decides whether you merge or bring the pull request to the user, and finishes it. Give it:

- the Spec pull request and the Spec it builds; as the issues to close where the tracker has no pull-request closing support, the Spec and the landed tickets;
- the method: a **merge commit**, not a squash, so main keeps each ticket as its own commit, titled with the Spec pull request's typed title (not the tracker's default merge title);
- an Implementer on the Spec branch (step 7's, or a new one briefed as there) as the committer of every commit the finish needs, so you still write no code;
- readiness: the review ended ready to merge, or is waiting on a boundary (step 7), which `merging` brings to the user;
- as its own pre-merge step, the closing-line reconcile: re-read the pull request body and apply step 6.5's rule again. The spec's own line and the lines of tickets that landed stay; remove any other ticket's line, and reconcile absorbed-source lines under `issue-absorption`. It runs last, just before any merge, the user's too, and again on each repeat when main moves.

The Spec pull request's Door is one-way if any ticket's call is, so any Ticket's one-way call makes the Spec one-way when `merging` decides who merges.

Done when `merging` has merged the pull request and closed the Spec and the landed tickets (and their eligible sources), leaving dropped or never-landed tickets and their sources unchanged, or the pull request is with the user and you have named what stops it (its "After the merge" then runs from step 10).

## 9. Clean up and report

Clean up the worktrees and local Ticket branches left (`git worktree list`, `git worktree remove`, `git worktree prune`). Remove those of a ticket that holds nothing ahead of the Spec branch, or has landed (step 6.4's part (a) only: later commits may have changed its files). **Keep the local Ticket branch of a ticket that has not landed** while this thread stays open (it waits on the user): its commits are unpushed, and the branch is what step 3.1 reuses on re-entry. Its worktree may stay too; if you remove it, remove only the worktree (`git worktree remove`, never with the branch), since a Ticket branch that survives without its worktree is not gone. Delete such a branch only when the ticket is dropped or the thread ends for good. Tell the user (or the coordinator) the pull request link and the outcome: merged with its merge commit, waiting on a boundary (the Finding and the boundary), or waiting for the user and why (what `merging` named), with any bug Tickets the review created and any ticket still waiting on the user. A report of waiting is not your end: stay open and re-enter at step 1 on the answer, report or wake that ends the wait (an unblocked ticket starts at step 3; step 6 ends again when it lands). For every merge of yours, also list each ADR, glossary, `CLAUDE.md`, `AGENTS.md` and `REVIEW.md` file it changed, and each agent design answer on it: the items of the `Agent-merged rules:` line.

## 10. Run the retro

Run the `retro` skill on this thread once the Spec pull request is merged and the spec and its landed tickets are closed, so the retro looks back on finished work. If you handed the pull request to the user, report as in step 9, stay open, and when they merge it or tell you that it is merged, first run `merging`'s "After the merge" (confirm the merge on the tracker, close the issues), then run the retro; if they drop it or close it unmerged, or no Spec pull request was opened because no ticket landed, ask whether they want a retro on what happened. If it finds a repeated Bug class to turn into a check, a regular-tier Implementer builds the check on a branch off main, in its own worktree made as in step 3.1 but off `origin/<default-branch>` (you still write no code), and you brief it as `implement` step 3 briefs one ([implement](../implement/SKILL.md)), not as in step 3.2: the branch is a lone one off main and is pushed, because the pull request needs it. Open its pull request with `pr`, its body recording `Retro origin: <Spec issue link>`; the check builds no issue, so its body is its spec. Review it as in step 7, with the check's own Implementer. Merge it by loading `merging` as `implement` step 7 does (squash, the check's own Implementer as committer, its Retro origin issue in place of a Ticket, which it closes none of): a check that changes `REVIEW.md` is merged by you unless `merging` brings it to the user, and listed on its `Agent-merged rules:` line. Tell the user (or the coordinator) the retro's outcome.
