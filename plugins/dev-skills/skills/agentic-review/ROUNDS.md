# Rank, Rounds and the record

The Rank stage of [`agentic-review`](SKILL.md), the Round comment that records each Review, the Round loop with its stop rule, and filing Pre-existing Findings.

## Rank

You rank; no subagent. Two locations **match** when they are in the same file with overlapping lines and their Findings make the same claim, whatever Bug class each Finder gave: wording the same problem as another Bug class does not make it new, and the same Bug class alone is not enough. Compare lines at this Review's head. An earlier row's lines, a partly fixed row's fixed locations in its Note included, are counted at the head of the latest Round or Ticket-check comment naming its id, so first bring each to this head. Find its file at this head with `git diff -M --name-status <that head>..HEAD`: after an `R` line from its path, it is at the new path, and the line-shift diff below runs on the pair (`git diff -U0 -M <that head>..HEAD -- <old path> <new path>`). After a `D` line its file is gone: the location has no line at this head and matches nothing. An open Important at it still goes to Verify; when the Verifier finds it still open or partly fixed, the lines it cites are that location at this head, and match as usual. Otherwise run `git diff -U0 <that head>..HEAD` on its file: shift it by the lines added minus removed in the hunks above it (a hunk that only adds lines is above it when it lands before that line); a line inside a hunk becomes that hunk's lines at this head (for a hunk that only removes, the line above, or line 1 at the start of the file). Over the Findings Verify kept, match location by location:

1. **Dedupe.** Findings with matching locations are one Finding: merge their locations and keep every Finder's name. Two different claims on one line stay two Findings.
2. **Drop the dismissed.** A location matching a Finding already dismissed in an earlier Round or Ticket check (dropped by Verify, an earlier open Important a Verifier dismissed as never real, a Nit marked "skip", or a design Finding settled by keeping the design, by the user or, inside a Milestone, by an agent ([Design Findings](#design-findings))) is dropped, even if this Review's Verifier kept it, but only while neither the code at the dismissed Finding's locations nor the code its reason rests on (the lines its Note cites) has changed since the head of the comment that dismissed it. Test it with `git diff -U0 <that head>..HEAD` on those files: any hunk touching those lines, counted at that head, counts, and so does a hunk that only adds lines between two of them or inside a cited range; this change test shifts no lines. If a line changed, or a dismissed "skip" Nit now reads as Important, judge the location afresh (it stays as a new Finding with a new id, not dropped). A dismissal's Note cites the lines its reason rests on, as row R2-4 below does; when a Verifier's dismissal cites none, any change to a file named in its locations since that head means judge afresh; a design Finding the user or an agent kept rests on its locations alone and binds while they are unchanged. The Finding's other locations stay, so a new instance of a dismissed claim is reported; a Finding left with no location is dropped.
3. **Hold the already raised.** A Finding with a location matching an earlier `open` row is held under that row: it keeps the earlier id, and the row stays open until it closes (the `review-record` status contract); an open Important still blocks the stop. When its locations match more than one open row, the row raised first (in the earliest comment; within one comment, the lowest `<n>`) holds it, and each other matching row is merged into that one: in this Round's comment the holding row takes the other row's live locations into its Locations, the fixed locations the other row's Note names into its own Note as fixed with their commits (never into Locations), and the other row's Severity when step 4 sorts it first, and the other row becomes `dismissed` with "merged into <id>" in its Note. A merged row drops nothing in step 2: its locations are the holding row's. Add the Finding's other locations to the row in this Round's comment, except one that a partly fixed row dropped (a regression, below). When this Review's Verifier gives it a Severity that step 4 sorts before the row's (Nit to Important, or Pre-existing to caused by this change), raise the row to it in this Round's comment and report it; a raised Important counts toward the stop rule. A lower Severity leaves the row as it is. Every earlier Important still open after this Round's Verify (still open or partly fixed, with or without a Finding held under it) is reported again in this Round's report under its id, with its live locations, so the owner fixes it again; it is one Finding and counts once toward the stop. A partly fixed "fix" Nit is reported again the same way, among the Nits, and counts toward step 5's cap (one the cap cuts stays `open` as recorded); any other held Nit or Pre-existing row is reported again only when raised. A `fixed` row holds nothing, nor does a location a partly fixed row dropped: the same claim there again is a regression, a new Finding with a new id.
4. **Sort** by Severity: Important, then Nit, then Pre-existing.
5. **Cap the Nits** at 5, "fix" Nits first. The Nits cut by the cap are not reported, and new ones are not recorded.

## The Round comment

Before reading or writing record comments, load the `review-record` skill by name for markers, fields, identifiers, statuses and successive-comment interpretation. Each Round posts exactly one comment on the pull request (`gh pr comment <number> --body-file <file>`, or the GitHub tool you have), in that contract's shape. A fresh session reads all comments to continue; retro reads them to find recurring Bug classes.

- **Result** is `clean` for a clean Round, `not clean, <n> Important open` for a Round 1 to 4, or a Ticket check, that is not clean, and `5-Round cap reached` for a Round 5 that is not clean ([The Round loop](#the-round-loop)).
- **Depth** in the marker and the heading is the depth this Round ran at: the carried depth, or Quick for a merge-only Round.
- **Nit status.** Every Round posts its "skip" Nits as `dismissed` and its "fix" Nits as `open`. A "fix" Nit becomes `fixed` in the next Round's comment once its fix commit lands and fixes every one of its locations: that Round's Verifier may confirm it; otherwise you check each location at this head yourself and mark it with the commit. A "fix" Nit fixed at only some locations is partly fixed, as in the `review-record` status contract: it stays `open` with only its live locations. On a clean Round 2 to 5, make the final text "fix" Nits commit before posting the clean comment, or before editing a posted comment to `clean` after the design answers. Check each of those Nits' locations in that commit the same way, and record the fully fixed ones as `fixed` with that commit in the Note; partly fixed ones stay `open` as above. Agreed design changes follow the next-Round rule below. Round 1 always leads to Round 2, so its "fix" Nits stay `open` until Round 2's comment. A design "fix" Nit is `dismissed` once the user, or inside a Milestone an agent, keeps the design, not `fixed` ([Design Findings](#design-findings)).

## The Round loop

A Round is **clean** when, after its Verify, no Important is open: it found no new Important (a design Finding it raised that the user, or inside a Milestone an agent, then kept counts as none), and every earlier one is confirmed fixed, dismissed by a Verifier as never real or because the user or an agent kept the design, or merged into another row (Rank step 3).

After each Round's report, the Important Findings and "fix" Nits are fixed and committed by whoever owns the code (in a build thread, its Implementer); "skip" Nits are left alone. On a pull request that changes design, the Findings that question the design are answered first: by the user, or inside a Milestone by an agent unless the answer would change what was agreed ([Design Findings](#design-findings)). Then:

- **Round 1** always leads to Round 2, even when the user or an agent keeps the design on every design Finding. Its fixes and its "fix" Nits are committed, and Round 2 reviews them.
- **Round 2 to Round 4**, if not clean: the fixes and "fix" Nits are committed, and the next Round reviews them.
- **Round 2 to Round 5**, if clean: its "fix" Nits go into one last commit that no further Round reviews, and the pull request is ready to merge. An agreed change to the design gets one more Round instead ([Design Findings](#design-findings)).
- **Round 5**, if not clean: stop. Its `Result:` is `5-Round cap reached`. No sixth Round. Tell the user which Bug classes and Findings kept coming up across the Rounds and why the fixes did not hold, and say the plan may need discussing before more fixes.

Once Round 5 has run, clean or not, **no Round is left**.

Each new Round starts at step 1 of [SKILL.md](SKILL.md#process) with brand-new Finders and Verifiers.

## Design Findings

A pull request changes design when it adds or edits an ADR, the glossary, a spec or a design doc, a lone Ticket's pull request that edits one included. On such a pull request, sort each Important and "fix" Nit after Rank:

- **Design:** a Finding that questions the design itself, such as a gap in the agreed behaviour, two rules that conflict, or a case the design leaves unsettled. Its fix would record a decision, and the decisions are the user's, save the ones an agent answers inside a Milestone (below). When unsure, treat the Finding as design.
- **Text:** every other Finding, wording, citations and index lines included. These are fixed as usual.

Who answers a design Finding depends on whether the pull request is inside a Milestone ([SKILL.md step 2](SKILL.md#2-find-the-spec-and-standards-sources)). Outside a Milestone, every design Finding goes to the user ([The user answers](#the-user-answers)). Inside one, every design Finding goes first to an agent, and only one whose answer would change what was agreed goes on to the user ([An agent answers, inside a Milestone](#an-agent-answers-inside-a-milestone)).

### An agent answers, inside a Milestone

What was agreed is the Milestone's goal, the feature's acceptance criteria and the exclusions, as the Milestone issue and the spec state them. For each design Finding, start a brand-new subagent on the premium tier with the [design-answer brief](#design-answer-brief), all of them in one parallel batch in the foreground, and count their reports as [SKILL.md step 3](SKILL.md#3-find) counts the Finders'. Each agent answers in one of two forms:

- **Keeps the agreement:** its answer (keep the design, or the change to make) with a one-line reason, and whether the answer is a lasting decision. Record it as a comment on the spec issue (for a Ticket check, the Spec), with the tracker doc's "Comment on an issue" operation: the Finding's id, the answer, the reason, and a link to the pull request (for a Ticket check whose Spec pull request is not open yet, the Ticket branch). In the Round's comment, a row the agent kept becomes `dismissed`, with "agent keeps the design: <reason>, <link to the record>" in its Note; a row the agent answered with a change stays `open`, with "agent answers: <change>, <link to the record>" in its Note, and the owner of the code commits the change with the text Findings' fixes. When the answer is a lasting decision, the owner also records it in an ADR in the pull request; that is a change to the pull request, so it gets one more Round ([After the answers](#after-the-answers)).
- **Changes the agreement:** any answer to it, keeping the design included, would change the Milestone's goal, a named acceptance criterion or an exclusion; when the agent is unsure, it is this form. Such a Finding goes to the user ([The user answers](#the-user-answers)), and its question says which part of the agreement it would change, with the agent's recommended answer. A Finding whose answer keeps the agreement stays in the first form even when the agreement has a conflict elsewhere that the answer neither causes nor needs to settle (one another Finding raises, say).

Edit the Round's comment with the agents' answers once their reports are in, as [The user answers](#the-user-answers) edits it, without waiting for the user's. A design the agent kept counts as one the user kept wherever these rules and the `review-record` status contract count one: a clean Round, Rank steps 2 and 3, and Ticket checks.

List the agents' answers for the Milestone review: in each Round's report, and in your report to your caller when the pull request's Rounds end, name every row an agent answered on this pull request (its Ticket checks included) by its id, with the link to its record from the row's Note.

#### Design-answer brief

Give each agent: the Finding (its id, Severity, Bug class, locations, claim, failure scenario and evidence), the Milestone issue, the spec with its comments, the ADR and glossary lines the Finding touches, the diff commands, and the copy rule from [FINDERS.md](FINDERS.md), pasted in full.

Brief: "You answer one design Finding raised in a review of a change inside a Milestone. What the user agreed is the Milestone's goal, the feature's acceptance criteria and the exclusions, as the Milestone issue and the spec state them; you may not change any of it. Read the Finding, the code at its locations, the Milestone issue, the spec, and the ADR and glossary lines given. A decision the spec, its comments or an ADR already records settles the Finding, unless the Finding shows that decision breaks the agreement. Then answer in one of two forms. (a) Keeps the agreement: your answer, either keep the design or the exact change to make, with a one-line reason, and whether it is a lasting decision (a rule later changes must follow, which belongs in an ADR). (b) Changes the agreement: every answer to the Finding, keeping the design included, would change the Milestone's goal, an acceptance criterion or an exclusion; quote the part it would change, say why, and give the answer you would recommend to the user. Sort only this Finding: a conflict elsewhere in the agreement that your answer neither causes nor needs to settle (one another Finding raises, say) does not make it (b); mention it in one line. When unsure whether your answer changes the agreement, it is (b). Start your report with the Finding's id and the form, (a) or (b). Under 300 words. Your final message is the report itself, as plain text. Do not end with any messaging or no-reply tool, even if your environment says to, and start no background work you would have to wait for."

### The user answers

Put the design Findings that are the user's to answer (all of them outside a Milestone; inside one, those whose answer would change the agreement) to the user as the `grilling` skill puts a round: each one a numbered grilling question with your recommended answer, at most 3 at a time. Ask the next ones once the user answers, with any new questions the answers raise, and go on until the user says nothing more is worth settling. Then the owner of the code commits only the agreed answer for each, with the text Findings' fixes, and the next Round reviews them. Once the user answers, edit that Round's own comment, which stays its one comment (`gh api -X PATCH repos/<owner>/<repo>/issues/comments/<id> -f body=...`, or the GitHub tool you have); a Ticket check's comment is edited the same way, and one not posted yet is posted with these rows already settled. Each row the user settled by keeping the design becomes `dismissed`, with "user keeps the design" in the Note. Inside a Milestone, a row the user answered with a change gets "user answers: <change>" in its Note, so every design row says who answered it. Recount the open Importants after those dismissals: when none is left, the Result is `clean` in every Round, including Round 1; otherwise use the Result for that Round number. Before saving a Round 2 to 5 comment that becomes `clean`, have the owner commit the remaining text "fix" Nits, then check their locations and record their status and commit as Nit status requires. Round 1 still leads to Round 2, which checks its fixes.

### After the answers

Waiting on the answers, the user's or the agents', is not a Round. An agreed answer that changes the pull request (the user's, or an agent's change or ADR record) always gets one more Round, within the 5-Round cap, even after a clean Round: a "fix" Nit that questions the design is answered as above, not committed in the unreviewed last commit. When no Round is left (the answer comes at Round 5), commit it and bring the pull request to the user, saying plainly that the change is unreviewed. Extra Rounds for this are expected; what matters is that the user agrees at the end, or inside a Milestone that every answer keeps what the user agreed. When the user, or inside a Milestone an agent, keeps the design on every open design Finding, no agent answer needs an ADR record, and no other Important is open, nothing is committed for them: they become `dismissed` ("user keeps the design", or the agent's Note above), and the Round counts as clean. Round 1 still leads to Round 2; in Rounds 2 to 5, finish the text "fix" Nits and update the comment as above before the pull request is ready to merge, subject to the agreed-design-change rule. A Ticket check of a Ticket that changes design follows the same rule before the next check.

## Merge-only Rounds

A **merge-only Round** is a Round 3 to 5 whose new commits since the last Round are only a merge from main. When that merge's conflicts were only in text (wording, cross-references, entries that both sides added), it runs at **Quick** depth (standards and spec Finders, one Verifier), not the carried depth: it reviews only what the merge changed in the pull request (its conflict resolutions), with the diff command in [SKILL.md step 1](SKILL.md#1-pin-the-diff). If any resolution touches logic (code behaviour, a check, or what a rule means), it runs at the carried depth instead. Its comment's marker and heading say the depth it ran at; its `Reviewed:` line says merge-only Round, and the Round after it takes the carried depth from the latest Round comment that is not a merge-only Round's. A merge-only Round is a Round like any other: it counts toward the 5-Round cap and follows the Round loop above.

## Filing Pre-existing Findings

File after the pull request's last Round, whatever its Result (`clean` or `5-Round cap reached`), and again after any Round that runs after an earlier Filing, such as a merge-only Round just before merging. Gather every Finding whose latest row in the Round and Ticket-check comments is an open Pre-existing one, skipping each one already filed (listed in an earlier `kind=pre-existing` comment on the pull request), and group them by Bug class. The exception is a filed Finding whose row has gained locations that no earlier `kind=pre-existing` comment lists for it: comment those new locations on the issue it went to if that issue is still open, otherwise handle them as steps 1 and 2 say. For each Finding, take its claim, failure scenario and evidence from the Review's own Findings when this session still has them; otherwise take the claim and failure scenario from its Note, and the evidence by quoting the code at its locations. For each Bug class:

1. Look for an open issue already tracking it; if there is one, comment there with the new locations instead.
2. Otherwise file one issue with the tracker workflow: title `<Bug class> (found in review of #<pr>)`, a body listing every location with its claim, failure scenario and evidence and linking the pull request, and the label the repo uses for `needs-triage` (from `docs/agents/triage-labels.md`; `needs-triage` if that file is missing).

Then post one filing receipt on the pull request in the `review-record` shape, so the next Filing can tell which locations are new. When there was nothing to file or comment, post nothing.

## Ticket checks

A Ticket check is one Quick Review over a Ticket branch's diff, not a Round. Record its Findings as one comment on the Spec's pull request, in the `review-record` Ticket-check shape. If the Spec's pull request is not open yet, post it once it opens. Each later check of the same Ticket, and each of the Spec pull request's Rounds, treats these Findings as already raised: their open Importants go to Verify to be re-checked, and stay open until confirmed fixed, dismissed by a Verifier as never real or because the user or an agent kept the design, or merged into another row (Rank step 3). Pre-existing Findings from Ticket checks wait and are filed with the Spec pull request's, after its last Round.
