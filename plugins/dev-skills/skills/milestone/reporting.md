# Milestone report

The coordinator owns the report comment on the Milestone issue. Build it against the latest agreement, not the initial plan. Read the feature issues and their acceptance criteria, their pull requests and evidence, every release issue's Triage batch summary and the Retro planning record it links, and the delivery records: the `team-lead` skill's audit trail (starts, nudges, replacements, parks, pauses and check-ins) and any earlier delivery records on the Milestone issue. A closed issue alone does not prove a feature merged: read its pull request's merged state and account for every issue in a Spec or related-issue feature. An abandoned or obsolete feature is a gap against the agreement unless the user agreed to its disposition. A feature with a parked Ticket is reported as parked, with that Ticket's blocker; the remaining unmerged work stays visible.

## Gather the evidence

Use the runtime's readable chat/session history and the tracker doc's **Read an issue** and **List issues** operations. Inventory the coordinator, verification (the check's probe workers included), planning, build and Release threads, including replaced threads and their Implementer subagents where records expose them. Link the source of each fact; report unknowns where histories or session records cannot be read. Runtime settings, recorded load paths and session usage are evidence; a current manifest is not proof of what an earlier thread loaded. Collect these records during delivery as they become readable, so an archived thread's unavailable history remains an explicit gap rather than silently disappearing.

- **User messages.** Read every user-authored delivery message in the coordinator and other threads and in issue and pull request comments. Keep a row per message with its time, source link or stable id, a concise faithful quotation or summary, and classification. Planned points are feature planning, the Milestone review, answering a parked feature's blocker, and an action the Boundary record or Milestone agreement requires the user to take. Cite the authority for that last kind. Mark everything else **unplanned step-in**, including the user noticing a problem or pushing a thread. A message with both kinds flags the unplanned part. Name unreadable histories and time ranges; invite the user to check the inventory at the review. Clean self-review or an incomplete inventory is no proof that no step-in happened.
- **Time and tokens.** For every thread, record its start and end (or last observed time for one still live), elapsed time, runtime, and session-record link. Give Milestone wall time from delivery start to report and summed thread elapsed time separately: overlapping threads do not add to wall time. Read session token totals using the runtime's own field meanings, retaining input, output and cached categories without counting cached tokens twice. Identify whether parent totals include subagents; count each usage record once and name unknown overlap. Give per-thread and total usage, with known subtotals explicitly partial where any record is missing. For skill loading, record the input tokens each thread kind spends on its main path, from session usage where attributable; label a delta that includes other input as an estimate with its basis. Where no defensible estimate exists, say unknown, with why. Estimates remain separate from measured totals. Time and tokens are records with no caps.
- **Versions and environment.** For each thread list the plugin version and load source/revision it actually recorded, or unknown. Include Startup verification result links and every probe's outcome and limits, including any user go-on after a failed essential probe. Name the runtime's permission mode and sandbox settings as recorded, distinguishing environments and changed settings; unreadable settings are unknown.
- **Agent decisions.** Read review records, build reports and the `Agent-merged rules:` line on merged pull request bodies for agent design answers (Finding id, answer, reason, record link) and rules-file merges (ADRs, glossary, `CLAUDE.md`, `AGENTS.md`, `REVIEW.md`, with file and merge link), and the check-in, replacement and park decisions and maintenance decisions the user should see. Name missing decision evidence rather than infer that no decisions were made.

## Post and stop

Post one comment with the tracker doc's **Comment on an issue** operation. First line `<!-- milestone report -->`, then `## Milestone report — ready for user review`, the agreement revision/source and report time. Use concise tables or bullets under:

1. **Outcomes:** every feature, each acceptance criterion, merged or parked outcome and evidence links. Distinguish satisfied, unmet and unverified criteria. Include any regression/end-of-Milestone checks actually run and their limits; invent no pass or user acceptance.
2. **Parked and maintenance:** every parked feature/Ticket, blockers, park evidence and whether a writer may remain; every maintenance issue left open from the Release batches/plannings, with its recorded reason.
3. **User messages:** the full per-message inventory and planned/unplanned classification, with visibility gaps clearly called out.
4. **Time and tokens:** per-thread records, totals, skill-loading usage by thread kind, estimates and gaps.
5. **Versions and Startup verification:** the per-thread versions/load sources, probe results and permission/sandbox settings.
6. **Agent decisions:** design answers, rules-file merges and other material decisions with their source links.
7. **Next Milestone:** suggestions from outcomes, blockers and maintenance records. These are proposals, not added scope; the next Milestone's planning step 3 lists them first.

End with `Ready for the user's Milestone review; acceptance pending.`, explicitly leaving the Milestone open. Read the comment back before telling the user its link and stopping delivery. If the write/read-back fails, report the failure and retry from the tracker at the next wake; a proposed or failed write is no posted report.

On re-entry, read existing report comments and compare the latest agreement and feature outcomes with their sources. Reuse the existing report for an unchanged review state: no duplicate comment, schedule-ending action or user notification. A later check-in while the report waits has nothing to do. If the user sends a feature back or lifts a park, re-read the agreement and tracker, resume only the authorized work through the `team-lead` skill (which arranges the check-in again), and post a new report when the gate holds again, linking the prior report and naming what changed. The user alone accepts the Milestone: stop for that review rather than declaring a proof run passed. When the user then accepts it in words after the report, close the Milestone issue, with the tracker doc's **Close** operation and a comment naming where and when they accepted.
