# Triage

Move issues on the project issue tracker through a small state machine of triage roles.

If this repo treats external pull requests as a request surface (see the issue-tracker config), triage covers them too: **a PR is an issue with attached code**, using the same roles, same states, and same machine, with a few deltas marked "for a PR" below. Resolve a bare `#42` to an issue or PR per the tracker config.

Every comment or issue posted to the issue tracker during triage **must** start with this disclaimer:

```
> *This was generated by AI during triage.*
```

This file describes triage as it runs with the user. At a Release end the Release thread runs the **Triage batch** instead (see "The Triage batch" at the end), where agents decide.

## Reference docs

- [AGENT-BRIEF.md](AGENT-BRIEF.md): how to write durable agent briefs
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md): how the `docs/dev-skills/out-of-scope/` knowledge base works

## Roles

Two **category** roles:

- `bug`: something is broken
- `enhancement`: new feature or improvement

Five **state** roles:

- `needs-triage`: maintainer needs to evaluate
- `needs-info`: waiting on reporter for more information
- `ready-for-agent`: fully specified, ready for an AFK agent
- `ready-for-human`: needs human implementation
- `wontfix`: will not be actioned

**Repo labels** are the labels the repo records for its own kinds of work, in the **Repo labels** table of its triage-labels doc: each a label string with one line saying when it applies. They are not roles, and the labelling rule is written here once; `to-spec`, `to-tickets` and `review-rounds` point to this paragraph. Read the table, and apply each label whose line fits the issue, by your judgement. A label the user named for the issue (in the request, or while planning it) goes on whatever you judge. Never apply a label that is not in the table unless the user named it. Remove a repo label only when you judge it no longer fits the issue, with a one-line comment on the issue saying why, and never remove one the user named. A repo with no table, or an empty one, has no repo labels: apply none, and leave any such label already on an issue as it is.

One **mark** role, `next-release`, says an issue must join the next Release; Release planning takes it and removes the mark. It is neither a category nor a state role. Set it on a `ready-for-agent` issue that is **severe** (a security hole, lost data, or delivery stopped: nothing can merge or ship) or that blocks a **planned feature** (one the Milestone issue lists: the open issue carrying a label in the Boundary record's Milestone label form, or for a batch the one its release issue names). Triage applies no release label.

An **agent-found enhancement** (an audit, investigation or retro finding: an enhancement an agent filed, or whose body says an agent found it) waits for the user at `ready-for-human`: the user decides every new feature, and only the user moves it on or closes it. An agent never ranks, closes, expires or marks one.

For a PR, the same states read against the attached code: `ready-for-agent` means a brief is attached and an agent should take the next step on the diff; `ready-for-human` means it's ready for a human to merge.

Every triaged issue should carry exactly one category role and one state role (the repo labels, when used, come on top of those). If state roles conflict, flag it and ask the maintainer before doing anything else.

These are canonical role names. The actual label strings used in the issue tracker may differ. The mapping should have been provided to you. If not, tell the user to run `setup-dev-skills`.

State transitions: an unlabeled issue normally goes to `needs-triage` first; from there it moves to `needs-info`, `ready-for-agent`, `ready-for-human` or `wontfix`, or closes as completed when it is already implemented. `needs-info` returns to `needs-triage` once the reporter replies. The maintainer can override at any time; flag transitions that look unusual and ask before proceeding.

## Invocation

The maintainer invokes `/triage` and describes what they want in natural language. Interpret the request and act. Examples:

- "Show me anything that needs my attention"
- "Let's look at #42" (issue or PR)
- "Move #42 to ready-for-agent"
- "What's ready for agents to pick up?"

## Show what needs attention

Query the issue tracker and present three buckets, oldest first:

1. **Unlabeled**: never triaged.
2. **`needs-triage`**: evaluation in progress.
3. **`needs-info` with reporter activity since the last triage notes**: needs re-evaluation.

When PRs are in scope, include external PRs in these buckets and tag each line `[PR]` or `[issue]`. Discovery surfaces only *external* PRs (the tracker config defines who counts as external), so a collaborator's in-flight PR is not triage work. This filter is discovery-only; an explicitly named PR is always triaged regardless of author.

Skip issues labelled `retro`: they are Retro issues, planned in batches, not untriaged work.

Show counts and a one-line summary per item. Let the maintainer pick.

## Triage a specific issue or PR

1. **Gather context.** If the issue is labelled `retro`, stop: it is a Retro issue, planned in batches, so skip it (a Retro the user takes into a Milestone is absorbed by its feature's Ticket, as `issue-absorption` says, not triaged). Otherwise read the full issue or PR (body, comments, labels, author, dates; for a PR, the diff too). Parse any prior triage notes so you don't re-ask resolved questions. Explore the codebase: start at `docs/dev-skills/index.md` (with no index, fall back to `docs/dev-skills/glossary.md` and `docs/dev-skills/adr/`), open only the docs that fit, and respect ADRs in the area. Run two checks against the codebase: (a) **redundancy**: search for an existing implementation of the requested behavior by domain concept (not just the request's wording), and report where you looked. If found, it's already implemented (step 5). (b) **prior rejection**: read `docs/dev-skills/out-of-scope/*.md` and surface any that resembles this request.

2. **Recommend.** Tell the maintainer your category and state recommendation with reasoning, plus a brief codebase summary relevant to the request (including whether it's already implemented). Wait for direction.

3. **Verify the claim.** Before any grilling, check that the claim holds up. For a bug, reproduce it from the reporter's steps. For a PR, confirm the diff does what it claims: check it out, run the relevant tests or commands. Report what happened: confirmed (with code path), failed, or insufficient detail (a strong `needs-info` signal). A confirmed verification makes a much stronger agent brief.

4. **Grill (if needed).** If the request needs fleshing out, call the Skill tool twice, for "grilling" and "domain-modeling", and grill it into shape a round of questions at a time, sharpening domain terms and updating the glossary (`docs/dev-skills/glossary.md`, or the Area page it points to once split) and ADRs inline as decisions land. When writing any doc here, including `docs/dev-skills/out-of-scope/` files, load `docs-index` and apply its contract.

5. **Apply the outcome**, with the repo labels that fit (see Roles) on an issue that stays open:
   - `ready-for-agent`: post an agent brief comment ([AGENT-BRIEF.md](AGENT-BRIEF.md)), and set `next-release` when the issue is severe or blocks a planned feature (see Roles).
   - `ready-for-human`: same structure as an agent brief, but note why it can't be delegated (judgment calls, external access, design decisions, manual testing).
   - `needs-info`: post triage notes (template below).
   - **Already implemented**: the change already exists on main. Close the issue as completed, without the `wontfix` label, and with a comment pointing to where it lives on main (the commit or pull request when you find it). Main already has the work, so an issue it blocks is unblocked. Write nothing to `docs/dev-skills/out-of-scope/` (that KB is for *rejected* requests, not built ones).
   - For `wontfix`, close the issue as not planned, with the comment depending on *why*:
     - **Rejected (bug)**: give a polite explanation, then close.
     - **Rejected (enhancement)**: write to `docs/dev-skills/out-of-scope/`, link to it from a comment, then close ([OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)).
   - `needs-triage`: apply the role. Optional comment if there's partial progress.

## Quick state override

If the maintainer says "move #42 to ready-for-agent", trust them and apply the role directly. Confirm what you're about to do (role changes, comment, close), then act. Skip grilling. If moving to `ready-for-agent` without a grilling session, ask whether they want to write an agent brief.

## Needs-info template

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

Capture everything resolved during grilling under "established so far" so the work isn't lost. Questions must be specific and actionable, not "please provide more info".

## Resuming a previous session

If prior triage notes exist on the issue or PR, read them, check whether the reporter has answered any outstanding questions, and present an updated picture before continuing. Don't re-ask resolved questions.

## The Triage batch

The Release thread runs the batch at a Release end, naming the Release just closed or its release issue. Agents decide: the user is asked nothing per issue, except as "Goes to the user" says. Before the first issue, read the release issue, the Milestone issue it names (goal, features, acceptance criteria, exclusions) and the Boundary record (`docs/dev-skills/boundaries.md`), and fetch main. Every comment triage posts here starts with the disclaimer above, and each one on an issue names the Release, so a rerun can tell what this batch already did. Skip `retro` issues throughout.

### 1. Triage the new issues

For every open `needs-triage` issue:

1. Gather context and verify the claim (steps 1 and 3 of "Triage a specific issue or PR"). Where the issue needs fleshing out (step 4), settle it by reading the code, docs, ADRs, the Milestone issue and the issue's comments; ask nobody.
2. Decide the category and the state, with the Roles rules for `next-release`, agent-found enhancements and repo labels. When "Goes to the user" applies to the issue, apply nothing (no brief, no label change) and leave it `needs-triage`. Otherwise apply the outcome as step 5 says: an agent brief for `ready-for-agent`, a brief for `ready-for-human`, triage notes for `needs-info`, a close as completed for an already-implemented one, a reasoned close for `wontfix`.
3. Record the decision on the issue in a comment: category, state, any mark, any repo label added or removed and the reason (a removed repo label's one-line reason can be this comment).

Done when no open issue but those waiting on the user is at `needs-triage`.

### 2. Sweep the backlog

The **sweep** keeps the `ready-for-agent` backlog true, since Release planning ranks all of it. For every open `ready-for-agent` issue (those part 1 just moved there included), take the first test that fits:

1. **Agent-found enhancement**: move it to `ready-for-human`, with a comment saying why. Nothing else in the sweep touches it.
2. **Duplicate**: it reports the same problem or asks for the same change as another open issue. Keep the one with the fuller brief (the older when they are even), close the other as a duplicate (as not planned where the tracker has no duplicate outcome) with a comment linking the kept issue, and comment on the kept issue anything only the closed one said.
3. **Obsolete**: main's current code no longer has the problem or already does what the issue asks; reproduce it or read the code to confirm. Close it as completed, since main already has the work and nothing is left to do, with the reason: where on main it is fixed or done, and the commit or pull request when you find it. A planned feature it blocks is then unblocked, as a close as completed counts as done.
4. **Needs the mark**: it is severe or blocks a planned feature and lacks `next-release`: set it, with a comment giving the reason.
5. **Expired**: it is listed under "Left out" in the release issues of each of the last 3 Releases cut (the one just closed and the two before it). Find the two earlier release issues by the name, label and title forms the repo's release doc (`docs/dev-skills/release.md`) gives (the Releases whose names come just before the closed one's), and read only each one's "Left out" section. Close it as not planned, with a comment naming those Releases and saying "reopen to bring it back". With fewer than 3 Releases cut, nothing expires. A planned feature, a Ticket of a planned Spec, a parked issue and one already marked `next-release` never expire.

A planned feature, or a Ticket of a planned Spec, that reads as a duplicate or obsolete is not closed: closing it would change the Milestone's agreement, so it goes to the user. Any other issue stays as it is.

Done when every open `ready-for-agent` issue has been through the tests.

### Handled at once

An issue that blocks a feature being built now, and a severe one, are triaged as soon as they are seen, outside the batch, with no Release named. Whoever sees one triages it as part 1 does for one issue, which gives it `next-release` once it is at `ready-for-agent`, and its comment says it was handled at once; "Goes to the user" applies to it too. The next batch's summary lists it.

### Goes to the user

Ask one question per decision, saying which kind it is, for a decision that:

- **crosses a boundary** in the Boundary record,
- **changes the Milestone's agreement** (goal, acceptance criteria, exclusions), for example a person's request for a feature the Milestone issue does not list, or closing a planned feature, or
- needs the issue's **conflicting state roles** settled.

The issue keeps its labels until the user answers, and the summary lists it as waiting on the user. Every other decision is the agent's.

### The summary

At the end, post one comment on the release issue. It starts with the disclaimer and then the heading `## Triage batch`, and lists every issue the run decided, changed in the sweep or handled at once since the last summary, one row each: issue, category, state, reason, and one outcome of `next-release`, `stays open`, `ready-for-human`, `closed` (duplicate, obsolete, already implemented or `wontfix`), `expired`, `waiting on the user` or `handled at once`. An issue the sweep left as it was gets no row. A rerun for the same release issue posts a new comment under the same heading, covering only what it decided; an issue whose comment from this batch is already on it is not decided again.

### Dry run

When the caller asks for a dry run (proposals only), run parts 1 and 2 and the "Goes to the user" test, and write nothing to the tracker: no comment, label, close, brief, `docs/dev-skills/out-of-scope/` file or summary, and ask the user nothing. Return the rows the summary would hold, plus for each the outcome you would apply, in your reply.

Any merge-time step the repo's own docs give is not part of the batch; it stays at or after the merge it belongs to.
